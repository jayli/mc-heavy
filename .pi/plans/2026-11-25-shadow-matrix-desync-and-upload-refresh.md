## ⚠️ 最重要的更正（先读这一节）

**本文档初版把症状一归因为「阴影矩阵上传/重算时序错配」，那个结论是错的 —— 它是我的测量伪象。**

- 初版探针在 **`renderer.render()` 入口**取 `shadow.matrix` 当作「采样侧的值」。
  但那一刻 GPU **还没上传**，读到的是「本帧刚算好的新值」或「上帧旧值」取决于时序，
  与 GPU 实际拿到的字节**无关**。
- 换成正确取样点（`renderer._bindings.updateForRender` **之后**读
  `uniformsGroup.values.slice(offset, offset+16)`，即真正写进 GPU 的字节）后：
  **desync 恒为 0**，无论修法在不在位。
- 据此写的「矩阵一致性」Tier 4 用例是**无效判据**（注入缺陷后仍 PASS），已删除；
  `game.js` 里那段 `updateMatrices` 提前调用是**无效修法**，已回退。

**教训（已同步 `docs/pitfalls.md`）**：判「GPU 用了哪份数据」必须在**上传完成后**读
GPU 侧缓冲，不能在 JS 侧函数入口读源对象 —— 后者与被测量之间隔着整条上传链。

## 一、症状二：整片沙漠突然全覆盖阴影 —— 根因确认并已修复

### 根因

阴影按需重渲（DR-5 `autoUpdate=false`），原有**三个**刷新请求源
（`game.js` 的日夜方向 / 玩家编辑 / 移动超 5 格）**都不覆盖「新几何发布」**。

玩家走动时新列不断加载 → 这些几何不在阴影贴图里（贴图是它们出生前渲的）⇒ 新地形无影；
等某次移动阈值或日夜门控放行，一次重渲把**积累的所有新几何**一起纳入 ⇒
观感就是「刚才还没有，突然整片沙漠全是阴影」。

### 实测（`probe10`，沿 +X 走 200 格）

```
i=190  sections 720  refreshes 8
停下    sections 675  refreshes 8
+2 秒   sections 792  refreshes 9   ← 117 个新 section 只换来 1 次刷新
```

### 修法（复用既有 200ms 节流 —— 用户 2026-11-25 拍板）

1. `src/core/scheduler.js`：新增 `onSectionsUploaded(cb)` 订阅入口（与既有
   `onColumnReady` / `onColumnWillRemove` 同款），在 `_processUploadQueue()` 末尾按
   **`uploaded > 0`** 触发一次（按帧聚合，不逐 section）。
   ⚠️ 用「队列非空」代替 `uploaded` 会在「全是已卸载/过期项」时凭空通知。
2. `src/core/game.js`：装配处订阅 → `if (this.sunLight.castShadow) this.shadowScheduler.request();`
   （与其余三源同一 `castShadow` 不变式）。节流器天然把加载期请求合并到 ≤5Hz。

⇒ 唯一可能的请求源就是新几何发布。实测 `requests=44`、sections 179→369、`playerMoved=0`。

## 二、症状一：走动时影子刷新变化 —— 尚未定位到可修根因

### 已排除的假设（都有实测）

| 假设 | 实测结论 |
|---|---|
| 纹素对齐（texel snapping）失效 | **排除**：noon 下连续移动 + 每帧强制刷新，影区亮度 spread **0** |
| 阴影矩阵上传/重算时序错配 | **排除**（我的测量伪象，见开头更正）：正确口径下 desync 恒 **0** |
| 贴图内容与采样矩阵不一致 | **排除**：`probe17` 逐帧读 VSM RT，`mapChangedPx=0` 而屏幕仍跳 22.96 |

### 已确认的事实（`probe21`，世界静止 + 玩家静止 + 每帧强制刷新）

| 模式 | 最大点跳变 | >4 的跳变次数 |
|---|---|---|
| `noon`（太阳方向恒定） | **1.97** | **0** |
| 日夜循环（太阳方向推进） | **8.27** | **6**（全在刷新帧） |

⇒ **跳变与「太阳方向是否在推进」强相关，与「玩家是否移动」无关。**
`probe22` 进一步量到：着色用的 `uSunDirection` 每帧连续推进，而阴影贴图按
`SUN_DIR_GATE_DEG=0.5°` 门控 + 200ms 节流离散刷新，两者方向差最大 **0.0135**（归一化分量）。

### 但这条还不能直接当根因修 —— 后续四个探针又把它推翻了

`probe20` 的交替对照显示：**关掉阴影后仍有 4.65 的跳变**，且 `probe19` 里
`secDelta=0`（世界完全稳定）时仍出现 22.55 跳变 ⇒ 屏幕取样里混着非阴影层噪声。
于是又跑了四个探针分离噪声底，结果把「方向不同步」这条也推翻了：

**第二轮**（世界静止 + 玩家静止 + 每帧强制刷新，`reflect=0&ambient=0`）：

| arm | 最大点跳变 | >4 跳变 |
|---|---|---|
| A 阴影关（噪声底） | **0** | 0 |
| B 阴影开 + noon | **0** | 0 |
| C 阴影开 + 日夜 120s/天（**比真实快 10×**） | **1.34** | **0** |
| D 阴影开 + 日夜 **1200s/天（真实速度）** | **0.75** | **0** |

⇒ 前一轮的「6 次跳变」在关掉反射/环境特效后**完全消失**；且我那轮用的是
`cycleSeconds=120`，而**默认是 1200**（`daynight.js:381`）—— 把太阳速度人为放大了 **10 倍**，
效应量不可外推到实玩。

**第三轮**（同夹具内逐项开关，不隐藏 HUD）：基线 4 次 → 只关反射 2 次 →
再隐环境特效 **0 次** → 恢复反射 6 次 → 方向钉死 noon 0 次。

**第四轮**（**只做环境特效开关**的干净交替对照，反射恒关、方向恒 noon、三轮）：
**六个 arm 全部 0 次跳变**（maxJump 0.44~3.83），且 `fxVisibleMax` 恒为 1 ⇒
**`mesh.visible=false` 没拦住特效**（渲染器每帧 sync 写回）⇒ 第三轮那个「隐藏」无效，
它的 0 跳变不能归因于特效。

**诚实结论（已被后续探针更新，见下一节）：症状一在 clear 档夹具里没能稳定复现。**

尚欠的关键一步：用户截图里有**雨丝**（雨天光影档开着），而前面全部探针都跑在
`weather=clear` 且**未开雨天档**。雨天档会改湿表面/雨丝/水花三层材质，且它们都消费
`uShadowStrength` 实例（`storm-rain-material.js` / `leaf-fx-material.js`）。

### ❌ 根因③尚未解决（已证存在，修法失败已回退）

**机制**：`texelSnapOffset` 只钉住**网格相位**（uv 小数部分），相机中心仍随玩家连续平移
⇒ 固定世界点的 uv **整数部分**在变 ⇒ 采到别的纹素。实测：同一世界点 70 帧内
采到 **6 个纹素**（503→526→552→578→603→629）。VSM 模糊邻域（radius 2.6 纹素）在不同
纹素上覆盖到不同世界几何 ⇒ `mean` 变 ⇒ `step(z,mean)` **间歇**翻转。
**这就是用户说的「时有时无、找不到规律」** —— 它是数据相关的，取决于那棵树周围几何的深度分布。

**试过的两个修法，均失败并已回退**：

| 方案 | flips | 纹素数 | 覆盖代价 | 结论 |
|---|---|---|---|---|
| 相机完全世界固定 | 0 | **1** | 走 220 格仍在盒内（夹具） | 真实世界跑远会没影，违背「边缘可刷新」语义 |
| 粗格吸附 cell=32 | **1** | 2 | 140 格掉出 | 没彻底解决 |
| 粗格吸附 cell=64 | 探针 0，**入生产后 2** | 1 | 180 格掉出 | ☠️ **且打破既有门禁** |

☠️☠️ **cell=64 入生产后同时出现两个真失败（实测输出）**：
```
✘ 光源跟随玩家：target=[282.94,21.98,117.03] player=(289.0,22.0,117.0)
  差 6.06 格，容差 0.153 ⇒ 真实行为回归（相机不再覆盖玩家所在几何）
✘ 身边影子恒定：实测 2 次翻转（mean 0.034 ↔ 0.2598）
```
⇒ 探针里「包一层 `_updateSunPosition`」的量法与生产串联不等价，探针结论不可直接外推。
**已整体回退**（`snapCenterToCell` / `SHADOW_CENTER_CELL` / 对应单测全部删除，grep 残留 0）。

⚠️ **负向验证的判别力不稳**：绕过③修法连跑 3 轮 ⇒ flips 0/1/2（只 2 轮红）。
间歇缺陷 + 单轮采样 ⇒ 不能凭这个分布宣布任何一侧成立。

**下一步（未做，需重新设计而非调参）**：③ 要的是「保持已投影内容的纹素映射不变」
的相机投影策略（类似 stable shadow projection / 阴影图重投影），而不是格长/频率这类参数。
它同时必须满足「相机覆盖玩家所在几何」（既有门禁），两者如何兼得需单独设计。

### ✅ 本轮已交付且已验证的部分（根因①②）

**① 沿太阳方向的平移污染深度编码** —— 光源 = `玩家位置 + dir×60`，玩家一走就产生沿 dir
平移，而正交阴影相机 z 是「世界点到光源的视空间深度」线性编码 ⇒ 固定世界点 shadowCoord.z
随玩家漂。纯数学单变量（零 GPU 噪声）：沿 dir 平移 30 格 ⇒ zSpread **0.10003**；垂直平移 ⇒ **0**；
玩家沿 −Z 走 30 格 ⇒ **0.06002**。判据余量仅 0.011 ⇒ 必然翻转。
修法 = `depthStableCenter`（沿 dir 分量钉死在首次定位锚点、垂直分量跟随）。

**② 相机平移与贴图重渲不同帧** —— 两条触发路径原本先动相机再 request()，节流器可能吐后
⇒ 矩阵已新、贴图还旧。修法 = **把相机重定位推迟到 tick 放行那一帧**，与重渲原子提交。
⚠️ 反过来「相机一动就强制刷」已实测否决：draw call 523→901、frameP95 9→10。

**实测（新 Tier 4 不变式用例，量「固定世界点此刻有影/无影」而非屏幕亮度）**：
HEAD **4 次翻转**（帧 11/23/35/59）/ zSpread **0.055018**；只修① ⇒ z 恒 0.0453 但仍 2 次翻转；
①+② ⇒ **flips 0 / zSpread 0**。负向验证：同时注掉两处 ⇒ 真 FAIL。

**⚠️ 曾被误当根因的「刷新节奏」（用户当场驳回：治标不治本）**：
实测刷新间隔 = 「200ms 内走过的距离」（慢走 0.804 格 / 中速 1.8~5.1 / 快走 6~6.5），
68 次 request 只换 12 次刷新。**那只回答了「多久变一次」，没回答「为什么不该变的东西变了」**
⇒ 是现象不是根因。降低 minIntervalMs 属治标，本轮未做、也不建议做。
