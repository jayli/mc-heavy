# 简化 CLAUDE.md：活跃约束按归属分三类搬走细节

## 现状

CLAUDE.md **548 行**，其中「活跃约束」两段共 **228 行 / 64 条**（占全文 42%）：
- `### 活跃约束（历次改动沉淀）`：46 条，133 行
- `### M6 丧尸沉淀的活跃约束`：18 条，95 行

每条都夹带大量实测数据、根因叙事与版本号引用。这让 CLAUDE.md 从「协作规范」变成了
「改动记录 + 约束手册」的混合体，与它自我声明的「本文件不复制进度表 —— 同一事实的
多个副本会漂移」冲突。

## 核实结论：三类归属不同，且副本分布不均

逐条核实后（不是凭印象分类）：

| 类型 | 条目数 | 细节现状 | 新家 |
|---|---|---|---|
| **进展/改动记录** | 约 22 条 | 部分只在 CLAUDE.md（「避开树半径」「桅杆判据」在设计文档 0 命中），部分已有副本（cutout 标定在 roadmap v1.37、五处偏离在设计文档 §4.3） | `docs/roadmap.md` |
| **测试方法论** | 约 6 条 | **「恒真陷阱」在 `testing-policy.md` §2.5 已有完整副本（比 CLAUDE.md 更详细）**；「导航监听武装」「指纹步长采样」只在 CLAUDE.md | `docs/testing-policy.md` |
| **架构口径**（持续生效） | 约 36 条 | 多数只在 CLAUDE.md | **留在 CLAUDE.md**，只压缩表达 |

**关键**：不能一刀切「全搬进 roadmap」—— 架构口径类（如「形状唯一权威 = mesher」
「`_discardEdits` 唯一入口」「`WorkerPool.call` 返回 `{id,promise}`」）不是历史记录，
是持续生效的实现约束，搬到「进度总览」文档会失去作用（没人改代码前去查进度文档找约束）。

## 改动方案

### 1. `docs/roadmap.md`：新增「活跃约束详情」段（承接进展类细节）

放在「M3.2 之后的独立 bugfix / 改造」表之后，按主题分组：

- **结构撒布**（v1.37/v1.38 沉淀）：四条路径 / 四处有意偏离（含「避开树半径 2」的实测
  保留率数据、`seededRandom` 守红线 2、判定不带 occupied 参数、不撒水下）/ 撒布密度刻意
  低于 mc-lite 的两条冻结断言 / `CODE_GENERATED_SCATTER_TYPES` 派生基准 / ship 门控与
  桅杆判据
- **渲染与容量**：cutout 离散 ×1.5 扩容与 550 标定 / 五处有意偏离清单（指向设计文档 §4.3）
  / lilypad 几何与格位耦合
- **M6 丧尸沉淀**（18 条全搬）：WorkerPool 形状 / performance.now 基准 / 全新 state+数组 /
  物理轴顺序 / visible=false / onDespawn 单槽覆盖 / column 卸载回收顺序 / findSpawnY 云面 /
  atan2 反解旋转 / MOVING_EPSILON 单一权威 / 单位换算 / S 路线隐含前提 / worker 消费共享
  纯函数 / WebGPU 不支持 groups / BoxGeometry vdir 符号 / Tier 4 阈值匹配 outputColorSpace /
  烘焙产物指纹门禁

同时**修掉循环引用**：v1.37 段现在写着「详见 CLAUDE.md 活跃约束」→ 改为指向新段。

### 2. `docs/testing-policy.md`：扩写 §2.5 + 新增小节

- **「恒真陷阱」那条直接删**（§2.5 已有完整副本，CLAUDE.md 是重复）
- 新增 §2.6「断言落点的三类踩坑」，承接只在 CLAUDE.md 的方法论：
  ① 计时类断言须交替对照（含「HEAD 侧失败率反而更高」的实测结论）；
  ② 重载类断言的导航监听须在触发动作**之前**武装；
  ③ 测试指纹口径须匹配改动范围（步长采样 vs 全量求和）；
  ④ 时序不定的竞态只能用内存侧断言钉住
- 负向验证的 7 类盲区高发区也归这里（它是测试方法论，不是进展）

### 3. `CLAUDE.md`：活跃约束段压缩到约 36 条（只留架构口径）

保留的每条**压成 2~3 行**：结论 + 「勿照直觉改回」的理由 + 指向细节。例：

改前（6 行）：
> 「避开树」半径 = **2**（mc-lite house 8/10、pavilion-tallWell 5~7）—— mc-heavy 城市树
> **无互斥**，密度 1.39%（mc-lite 约 0.44%，高 3 倍），照搬大半径会把撒布结构**全部挡掉**
> （实测各半径保留率：2→66~72% / 7→2~3% / 8~9→**0%**）

改后（不保留在本文件，细节进 roadmap）；而架构口径类如：
> **形状与 UV 的唯一权威 = `src/mesh/mesher.js`**（`TEMPLATES`/`FACE_VERTICES`/`FACE_UVS`）。
> 图标烘焙与等轴测投影只 import，禁止手写第二份几何定义（红线 1）。

保留原样（它已是 2 行、且是持续生效的口径）。

预计 CLAUDE.md **548 → 约 330 行**（活跃约束段 228 → 约 100 行）。

### 4. 交叉引用一致性

- CLAUDE.md「当前进度」段的一句话现状压缩（现在 8 行、夹带 M6 TODO 细节）→ 指向 roadmap
- CLAUDE.md 各保留条目末尾加「细节见 roadmap『活跃约束详情』」
- roadmap「去哪找细节」表加一行指向新段
- testing-policy §9「本文的自检」若列了章节清单，同步加 §2.6

## 验证

- 无代码改动 → 不跑测试，只跑 `npm run check`（lint 会扫 markdown？不会，但确认无回归）
- **人工核对三条**：① 每条搬走的细节在新家可检索到（`grep` 关键词）；
  ② CLAUDE.md 无悬空引用（指向的段名真实存在）；③ 无重复副本（同一细节不在两处各写一份）
- `git diff --stat` 确认行数变化符合预期

## 风险

1. **搬错归属会让约束失效**：架构口径搬进 roadmap → 改代码的人不会去进度文档查约束。
   故分类必须保守：拿不准的留在 CLAUDE.md。
2. **细节丢失**：若某条细节只在 CLAUDE.md 而我误判为「别处已有副本」→ 删掉就丢数据。
   故每条搬走前须 grep 确认新家确实有（或我确实写了进去）。
3. **roadmap 变长**：新增约 120 行。可接受 —— roadmap 本就是「去哪找细节」的索引文档，
   承接实测细节符合其章程；而 CLAUDE.md 是每次会话都加载的，压缩它的收益更大。
