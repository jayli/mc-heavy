## 编辑与数据

- `WorkerPool.call()` 返回 **`{id, promise}`** 而不是 promise。只判 `typeof then` 会走同步分支拿到
  那个对象（无业务字段）→ 回包静默丢失。写 fake pool 时必须返回同形状。
- 时间基准统一 `performance.now()`，禁止 `Date.now()`（相差约 17 亿毫秒，任何到期判定会恒真/恒假）。
- `WorldData.getSectionView()` 曾经逐格 `Map.get`（5508 次/次调用 × 每帧 64 次派发）是慢帧根因；
  改这里先解析 9 列再逐格取。**量帧只能用 `perf.snapshot().frameMs`**，用 rAF 包的另一个口径恒定偏高。
- 编辑热路径一次 `WorldData.readCell(x,y,z)` 读出 id/meta/entity，别分别调三个 getter（同一换算做三遍）。
- 光照类缺陷的断言必须落在**画面**上：数据层（`col.light`）对、网格层（上传的 packed）旧，两者会分裂。
  诊断顺序 = 整图参考 BFS → 拦截 `uploadSection` 比对 → 截图。

## 方块语义

- `opaqueTable=1` 有**四项**后果：面剔除、AO 遮挡、blocklight 阻断、炮塔 LOS/弹丸阻挡（改玩法）。
  只要面剔除就用 `cloud` 手法（`cullMode:"opaque"` + `opaque:false` + `SAME_TYPE_CULL`）；
  非 box 几何必须显式写 `"opaque":false`，否则转换规则会按 cullMode 误推 opaqueTable=1。
- 判断方块渲染语义读 mc-lite 的 `MaterialManager` + `BlockData`，不能只看本仓 `cullMode`。
- 朝向：台阶/栏杆的 facing→orient 映射**只能用真实 mesher 实测定**（给方块设 orient 读发射顶点
  的 bbox 跨度判断高侧），不能从 `orientation.js` 或 Minecraft 定义推。倒置台阶刻意不复用
  `cobblestone_step_updown`（那个是「颠倒 + 水平镜像」，高侧差 180°）。
- 碰撞类断言必须在两侧实测值之间取阈值（曾写「峰值 < 4」，而自由跳跃本身 3.0 → 注入回退仍全绿）。
- **地下结构的「空气格」必须写进烘焙产物**（废弃堡垒 v2.89）：nbt 里房间是**显式 air**，
  而 `rasterizeStructure` 只写产物里的格 ⇒ 不写空气则 `fillColumn`+`carveCaves` 的天然岩层
  会填满整个地牢（22.6 万格白搬）。做法：palette 加 `air` 条目（id=0、`cullMode:'none'`
  不渲染任何面），`setBlock(…,'air')` → `blocks[idx]=0` 清空格。**零运行期代码改动**。
  ⚠️ 失效形态是静默的：格数/类型/指纹全对，只有挖下去才发现 ⇒ 必须用**内容级判据**
  （air 格数）钉住，指纹拓不到。
- **产物 bbox ≠ footprint bbox**（废弃堡垒 v2.89）：写进产物的空气会把包围盒撑大
  （实测 106×63×108 → 107×63×110）。AABB 早退 / 避让 / 压制 / 干燥判据一律用**非空气 bbox**
  （= footprint，HALF_X/HALF_Z），用产物 bbox 会各多算 1 格。
- **从 mod 素材看「柱」不能只看外观**：`end_stone_pillar` 在 mod 里是 `cube_column`
  （顶/底 `_top` + 四侧 side）= **完整正六面体**，不是细柱。用户口述「半粗石柱」是视觉误读，
  必须读 mod 的 `models/block/*.json` 定几何（本仓按 `geometry:'box'` + 六面贴图数组烘焙）。

## 坐标与旋转（骨骼动画）

- 实例原点两套口径：mc-lite 几何以**块中心**为原点（`position.set(x+.5,...)`），本仓模板以**块底角**。
  比对上游几何数字时必须 +0.5。
- 从实例矩阵反解旋转用 `atan2(m[8], m[0])`，**不能** `Euler.setFromQuaternion`（`asin` 在 |θ|>π/2 折叠）。
  判「相机歪头」读基向量（`up.y`/`right.y`），不能读 `camera.rotation.x/z`（yaw=π 时是等价表示）。
- 坐标类判据一律非负取模：`wx % 16` 在负坐标返回负值 → 判据恒真。
- **锚点搜索的「方向」是载荷性的，照抄另一侧的判据会 8/8 seed 全返回 null**（废弃堡垒 v2.89）：
  大竞技场在城东，城市净距判据是 `wx - HALF <= city.maxX + CLEAR → 拒绝`；废弃堡垒在城西，
  必须是 `wx + HALF_X >= city.minX - CLEAR → 拒绝`。第一版照抄了城东那行 ⇒ 每个候选都被
  city 判据拒掉，9ms 就退出（结构永不生成，且**没有任何报错**）。同理瞬移落点：城东结构落在
  **西**缘外、城西结构落在**东**缘外（都是「靠 City 的那一侧」），照抄 `toBeLessThan` 会恒红。
- 三层 v 方向翻转（BoxGeometry 各面 `vdir` 符号不同 + `TextureLoader.flipY=true` + 皮肤矩形按图左上
  原点写），调试时必须走**真实加载路径**（`DataTexture` 的 `flipY` 与 `TextureLoader` 相反，用它造探针会得出假结论）。
- **Bedrock/Java 骨骼旋转的数值 ≠ 标准右手系的 `Euler(x,y,z,'XYZ')`**（焰魔 v2.58，曾误诊为「设计幅度大」）：
  矩阵是 `Rz·Ry·Rx`，关键帧与 bind **欧拉角逐轴相加**，且 Bedrock 几何 y 与 Java 相反 ⇒ 落到 Bedrock 几何空间必须取
  `Rz(−θz)·Ry(+θy)·Rx(−θx)`（`bake-ignis.mjs` 的 `bedrockRotation` 是唯一入口，飞龙是 bbmodel，不适用）。
  **两侧「数值逐帧一致」证明不了姿态一致** —— 症状（蓄力向身后抡、劈砍变尖刺、躯干后仰）只在比对**世界坐标**时现形：
  用 `tools/ignis-java-reference.mjs` + `test-ignis-bake.js` 的冻结表；动画「看着不对」时先比世界坐标，**不要加衰减补丁**。
- ⚠️⚠️⚠️ **SkinnedMesh 的顶点必须是「绝对模型坐标」，不能用骨骼局部坐标**（守卫 v2.93 实测）：
  skinning 公式 `bindMatrixInverse · (bone.matrixWorld · boneInverse) · bindMatrix · p`，
  **bind 姿态下 `bone.matrixWorld · boneInverse ≡ I`** ⇒ **顶点原样返回**。
  skinning 只做「相对 bind 的**形变**」，**不做「骨骼局部 → 模型空间」的摆放**。
  用局部顶点的形态：24 个盒全堆在原点 —— 用户描述是「**腿没分开 / 脑袋长到肚子上 / 手臂进入身体**」
  （实测最大误差 **3.29 格**、两腿间隙 **−0.5**、正面宽高比 **0.877** 而不是 1.26）。
  修法：烘焙时顶点**预乘该骨骼的 bind 世界矩阵**（`vertexConvention: 'java-model-absolute'`）。
  焰魔的 Bedrock 顶点本来就是绝对的，所以它没这个问题 —— **不是 bind 时序问题**
  （`bind()` 内部已 `updateMatrixWorld(true)` + `calculateInverses()`，两种时序结果逐位相同）。
  ⚠️ **离线轮廓光栅化对这类缺陷零判别力**（它直接乘世界链，绕过了 skinning）：
  判据必须落在 three 自己的 `SkinnedMesh.applyBoneTransform` 上（`test-guardian-skinning.js`），
  且要钉**解剖学关系**（腿间隙/头高/臂位置）而不只是顶点数。
  ⚠️ 探针里 `mesh.bind()` 必须在**bind 姿态**下调用（先摆回 bind → bind → 再摆到目标帧），
  否则 boneInverses 把动画姿态当 bind，造成 3.5 格假失配。
- **Java 与 Bedrock 的顶点坐标系不同，渲染器公式也不同**（守卫 v2.91）：Java `addBox` 的 origin 是
  **骨骼局部**坐标，Bedrock 是**绝对模型**坐标。本仓守卫取口径 A（保留局部顶点 + 仅 `y→−y`）
  ⇒ `localPosition = pos/16`（y 取反）、`pivot` 恒零、渲染器 `bone.position = localPosition + delta.pos`。
  **照搬焰魔的 `pivot − R_current·pivot + delta` 会把模型炸成碎片**（pivot 为零时它退化成「丢掉 localPosition」），
  而骨骼数/盒数/顶点数/指纹全对。哨兵：`root.localPosition === [0,−1.5,0]`（`check:data` 钉住）。
  ⚠️ **`feetOffsetY` 是「相对脚底」的量，会随它变**：核心盒 `center[1]` 同理 —— 改了烘焙器就得重算两者。
- ⚠️⚠️ **box UV 铺开：Bedrock 与 Citadel（Java）不是同一套表，不得互照**（守卫 v2.92 实测）：
  把 `bake-ignis` 的 `boxUVRects` 照搬到守卫 ⇒ **576 角中 480 个 UV 错**（±X / ±Z / −Y 全错，+Y 恰好对），
  而骨骼数/盒数/顶点数/索引数/UV 值域/指纹**全部通过** —— 只有画面能看出（躯干亮面朝下、
  护甲渐变上下颠倒、侧面整体错位）。权威在 `tools/citadel-box-uv.mjs`，判据在 `test-guardian-uv.js`（逐角）。
  三条非显然的子坑：
  · **mirror 的 `positionsIn[j] ↔ positionsIn[i-1-j]` 搬的是整个 `{position, uv}` 元素**
    ⇒ 「角位置↔UV」配对**不变**（只改绕序）。**只对调 UV 会把 7 个 mirror 盒上下翻转**（168 角）；
    mirror 对 UV 的真正影响**只来自** `swap(x, f)`。
  · **面法线必须由角位置推，不能查静态表**：`swap(x,f)` 让标为 EAST(+X) 的四角落在 x **最小**侧
    ⇒ 静态表会让 7 个 mirror 盒共 80 角失配。
  · **按角位置查 UV 必须先按法线筛面**：每角被 3 个面共用 ⇒ 24 顶点里同一位置出现 3 次、UV 各不同，
    在全量里 `find` 会取到别面的 UV（实测 304 个假失配）。角匹配容差取 **1e-6**（负 inflate 盒的浮点往返差 ~1e-16）。
  ⚠️ **Citadel 源码的 8 角变量名后缀与声明顺序差一**（`...vertex7` 是第 1 个角）—— 手抄索引极易错，
  用程序化提取（本次调查手抄连错 5 版）。
- **旋转约定已验证无缺陷，不要“顺手修”**（守卫 v2.92）：口径 A（顶点翻 y + localPosition 翻 y +
  `Rz(−z)Ry(+y)Rx(−x)`）与「整条链在 Java 空间全正号算完再乘 `F=diag(1,−1,1)`」**逐点等价**
  （bind/strongR/stomp/uppercut 四姿态 576 顶点最大差 **0.000000**）。形态不对时先查 UV，别动旋转。
- **Java `move` 关键帧的 y 符号**：Java y 向下，`move(leg,0,−9,−9)` 是**抬腿** 9px
  ⇒ 产物 `pos.y = +0.5625`。转反的形态是「出招时身体往反方向纩」，而计数类判据全对。
- **动画帧数取「关键帧 tick 合计」而不是 `Animation.create(n)` 的声明值**：守卫上勾拳声明 100
  但关键帧只到 **90** ⇒ 照声明值烘焙会多出 0.5s 静止尾巴。
- **解析 Java 角度时 `Math.toRadians` 的后缀正则必须大小写都认（`/i`）**：守卫混用 `5f` 与 `32.5F`，
  而焰魔素材全大写。只写 `F?` 时小写那批解成 **null** → 四元数 NaN（JSON 落 null），
  实测 1415/2730 个四元数报废而骨骼数/帧数/指纹全对 ⇒ 靠**归一化断言**拓。
- **程序化 idle 的「空姿态」不会触发过渡器切换**（守卫）：移动→静止时 target 从非空变空 Map，
  而来源 key 两边都是 'idle' ⇒ 不走淡入 ⇒ 那几根骨骼从输出里消失 ⇒ **永远冻结在最后一个摆臂姿态**。
  渲染器必须每帧把整副骨架（位置**和旋转**）复位到 bind 再写本帧驱动的骨骼。
  （焰魔没这问题：它的 idle 是烘焙片段，始终驱动同一批骨骼。）

## 渲染与 GPU

### ☠️☠️☠️ 同一盏灯挂两个 `ShadowNode` ⇒ 争抢单一 `needsUpdate` 却共享 `shadow.matrix`（v3.41，v3.40 五轮没找到的真根因）

用户报「走动时身边影子跳变」+「整片沙漠突然全是阴影」。**真根因不在阴影管线本身，
在水面倒影的反射替身材质**：`render-world.js` 的 `beginReflectMaterialSwap()` 用
`createVoxelMaterials(atlas, this._sunLight, null)` 造替身（v3.33 为避 WebGPU 读写冲突），
而 `materials.js` 里 `shadow(sunLight)` **每次调用都 new 一个 ShadowNode** ⇒ 全场景多出第二个。

- **共享与独立的部分要分清**（three r185.1）：`shadow.needsUpdate`（单一标志）、
  `shadow.matrix`（单一 Matrix4）、`shadow.camera` 都是**共享**的；
  而 `shadowMap` / `vsmShadowMapHorizontal` 是 `setupShadow` 里 `builder.createRenderTarget`
  ⇒ **每 node 独立**。这个「标志共享、贴图独立」的组合就是缺陷。
- **失效链**：`_renderWaterReflection()` 在主 `renderer.render()` **之前**跑 ⇒ 替身 node 先
  消费 `needsUpdate`（渲完置 false，`three.webgpu.js:45504`），并在 `renderShadow` 里
  `updateMatrices` 写**共享矩阵**（:45331）⇒ 主 node 看到 false 不渲 ⇒
  **主 pass 用新矩阵采样旧贴图**。反射每 2 帧 + 200ms 节流 ⇒ 刷新权随机交替 ⇒「时有时无」。
- **修法**：反射期把 `needsUpdate` 暂存置 false、`finally` 里原样写回（`game.js`）。
  代价是替身自己的贴图长期陈旧 ⇒ **倒影里**地形阴影偏旧，主画面不受影响。
  ⚠️ 不要为修倒影让替身也渲 —— 那正是成因。
- ☠️ **判据必须量「主 pass 实际采样那张 RT 的刷新归属」**，不是「阴影刷新有没有发生」。
  主 RT 身份要从 `renderObject.getBindings()` 按 `texture.id` 反查
  （实测主 node 是 **idx=2**，不是第 0 个 —— 按序号假设会量错对象）。
  实测 40 帧每帧 request：主 RT 只刷 **1** 次，其余全落在别的 RT。
- ☠️ **只量矩阵一致性抓不到它**（v3.40 第 2 轮 desync 恒 0 的原因）：矩阵的 JS 值与 GPU 字节
  **都是新的、完全一致**，旧的是**贴图内容**那一半。判据要落在
  `gap = (z − mean) × (far − near)` 守恒 + 主 RT 刷新次数（下界）**与其它 node 刷新次数 = 0（上界）**。
- **交替对照 3 轮**（每轮换源码、新页面）：修复态 mainRefresh 62/64/61、otherRefresh **恒 0**、
  gapSpread **恒 0**；缺陷态 mainRefresh 13/11/7、otherRefresh 49/51/54、gapSpread 245/11.5/245、flips 恒 2。

### ⚠️⚠️ 「采样点在影区」不能写成 sanity floor（v3.41，负向验证的判别力陷阱）

新 Tier 4 用例首版把 `gapMin > 0` / `litFrac < 0.5` 放在**前提断言**里。
负向注入后**先撞 sanity 而红**（实测 gapMin −236.116）⇒ 证明不了「主判据有判别力」。
处置：影区归属改由**主判据**承担（修复态 gap 恒正 2.6838，缺陷态掉负），
sanity 只留「与缺陷无关的观测前提」（反射跑了 / 替身存在 / 相机动了 / 采样入图）。
改完负向落在主判据 `mainRefresh=49 < 60` 上，判别力才成立。

### ⚠️⚠️ 反射类夹具必须让 pass **真的跑**：`reflectHeightFade` 读的是**相机** y（v3.41）

首版标定探针照抄既有 `setupShadowPlatform`（平台 y=80、相机 y=102），
而 `REFLECT_HEIGHT_ZERO=48` ⇒ fade=0 ⇒ 反射 pass 整个不跑 ⇒ 替身不消费刷新权 ⇒ **判据全绿毫无意义**
（实测 `reflectDelta=0`）。处置：平台压到 y=6、相机 y≈9。
⚠️ 同源坑：手动摆光源会与帧循环的 `_updateSunPosition()` 打架（实测 z 在两个值间跳）⇒
夹具应把光源交给游戏自己的移动阈值路径。

### ⚠️ 源码结构型断言不要用固定字符窗口（v3.41，既有守卫被注释长度误伤）

`test-puddle-reflect.js` 用 `src.slice(i, i + 900)` 取反射装配段。本轮在该段插入注释后
`endReflectGuard()` 落到 900 字符外（实测跨度 **1388**）⇒ 守卫对**正确的代码**真红。
处置：窗口按「到 `endReflectGuard()` 为止」取。判据要锚在结构上，不锚在字节数上。

### ☠️☠️☠️ 「把光源沿太阳方向的分量钉死」会把阴影深度推出远平面（v3.40，我引入的回归）

用户报「眼前的树一会有影一会没影」，我据「沿 dir 平移会改变正交深度编码」这个**正确的观察**，

- ⇒ **「诊断正确」不等于「修法正确」**。改一个载荷性常量前，先问它原本在保证什么不变式。

### ⚠️⚠️⚠️ 判「GPU 用了哪份数据」必须在**上传完成后**读 GPU 侧缓冲（v3.40，我自己的测量伪象）

用户报「走动时身边影子每 5 格刷新一次」。我把它归因为「阴影矩阵的上传时刻早于重算时刻」，
写了修法 + Tier 4 用例，单变量对照还「验证通过」（desync 0.0225 → 0）—— **全是假的**。

- **错在哪**：探针在 `renderer.render()` **入口**读 `sunLight.shadow.matrix`，当作「采样侧的值」。
  那一刻 GPU **还没上传**，读到的是 JS 侧源对象的当时状态，与 GPU 真正拿到的字节隔着整条上传链。
  于是「入口值 vs 贴图生成值」的差只是**函数调用顺序**的产物，不是缺陷。
- **正确取样点**：`renderer._bindings.updateForRender(renderObject)` **返回之后**，从
  `renderObject.getBindings()` 里找到 `uniform.getValue() === shadow.matrix` 的那个 uniform，
  读它所在 `uniformsGroup` 的 `values.slice(uniform.offset, +16)` —— 那才是写进 GPU 的字节。
  换成这个口径后 **desync 恒为 0**，修法在不在位都一样 ⇒ 根因不存在，修法与用例一并回退。
- **发现方式 = 负向验证**：注掉修法后用例**仍然 PASS**。若跳过负向验证，就会带着一个恒真判据
  和一段无效修法交付。⇒ 这是「负向验证是必需环节」的又一次实证。
- ⚠️ 两条歧路（都试过、都失败，勿重试）：① 遍历 `renderer` 找 `updateMatrix4` 的 prototype
  —— 不可达；② 拦 `UniformNode.prototype.update` 判 `this.value === shadow.matrix`
  —— 命中 0 次（`onUpdate` 包装后 `this` 绑定与实例判据不匹配）。
- ⚠️ **同一轮里「屏幕亮度跳变」也不能直接当阴影缺陷的判据**：`?shadows=0` 后仍量到 4.65 的跳变，
  且 `sections` 完全不变时也出现 22.55 ⇒ 取样里混着非阴影层噪声。要先量噪声底再谈效应量。

### 真倒影：复用已验收资产前必须核对**镜面高度**（v3.33，实玩证伪）

用户要「水汪里映出建筑和树」。SSR 五种方案 + 自建镜像 pass 约 30 个探针全失败，
改用 ocean 已验收的 reflector 后我一度宣布成功 —— **用户实玩截图证伪：没有倒影**。

- ⚠️⚠️⚠️ **复用反射资产前先核对镜面高度与被反射面的高度差**：
  `ocean.js` 把 `reflectTarget` 挂在海面平面下，镜面高度恒为 **y=−1.5**；
  城市地面在 **y=22~28** ⇒ 差 **24~30 格**。镜像相机渲的是「海平面之下往上看」，
  与脚下地面毫无几何对应 ⇒ 采到均匀色块。
  实测：抬到 22/23/24 后水汪区开始变化、截图出现塔基暗影。
  **「几何近似、mip 能掩盖偏差」对 24 格错位不成立。**
  ⚠️ 改高度时要把 `reflectTarget` **从 plane 下摘出入场景**，
  否则 `ocean.update` 每帧把 plane 重置回海平面，local 偏移无效（实测 mirrorY 恒 −1.5）。
- ⚠️⚠️ **`ReflectorNode.clone()` 的 value 独立**：reflector 只把真 RT 写进
  `base.textureNode.value` ⇒ 消费 clone 前必须**每帧同步**，否则永远采 **1×1 占位图**。
  该坑 `ocean.js:555-557` 注释早已写明 —— **读到坑不等于落实了坑**。
- ⚠️⚠️ **体素材质采样反射 RT 时，feedback 的正解是「换同构替身材质」**：
  把采样权重 uniform 置 0 **不够** —— texture 节点仍在 bind group 里，
  WebGPU 按**绑定**算 usage。替身必须是**同一个 `createVoxelMaterials` 但不传 RT**
  ⇒ 除不引用 RT 外着色完全一致。用**常量基色**当替身会让 RT 内容错。
- ⚠️⚠️ **反射 pass 必须包 `beginReflectGuard()/endReflectGuard()`**（现成守卫，
  隔离 BatchedMesh `_indirectTexture` 覆写）—— 自建镜像 pass 那轮完全漏了它。

### 量 GPU 片元成本：两个常用口径都是假的（v3.32）

用户追问「对性能影响有多大」时实测，两个直觉口径先后被推翻：

- ⚠️⚠️⚠️ **连续 `renderer.render()` 压测测的是 CPU 命令编码时间，不是 GPU 执行**。
  它只编码并提交就返回（实测 0.24ms/render 画 977 draw call）。三档对照下
  「开湿表面反而比晴天快」—— 看到这个就要知道口径错了，不是「优化生效了」。
  （v3.17 量水面反射时用这招是对的 —— 那里成本大头在 **draw call 提交**；
  本轮成本在**片元 ALU**，同一招就失效了。）
- ⚠️⚠️ **`device.queue.onSubmittedWorkDone()` 在 Chromium 上不保证阻塞到片元完成**：
  加了它之后三档仍全在 0.31ms，且依然出现「开湿比晴天快 −0.008ms」。
- ✅ **有效口径：放大片元数看斜率**。片元成本 ∝ 覆盖像素数 ⇒ 用离屏 `RenderTarget`
  （或 `setPixelRatio`，**但要读 `canvas.width` 确认真的变了**）把像素数放大，
  在**最大档**上做交替对照（小档噪声压倒信号：512² 同档读到 0.575 与 0.23，
  2048² 两次重复收敛到 0.775/0.755）。绝对值里混着 CPU/驱动固定开销，**只有差值有意义**。
- ⚠️ **vsync 锁帧会把一切 GPU 成本掩盖成 0**：本机 120fps ⇒ 帧间隔恒等 8.3ms。
  但「放大 9× 像素后仍恒等 8.3ms」**本身就是结论**（GPU 余量极大），
  与「没放大成功」区分的方法就是读 drawing buffer 尺寸。

### 被钳位的参数再乘系数是恒等 —— 「积水斑没有反光」（v3.32，用户实玩报告）

用户：「实现了地面的水汪的效果，水汪没有反光」。形状对、位置对、数值判据全绿，就是不像水。

- ⚠️⚠️⚠️ **`min(x, 1)` 钳位之后再乘任何 >1 的系数都是恒等**：v3.31 的积水修正写了
  `specGain × 1.60`，但 `wetSpecGainAt` 结尾就是 `Math.min(p[3] * k, 1)`，而抛光/冰类的
  `specGain` 本来就是 **1.0** ⇒ ×1.60 后仍是 1.0。积水 reflK 只从 **0.1883 → 0.1962（+4%）**，
  却额外 `albedo × 0.88` 压暗 12% ⇒ 屏幕上水汪比周边**暗 5.9 luma**（石材暗 3.0）。
  GPU 侧交叉验证：开档后地面区 mean luma **181.58 → 178.32**（净变暗）。
  ⇒ 想让某个**已饱和**的量再涨，必须给它一条**独立的绝对目标**（`mix(原值, TARGET, 掩码)`），
  不是再乘一个系数。判据要钉「目标量真的涨了」，而不是「系数写了」。
- ⚠️⚠️ **太阳高光在光滑面上数学恒为 0，抬增益零作用**：积水处 rough 0.0875 ⇒
  `wetShininess` **320.6**，半俯视机位 N·H 0.677 ⇒ `pow(0.677, 320.6)` = **4.94e-55**。
  「反光不够就抬高光」在这类机位上是无效旋钮（它只在掠射角可见）。
- ⚠️⚠️ **标定强度必须代入掩码的真实峰值，不是 1.0**：`smoothstep(0.52, 0.76, n)` 而
  perlin 的 n 实测 p95 才 **0.753** ⇒ 掩码峰值只到 **0.7682**（绕开 ACES 直接量）。
  按 p=1 算会**高估效果 26%**，于是「公式说 +21 luma、屏幕只有 +15」。
- ⚠️ **量噪声/掩码分布必须 `mat.toneMapped = false`**：ACES 会把 0..1 压扁，
  第一次探针经 ACES 读到「n 的 p50=199/255」，反推回去完全是错的分布。
- ⚠️⚠️ **光滑面 + 单色天空 = 纯色塑料板**：积水处 rough→0.015 ⇒ 天空渐变带宽极窄，
  而正午 `sky` 与 `fogColor` 同为 `0x87ceeb` ⇒ `skyEnv` 在整个水汪内几乎同一颜色。
  只抬反光强度会得到一片均匀色块。真实水汪反的是**阴天云层** ⇒ 必须加低频噪声调制
  （尺度要比积水斑**大**，且噪声 z 取非零常量与积水噪声去相关，否则每摊水自带一个亮斑）。

### 串联的两道门：负向注入只删一道 ⇒ 判据恒真（v3.32）

- ⚠️⚠️⚠️ **注入前先数清楚有几道门在拦同一个缺陷**：本轮 `puddle` 里有
  `.mul(select(isTop,1,0))`，`puddleW` 里又乘了 `topGate`。负向注入只删前者时
  `puddleW = puddle × 0 × strength = 0` ⇒ 墙面**逐位不动**，注入根本没造出缺陷
  （实测 Δ=0.00，看起来像「判据失效」，其实是注入无效）。**两道门必须同时去掉**。
- ⚠️⚠️ **弱效应的区域判据要用位级差异，不能用 luma 阈值**：墙面 wet 只 **0.187**
  （`WET_WALL_FACTOR 0.22 × wetGain 0.85`），镜面漏上去的加权效应只 **0.05~0.8 luma**
  ⇒ 任何 `|Δluma| > 1` 的阈值都被 8bit 量化吞掉。改成 `diffBytes == 0`（正向）/
  `> 0`（负向）后判别力无穷：正向墙区 **0 字节**，负向 **51357 字节**。
- ⚠️ **掠射机位的信号强度要先扇描再定阈值**：同一夹具只改相机，
  仰视 11.8°（noV 0.164）→ Δluma **1.30**；俯视 30°（noV 0.640）→ **3.60**。
  前者贴着判据下界，后者有 1.8 倍余量。**机位是判据的一部分，不是夹具的装饰**。

### 上游「独立地面 mesh」的 shader 不能挂到体素通道（v3.31，用户实玩报告）

用户：「为什么远处的云层和近处的岩壁上有光晕，很明显」。**不是雨雾**，是三个错配叠加。

- ⚠️⚠️⚠️ **上游 shader 的隐含前提是「地面就在镜面高度」**：`bj-shooting-game` 的
  `GROUND_FRAG` 服务一张独立地面 mesh（y=0），所以它的
  `vReflPos = uReflMatrix * vec4(wp.x, 0.0, wp.z, 1)`（压平到镜面再投影）是 **no-op**。
  挂到起伏体素上后，那一步只对**玩家脚下那一层**成立 —— 墙面 / 云层 / 任何其他高度
  的面都采到别处内容（天空暖白）。**这是方案层面的错，不是参数层面的错**：
  v3.30d 新建第二条 pass 把镜面移到玩家脚下，只修好了一层，其余仍错。
- ⚠️⚠️ **「侧面完全不湿」的注释与实现不符**：`wet = uWet*(0.3+0.7*up+0.55*streak)`
  在 up=0、streak 满档时给到 **0.85**（跑纯函数实测）。墙面于是吃到近乎满强度的镜面反射。
  正解是**离散朝向权重**（顶面 1 / 侧面 0.22 / 底面 0），不是连续 `max(N.y,0)`。
- ⚠️ **流水纹在竖面被拉成长条**：沿 y 的空间频率 `0.045×3.2=0.144` vs xz `0.55×3.2=1.76`
  ⇒ 竖直拉伸 **12.2×** ⇒ 读作「岩壁上的竖直亮带」。
- ⚠️⚠️ **`cloud.cullMode='opaque'` ⇒ 云也吃体素通道的任何材质分支**。
  云在 y=35/55、顶面 up=1 ⇒ wet **1.0** 满强度。凡「挂在体素材质上的地面效果」
  都必须显式把云排除（本仓的正解：材质分类表里 `cloud → NONE`）。
  自发光体（lava/glowstone/ochre_froglight/hanging_lamp）同理 —— 再叠反光会读作双层光源。
- ⚠️⚠️ **屏幕空间体积雾对天空吃满额距离权重**：`distK = T/(T+18)`，而天空背景的
  `viewZ` 恒为相机 far ⇒ T 被钳到上限 120 ⇒ distK **0.87**。于是「朝太阳一侧的暖色薄纱」
  铺满天空。bloom（阈值 0.9 / 增益 0.16）再把它和上面的亮斑扩散成「光晕」。
  ⇒ 用户裁定整条后处理链删除。**任何按 viewZ 加权的屏幕空间层都要先问「天空的 viewZ 是多少」**。

#### 材质分类不能进新顶点属性（内存门实测）

- ⚠️⚠️ 三通道静态 `gpuVertexBytes`：24B/顶点 = **193.83 MiB**，28B/顶点 = **219.68 MiB**，
  而 `tests/m3-fullscene.spec.mjs` 的门是 **200 MiB** ⇒ **加一个 float 属性直接超门 19.7 MiB**。
  正解：塞进 `packed` 的空闲位（Uint32，现用 bit0–14 ⇒ bit15–18 装 4 bit / 16 类），
  **零字节增量**，且 mesher 是 Worker/主线程共用同一份 ⇒ 两条路径自动一致。
- ⚠️ 分类是**逐 quad 常量** ⇒ 顶点阶段查 `uniformArray(...).element(cls)` 得 vec4，
  经一个 varying 传片元（常量插值逐位精确，片元零查表）。
  `uniformArray` 走 uniform buffer，**不会退化成逐顶点属性**。

#### 反光量级：Schlick 菲涅尔在半俯视只给 7%（v3.31 标定实测）

- ⚠️⚠️ **「湿地面要看得见反光」与物理正确冲突**：noV≈0.53（俯视 32°）时 F≈**0.068**。
  用真实 atlas 基色（Smooth_Stone 线性 luma 0.3816）+ 天空 0x87ceeb（0.5529）算，
  抛光石的 Δluma 只有 **1.46**（sRGB 0~255）⇒ 8bit 量化 + ACES 后屏幕上分不开。
  三个旋钮全扇描（`WET_REFL_MAX` 0.55→1.0 / 菲涅尔幂 5→3 / F0 基数 0.02+0.04→0.04+0.16）
  最强也只 **3.81**。**这是结构性的，不是参数没调够** ⇒ 必须让用户裁定要不要偏离物理。
  用户选「加非物理地板」⇒ `floor = 0.28 × (1−rough)` 加在 F 上，抛光 Δluma **6.19**。
- ⚠️ **地板必须随粗糙度衰减**：否则布/植被也反光，材质分层就没了。
  实测抛光 6.19 vs 布 0.06（差 100 倍）。
- ⚠️ **太阳高光不能用来抬俯视机位的读数**：noon 方向下 N·H≈0.677，而 shin 119~350
  ⇒ `pow(0.677, 350)` 下溢到 0。它是「对着太阳的掠射角」才可见的项，符合物理。

#### 判据选型：本轮四条假红/假绿（全部实测推翻）

- ⚠️⚠️⚠️ **写死屏幕相对坐标的取样区会恒真**：我按直觉写 cloud=[0.30,0.02,0.70,0.20]、
  wall=[0.30,0.34,0.70,0.52]，而真实 `camera.project` 是 cloud fy **0.043**、wall fy **0.641**
  ⇒ 两个区**取到的是天空**，「云/墙不变」两条判据恒真（负向注入落地却 frac 不变）。
  **正解：取样区由真实投影算包围盒**（8 角点 project + 内缩 15%），
  并加夹具前提断言（区不退化 / 云在墙上 / 墙在地面上）⇒ 恒真被结构挡住。
  机位也要**由几何算**：fov 70° 半角 35°，三目标跨度 37.0° 时才都入画。
- ⚠️⚠️ **「变化像素计数」不能判光晕**：光晕的定义是「局部**变亮**」，而正确实现是
  「轻微**压暗**」。墙面压暗 5.2% 会让 frac 达 **0.667**（超过 d>8 阈值），但那不是光晕。
  ⇒ 改量**亮度幅度**（墙面 Δluma ≤ 0.5 且 |Δ| < 6）。
- ⚠️⚠️ **最终 luma 不能用来排材质反光序**：它同时吃「压暗」与「反光」两个**反向**项 ——
  SOIL 压暗最狠（0.62），尽管反光比 FABRIC 强，最终 luma 反而更低
  （实测 wood 168.89 > stone 166.91，期望 stone>wood）。⇒ 把 darken 固定 1 做单变量。
- ⚠️⚠️ **「相邻像素相同率」不能用绝对阈值**：匀质石头贴图的**场景本身**就有 0.8521，
  效应层 0.8506 与它几乎相同 ⇒ 写「eff < 0.60」把正确实现判成红。
  硬格子的形态是效应层**显著高于**场景水平 ⇒ 判据是 `eff < sceneSame + 0.05`。
- ⚠️ **注入确认不能全文件 `includes`**：jsdoc 里有同串公式说明 ⇒ `hasMix` 恒真。
  必须只扫**代码行**（滤掉 `*` 与 `//` 开头的行）。
- ⚠️ **负向注入要选对面**：相机仰视云时，云**底面**法线·视线 0.509、**侧面** 0.861
  ⇒ 侧面才是主可见面；而底面 up=−1 ⇒ orient=0 **完全不湿**。
  取样区取底面会让「cloud→STONE」的注入零判别力。


- ⚠️⚠️⚠️ **反射/阴影类额外 pass 必须在主 `renderer.render()` 之前跑**（水面倒影 v3.17 实测）：
  把 three 的 `reflector()` 挂在水面材质上让它**自动触发**时，它在 **transparent 队列末尾**才跑，
  而 BatchedMesh 的 instance 索引走 `_indirectTexture`（**GPU 纹理**）、一帧内**最后一次写入胜出**
  ⇒ 主 pass 的 `drawIndexed` 执行时读到反射相机的索引表 ⇒ **地平线以上整片天空撕成黑多边形**
  （近黑占比 **1.26% → 11.66%**），而 draw call / 三角数 / 帧时 / uniform 值**全对**。
  **三条假修法已实测排除，勿重试**：① 快照/恢复 multi-draw 列表（v1.46 阴影那套）——
  主 pass 已先 draw 完，快照时机不对；② 改 `renderOrder`（1→99）—— blackTop 逐位不变；
  ③ 改 `bounces` true/false —— 同样撕。**正解**：`updateBeforeType = NONE` + 装配层在主 render 前手动调。
  隔离手法：只加 target / 换常量色 / 采样但不跑 pass 三档均不撕，挂 opaque 材质不撕 ⇒ 锁定是**时机**。
- ⚠️⚠️ **水面加倒影必然提亮水面，「降强度」治不了**（v3.17）：固定掩膜均值实测
  **纯倒影 luma 185.9 = 天空亮度**、无倒影水面 127.4 ⇒ 反射亮天空就会把水抬白（物理正确，
  但撞用户四轮标定的冻结色阶 108~124）。强度扫描 0.5→155 / 0.15→137 / 0.08→133，
  要入带得压到几乎 0 = 倒影没了。**正解是新增「水面吸收」反射率**（水面不是理想镜面）。
  ⚠️ **吸收率必须随环境亮度减弱**：反射 RT 里的世界**已是夜景**（吃 `uSkyDim` + night 立方图），
  按白昼标定的吸收率再乘一次 = 双重压暗 ⇒ 固定吸收率时 TINT 0.18~0.30 扫下来 **night 恒 65~69**
  （下界 70，怎么调都出不了带）。有效吸收率按 `1 − 均值(uWaterTint)` 向 1 回升后 night → **73**，
  而晨/午 tint 中性 ⇒ 回升项 ≡0 ⇒ 那两档逐位不变。
- ⚠️ **「水面在不在视野里」不能用包围球判**（v3.17）：水面是 800×800 巨平面且**每帧跟随相机**，
  它的包围球**永远**与视锥相交 ⇒ `frustum.intersectsSphere` 恒真、门控形同虚设（实测 gateSkip 恒 0）。
  必须用**相机高度 + 俯仰**这两个真实自由度（`reflectVisible`）。
- ⚠️⚠️ **量额外 pass 的成本必须绕开 vsync**（v3.17）：rAF 下 120fps 锁帧会把 +0.9ms 的 GPU 成本
  掩盖成「帧时一点没变」。正解是**连续同步 `renderer.render()` 压测**取均值。
  另两个探针坑：① 包 `node.updateBefore` 得 `renders=0` 却看到画面变了 —— three 在 build 期已绑定
  原函数，**「零成本」是假象**，要包 `renderer.render` 才量得到；② `texture(node.value, …)` 捕获的是
  **占位 RT**（`updateBefore` 每帧把真 RT 写进 `node.value`）⇒ 画面只变暗没有倒影，
  正解是直接把 `ReflectorNode` 当纹理节点用（它本身就是 TextureNode，自带正确 UV）。
- ⚠️ **降反射 RT 分辨率几乎不省钱**（v3.17 实测）：0.125 与 0.5 只差 **0.1ms** —— 成本在
  反射 pass 的 **draw call 数**（vd16 发 1546 次），不在像素数。⇒ **朦胧靠 mip、省钱靠节流**
  （每 2 帧刷把 vd16 的 +0.93ms 降到 +0.36ms）。把倍率往下压是无效优化，只白损失倒影形体。
- ⚠️ **用众数峰量「参数敏感性」会得出假结论**（v3.17）：强度 0.5→0.18 时众数 luma 只从 160 降到 142，
  看着「几乎不敏感」——那是直方图**跳档**（不同强度下选中不同簇）。改**固定掩膜均值**
  （用基准帧选像素、两侧量同一批）后严格单调：155.4 / 146 / 137.5 / 133 / 127.4。
- ⚠️⚠️ **上游 raw GLSL `ShaderMaterial` 在本仓一行都不能用**（Nova Beam v3.20 实测）：
  `three.webgpu.js:86728-86740` 的 NodeMaterial 库只注册 12 种内置材质，**没有 ShaderMaterial**
  ⇒ `fromMaterial()` 返 null → `:53536` 报 `Material "ShaderMaterial" is not compatible.` 并回落空材质
  （画面什么都没有）。移植任何 WebGL 特效项目必须先确认这一点，**用 TSL 重写**。
  配套三条：① **`toneMapped` 在 WebGPU 后端不存在**（全文出现次数实测 **0**）—— 色调映射在
  `_renderOutput` 的全屏 output pass 上做，上游的高 glow 值会被 ACES 削成白 ⇒ 增益必须按像素重标；
  ② **参数化几何用 `vertexNode` 而不是 `positionNode`**（后者的返回值会被 `modelViewMatrix` 再乘一次，
  依赖「mesh 矩阵恒等」这个隐式前提）；③ **逐 pass 的 varying 用 `varyingProperty` 在顶点写、片元读**，
  不得在 `colorNode` 里直读 `positionGeometry` —— instanced 属性（`aStrand`/`aRing`）在片元阶段读不到，静默拿 0。
- ⚠️⚠️⚠️ **`Fn` 返回多键对象会被包成 SplitNode，自定义键全部 undefined**（Storm Lance v3.20 实测）：
  `const f = Fn(() => ({dir, n1, n2, span}))` 的返回值走 **swizzle** 路径，只认 `x/y/z/w`。
  实测：返 `{a,b}` 碰巧能用（映到通道），而返 `{dir,n1,n2,span}` 时 **四个键全 undefined**
  ⇒ `n1.mul(...)` 抛 `Cannot read properties of undefined (reading 'mul')` ⇒ **整片 pass 不上屏**
  （实测 lit=0 / blue=0），而材质构造、uniform 清单、Node 单测**全绿**。
  **正解：「把几行节点表达式装起来」用普通 JS 函数，不要用 `Fn`**（它本来就不需要是 shader 函数）。
- ⚠️⚠️ **`Loop(5, ({i}) => …)` 拿不到 `i`**（Storm Lance v3.20 实测）：裸数字 `5` 被 `nodeArray`
  包成 ConstNode（`isNode===true`），而 `LoopNode.getProperties` **只对 `isNode!==true` 的 param
  建 `inputs` 键** ⇒ `inputs={}` ⇒ 解构的 `i` 是 **undefined** ⇒ `float(i)` 抛错、整片 pass 不上屏。
  **正解：`Loop({start:0, end:5, type:'int'}, ({i}) => …)`**。
  ⇒ 上面两条的共同教训：**TSL 节点构造类缺陷只能靠真实 GPU 像素探针抓**。
  写一个最小探针（建 renderer → 摆两个 mesh → render → 回读像素 + 收集 console error），
  比在完整游戏页里猜快得多；它会直接把出错的**文件:行号**报出来。
- ⚠️⚠️ **`viewportDepthTexture()` / `viewportTexture()` 会重开 render pass**（v3.20 读源确认）：
  它们是 `ViewportTextureNode`，`updateBefore` 里 `currentPass.end()` + `copyTextureToTexture` +
  `beginRenderPass`（`three.webgpu.js:86491`）—— 正是 v3.17 水面倒影撕天空那一类时机缺陷。
  想做「深度软相交」的特效请改用 `depthTest: true` 硬遮挡（曳光既有口径），不要引这两个节点。
- ⚠️⚠️ **多时基写同一个 instanced 属性 = 静默全灭**（v3.20 自己踩的）：
  火花 `aSpawn` 在蓄力期写绝对秒、施放期写相对秒，而 `uTime` 在施放时切成相对秒
  ⇒ `age = uTime − aSpawn` 变负（实测 **−5**）⇒ **蓄力吸入粒子在释放瞬间全部消失**，
  而相位/可见性/draw call 判据全绿。正解：**全局单一时钟**（uTime 恒绝对秒），
  需要「施放内时间」的噪声另开一个 uniform（`uAge`）。判据要落在**真实属性值**上。
- ⚠️ **量额外特效的 draw call 必须关水面倒影**（v3.20 实测）：不关时 idle 275 → firing **518**
  （+243），关掉后 276 → **292**（**+16**）—— 前者把倒影 pass 算进了同一个计数。
  写 draw call 判据的 spec 一律带 `?shadows=0&reflect=0`。
- ⚠️⚠️ **`vec3(new THREE.Color(hex))` 在 WebGPU 后端输出纯黑且零报错零警告**（炮塔三档色调 v3.14 实测）：
  装甲 6 部件**整片消失**，而 tone 属性/长度/值域/冻结表/材质无 map/有 colorNode/集合关系式/指纹
  **全部通过**。根因：`vec3` 单参数走「转成 vec3」路径，而 `getValueType(Color)` 返回 `'color'`
  不是 `'vec3'`（`three.webgpu.js:1146`）⇒ 转换拿不到分量。**正解：显式拆分量 `vec3(c.r, c.g, c.b)`**
  （`color(hex)` / `uniform(Color)` / `vec3(...C)` 也都可用）。逐写法实测非黑像素数：
  `vec3(Color)` **0** / 其余四种均 **10455**。⇒ **凡新增 TSL 常量色必须配像素实测**，
  节点构造类判据对这类缺陷零判别力。
- ⚠️⚠️ **多档着色的像素亮度判据对「分类退化」与「色值全等」都零判别力**（v3.14 负向验证实测）：

  滑动但 p90 几乎不变（187→186.7），而 median 差 36.7；曲面（炮管）p90 差 7。
  取 **median 与 p90 的最大差**，两类几何才有判别力。

- ⚠️⚠️ **「保持粒子总量不变」会毁掉单根的节奏**（剑体阵列 v3.27）：根数 5→30 时把速率÷6，
  每根只剩 9 颗、逐帧每批恒 1 颗 ⇒ 「破土猛迸」读不出，且既有「首批 > 末批」断言真红。
  五档扇描后 **÷2** 才两头都保住（每根 27 颗，首批 2 / 末批 1）。改这类参数要**扇描 + 跑全部既有关系式**，
  不能只算总量。
- ⚠️⚠️ **实例矩阵加了朝向后，`|m.elements[0]| > 0` 不再是「可见」判据**（v3.27）：
  `e[0] = cos(yaw) × scale`，yaw≈±90° 的实例 cos≈6e-17 ⇒ 那些实例**永远被判不可见**
  （实测 30 根里 12 根恒假）。改用 `|m.determinant()|`（旋转不变，等比缩放下 det = scale³）。
- ⚠️⚠️ **「朝向对不对」的像素判据可能零判别力，要量几何投影面积**（v3.27 RF-4）：
  剑宽面/窄边的几何面积比恒 **6.5**，而暖色像素比只有 **0.74**（方向反了）—— 暖色阈值
  `dr>25` 只圈到金边，暗紫底两侧都过不了。另：**阵列类特效转 90° 后各方向互相抵消**
  （正前方变窄边、左右两排反而变宽面）⇒ 必须**按方向分区**。正解：读 `getMatrixAt` 真实矩阵
  × 顶点 → `project(camera)` → 屏幕三角面积和，且**升满后才读**（spawn 那一帧 scale≈0）。
- ⚠️⚠️ **抬高像素机位会把残余漂移放大到盖过信号**（v3.27 四轮实测）：为了让 30 根全进 clip
  而抬高 12 格后，**零特效对照组自身就有 20758 暖色像素**（比信号还大）。逐个隔离后
  sections 恒 275、全部 `update` 空转、相机逐位静止、`weather=clear` 仍有 ~2900 稳定差分
  ⇒ **`?shadows=0` 只关阴影 pass，不关太阳方向推进**。抬高机位前先量对照组的绝对读数。
- ⚠️⚠️⚠️ **换了带贴图的几何后，`instanceColor` 必须改成中性灰**（剑体 v3.27 自审实测）：
  three 的 `setupDiffuseColor` 把 `instanceColor` **乘到 colorNode（含 map）**
  （`three.webgpu.js:21619`）⇒ 沿用旧的火焰橙 `(1.0,0.45,0.12)` 会把剑贴图**染成橙色**，
  违背「贴图跟手里那把一模一样」。**形态极隐蔽**：材质基色是白的、map 也挂上了、
  几何/顶点数/朝向全对，只有逐实例色在染色。修法：有 map 的路径写 `(k,k,k)`，
  无 map 的回落路径保留原色。判据要钉**真实 `getColorAt`**（不是材质基色），
  且同时钉「缩回段仍在淡出」—— 否则把淡出一并关掉也能绿。
- ⚠️⚠️ **判「贴图有没被染色」的像素阈值必须两侧实测取中，线性估算会错**（v3.27）：
  剑身原色 b/g ≈ 0.556，乘 (1,0.45,0.12) 的**线性**估算得 0.148，而真实 GPU 实测是 **0.391**
  （ACES 色调映射在 output pass 上压缩了通道差）⇒ 阈值写 0.30 会让染橙态**仍然通过**。
  正确态 0.534 / 染橙态 0.391 ⇒ 取中 **0.463**。
- ⚠️⚠️ **「阵列每个方向都上屏」的像素判据要容忍地形遮挡**（v3.27 三轮实测）：
  低机位下边缘方向可能①在视野外、②代表点在 clip 内但剑体在外、③**被土坡遮挡**
  （实测右侧首根视线 5/19 采样点穿地形 ⇒ 暖色像素 0）。**遮挡是合法游戏行为**。
  判据改成「至少三个方向各自有显著像素 + 有像素的方向量级与可见根数相称」，
  五向完整性交给**数据层**（落点/方向分布/朝向点积，那些判据不受视野与遮挡影响）。
- ⚠️⚠️⚠️ **「从地里长出来」不等于「三轴等比缩放」**（剑阵 v3.27b 用户实玩裁定）：
  用户原话「剑体保持大小不变（即不要缩放），直接从地下伸出来……不要膨胀着冒出来
  好像从小涨到大似的」。等比 `scale` 会让物体**整体膨胀**（小剑长成大剑），
  而「伸出地面」要的是**尺寸恒定 + 竖直位移**：
  `y = groundY − (buriedDepth + exposeHeight) × (1 − progress)`。
  地下部分靠 `depthTest:true` + 地形先写深度自然遮住（实测：45ms 只露剑尖、
  180ms 完整剑身且**宽度与剑尖那截一样粗**、800ms 已沉回）。
  判据要钉**真实 `instanceMatrix` 的基向量长恒 1**（膨胀态下它等于 progress），
  且不能用 `sy>0` 过滤「未破土」—— 膨胀态下已破土的 sy 也 <1，会被当未破土跳过。
- ⚠️⚠️ **逐帧截图量时序在本机不可靠，改用页面内 rAF 连续采样**（v3.27b 四轮实测）：
  请求 t=60/120/180ms 而真实 age 漂到 87/321/386（截图耗时不稳定，与 CDP 往返次数无关）
  ⇒ 「及时样本」永远凑不齐。**时序信息就在实例矩阵里**（每根的高度 = 它自己的进度），
  在页面内一次 rAF 采完、零截图零往返 ⇒ 实测每圈破土时刻 7.4/58.1/107.8/158.1/207.3/257.2ms
  （逐圈 +50ms，每圈 5 根同帧）。⚠️ `reset()` **不归零 `_nextSlot`** ⇒ 探针里按 `i*16`
  直读会取到空 slot，要按**水平位置匹配**把实例认回对应的根。
- 序列帧切帧走 `texture.offset`（WebGPU 后端确认消费）；每个 slot 需独立材质 + 独立纹理 clone，
  `repeat` 要在 `clone()` **之前**设。
- 常驻实例池在零实例时必须 `visible = false`，否则每个 mesh 恒增 1 个 draw call。
- BatchedMesh 的 draw call **不是每通道一次**：每个可见 geometry slot 各发一次（加新几何前别假设 +0）。
- WebGPU canvas 的像素回读必须在 `renderer.render()` **之后**；Tier 4 逐帧读像素要在 rAF 回调内。
- ⚠️⚠️⚠️ **WebGPU 的 `maxVertexBuffers` 是 8，一个 `InstancedBufferGeometry` 最多 7 个逐实例属性**
  （环境特效 v3.26 实测）：position + 8 个属性 = 9 ⇒ `Vertex buffer count (9) exceeds the maximum
  number of vertex buffers (8)` ⇒ **render pipeline 创建失败、整池零像素**，而
  visible / count / 属性值 / biome 门控 **全对**。正解：**把标量打包成 vec2/vec3/vec4**
  （本轮：落叶 born+alpha → `aLife` vec2；萤火虫 size+alive+breatheFreq+breathePhase → **vec4**、
  born+life → vec2、driftX/Z+ground → vec3）。判据：`Object.keys(geometry.attributes).length <= 8`。
  ⚠️ 这类缺陷**只会在浏览器 console 里报 GPUValidationError**，Node 单测与所有数值判据零判别力。

## 体素查询与地面扫描

（v3.26 实测，全部静默失效型）

- ⚠️⚠️ **`world.isSolid` / `getBlockId` 必须传整数 x/z**：`blockIndex(x - cx*16, …)` 对小数坐标
  算出**小数数组下标** ⇒ undefined ⇒ 全读成 air。而**玩家坐标恒带 .5** ⇒ 直接拿 `player.physics.pos`
  去扫地面会整片扫不到（本轮：220 片叶全跳过、零报错）。
- ⚠️⚠️ **向下扫描的下界必须钳在 `WORLD_MIN_Y` 之上**：`getBlockId` 对 `y < WORLD_MIN_Y` 返回
  **bedrock**（防穿底）⇒ 未加载 column 全 air 时会一直命中世界底 ⇒ 地面解成 −32，
  粒子全出生在地下（实测 origin.y≈−20 / minY=−31.98，而 visible=true、count 全对）。
- **扫描深度要按「玩家高度 − 地面」定，不是按粒子自己的高度带**：既有 spec 的标准落点是
  `_teleportTo(x, 45, z)`，而森林真地面在 y≈8 ⇒ 相距 **37 格**。取 24 会整池播不出来；
  `rain.js` 用的是 **56**，同类粒子场照它。
- **地面要从玩家脚下往下扫，不能从粒子出生带顶部扫**：传送落点常在**树冠下**，
  从头顶扫会把叶层顶当成地面（实测 y=55 的树冠 ⇒ 地面解成 56）。
- **播种不能用一次性布尔标志**：首次进目标 biome 时 column 可能尚未加载 ⇒ 全部跳过，
  而标志已置位 ⇒ **属性永远全 0**。要逐片记成败数 + 每帧重试差额。

## 环境特效与持续动画 Tier 4

（v3.26，四条判据选型均被实测推翻）

- ⚠️⚠️ **被测对象自己就是动画时，「相邻帧差分」与「开的下限 > 关的上限」都必 flaky**：
  落叶是自由翻转薄片（侧面投影只 1~2px），**同实现同机位两轮读数 [0,0,0] vs [324,502,316]**；
  萤火虫呼吸三次幂让多数帧很暗（单张 0~108）。正解：**「关态固定基线 → 开态 N 帧并集」**
  （单调不减、随时序稳定，仍是单变量对照）。
- ⚠️⚠️ **draw call 不得跨机位比**：不同机位可见 geometry slot 数差异巨大
  （实测沙漠 353 / 森林 308 / 草地 300）⇒「森林−沙漠」得 **−45**。只能**同机位开/关差**；
  单池实测 **+2**（池自身 1 + three 把新 transparent mesh 插入排序列表带来的额外一次提交）。
- ⚠️ **「粒子在画面下半部」不能凭直觉定采样区**：落叶出生在地面+3..13 而相机眼高仅 +1.62
  ⇒ 多数叶子在相机**之上**。实测秋色命中 712 中 top 665 / mid 47 / **lower 0** ⇒ 取下半屏零判别力。
- ⚠️ **「注入后计数为 0」不是权重类负向判据**：真实叶种比例里仍有 25% 黄叶 ⇒ 计数仍非零。
  要钉**占比**（暖色命中 / 全部变化像素）：秋色档 0.111 vs 真实比例档 0.030。
  注入生效确认要读**真实 GPU 属性色分布**，不只读常量（实测 yellow 154→52 / green 20→136）。
- **机位要避开巨树树冠**：(−400,−400) 的整数落点恰在树冠内（y=39 是 `giant_spruce_leaves`，
  真地面 y=9）⇒ 玩家停在叶层顶 y=40、相机高于全部落叶。传送到**远高于树冠的 y 后等 `onGround`**；
  反复搜索式传送会让玩家在未加载 column 间坠落（实测到 y=−23）。
- **切开关后等 2.5s、冻完环境再等 4s**：池要重新播种/迁移，且远处 column 仍在流式上传
  （700ms / 2s 时读数几乎为 0，会被误读成「特效没画出来」）。

## 短命特效的断言时机（v3.30，KV-9 / 雨天档）

- ⚠️⚠️ **开火后任何 `await` 都会让短命特效自然过期**：曳光只活 `(L+len)/320 ≈ 0.02s`、
  枪口火光 0.045s、hitstop 0.022s。在 `page.evaluate` 里开火后接一个 `await import(...)`
  或 `setTimeout` 再读 `visible`，量到的是「过期后不可见」而不是「开火时可见」。
  **正解**：模块 import 放在开火**之前**，开火后**同步立刻**取样全部瞬态字段。
- ⚠️⚠️ **`mount()` 只置标志不写姿态 ⇒ 枪横在屏幕正中心**：Group 默认位置 (0,0,0)，
  而腰射基准位是 (0.165,−0.175,−0.31)。帧循环下一帧会纠回，但「切枪后立即量位置」
  的判据读到 0，玩家也看得到那一帧。**mount 必须当场 `update(0, …)` 写一次姿态**。
- ⚠️⚠️ **`onShot` 只置 `flashT` 等下一帧写 `visible` ⇒ 低帧率下火光一帧也不上屏**：
  两帧间隔 > 45ms 时 flashT 已减成负。kick/曳光/弹壳全对，只有火光消失（静默）。
  **开火当场就要点亮并写满功率**，下一帧再按剩余寿命衰减。
- ⚠️⚠️ **`clear()` 只清 `life` 不清计数与 GPU 属性 ⇒ 弹壳冻在最后一帧永久可见**：
  下一帧 `_updateCasings` 因 `active===0` 早退，不再写零矩阵。必须同时归零
  计数、instanceMatrix、各池的逐实例宽度/出生时刻。
- ⚠️⚠️ **切枪清理只写在「进入」分支 ⇒ 切走时旧特效留在画面上**：已 unmount 的枪
  不再抛壳，但旧弹壳还在地上躺到 3.5s 寿命结束，而玩家已拿着加特林。
  **两个分支都要清**（上游 `reset()` 的语义）。
- ⚠️ **hitstop 计时不钳 0 ⇒ 最后一帧减成负数**：`=== 0` 的「已结束」判据永不成立
  （实测 −0.0083）。用 `Math.max(0, t - realDt)`。
- ⚠️ **hitstop 用缩放后的 dt 计时会自我拉长**：0.022s 的 hitstop 实际持续 0.37s
  （读作卡帧而不是打击感）。计时必须用 realDt，只把**玩法 dt** 缩放。

## 雨的遮挡与高度（v3.30，用户三条硬约束）

- ⚠️⚠️ **`world.isSolid` 不能当「挡雨」判据**：v1.96 起 `cloud.solid=true`（云不可穿越），
  树叶族也全是 `solid:true` ⇒ 沿用它会让**雨停在树冠上与云顶上**（用户明确否掉）。
  正解：实心 ∧ **非镂空遮挡体** ∧ **非 cloud**（`rain-shelter.js`）。
  ⚠️ v3.34 修正：中间那一项**不是 `cullTable !== 1`** —— 详见下一节。

## 雨的逐点遮挡（v3.34，用户「棚下不下雨、棚外照常下」）

- ⚠️⚠️ **「玩家状态 ⇒ 全局开关」是遮挡类特效的通用错误形态**。
  旧实现两处总闸：`storm-rain.update()` 里 `玩家室内 ⇒ 两个 mesh visible=false 并 return`；
  `game._updateStorm()` 里 `uWet = indoor ? 0 : MAX`。后果：**玩家一进屋，窗外的雨与
  屋外的水汪一起消失**。遮挡是**空间属性**，不是玩家的属性 ⇒ 正解是空间数据 + 逐点门。
  ⚠️ 删总闸时最容易改成**另一个总闸**（例如按相机朝向整片关）⇒ Tier 4 必须有一条
  「玩家在屋内时屋外雨丝可见数 > 0」的正面判据（实测 2785 滴）。
- ⚠️⚠️ **`cullTable !== 1` 会把台阶/栏杆/柱子/箱子当成不挡雨**（实测漏判 **21 个**实心建材，
  含全部台阶族）⇒ **木台阶棚子完全不挡雨**。它们在 cutout 通道是因为几何非整格需要镂空渲染，
  与「是不是建材」无关。正解读 **`hollowOccluderTable`**（registry 派生 = cutout ∧ opaque），
  实测恰好命中 13 个树叶族。⚠️ 既有单测的「屋顶类」清单里**一个台阶都没有**，所以从未被抓到。
- ⚠️⚠️ **逐滴扫描起点取「滴自己的 y」永远看不到头顶的屋顶**：
  `rainStopY(world, reg, x, z, wy, 24)` 从雨滴当前 y 往下扫 ⇒ 屋内 y=5 的滴先撞到 y=0 的地板，
  **看不到 y=9 的屋顶**。这个缺陷被总闸**完全掩盖**（室内根本不画雨）⇒ 只删总闸会立刻变成
  「屋内下雨」。正解：列级量从**云层上界**往下扫。
- ☠️☠️ **任何 CPU 预采的「逐滴列级量」都跟不上雨滴的水平飘移**（本轮连测三次才定位）：
  雨有 **1.6 格/s 的水平风**，而 `aMinY`/`aShelter` 是 **10Hz 分批**在滴的**当时 xz** 上采的
  ⇒ 某滴在屋顶**外**被采样（拿到屋外地面的截停面），下一帧已飘到屋顶**下** ⇒ 属性仍是旧列的值
  ⇒ 屋内照旧下雨。**三轮实测读数**：只删总闸 C2=7 → 加 `refreshShelterNow()` C2=5 →
  改用逐顶点 `aboveFloor` C2=**26**（反升，因为 aMinY 本身也是旧列的）。
  ⇒ **提高刷新率只是缩短窗口，不是修法**。正解：在**顶点阶段按 `p.xz` 采同一张高度图**
  （与湿表面片元门同构、同一份常量与判据）。修后 C2=**0**。
  ⚠️ 这与 v3.30g 的水下门是**同一类缺陷**：列级量变化慢（可 10Hz），滴的位置每帧在变。
  当时的修法只把 **y** 交给 GPU，**xz 仍留在 CPU** ⇒ 缺陷只修了一半。
- ⚠️⚠️ **格顶判据：`stopY > floor(probe.y) + 1 + EPS`，不是 `probe.y <= stopY`**。
  `stopY` 是**格顶**（y+1），而探针落在**几何顶面**外半格。对整格方块恰好差 0.5，
  但对**非整格顶面**方块会共面：实测真实 `TEMPLATES` 里挡雨方块有 **8 个**顶面 ≠ 1.0 ——
  三款 slab + `bed_head/tail`（0.5）、`horizontal_pillar`（0.65）、`cactus`（1.05）、`chimney`（1.5）。
  `probe<=stop` 会让**露天半砖永远不湿**；改严格 `<` 也修不了**半砖棚顶自身**（恰好共面）。
  只有格顶口径把「自身格表面」结构性排除 ⇒ 11 个关键场景 + **1032 例穷举**全过。
- ⚠️⚠️ **TSL `step(edge, x)` 的参数顺序写反会得到完全 inverted 的门**（露天全干、棚下全湿）。
  本轮 CPU 同构校验实测：套 `oneMinus(step(cellTop, stopY))` 的写法 **7/8 关键场景判反**。
  ⇒ CPU 纯函数与 TSL 必须同方向，且要有**逐场景**的对照用例（不是只测一个点）。
- ⚠️⚠️ **环形窗口纹理必须用绝对索引 `floor(x) & 511`，不是 `(floor(x)-origin) & 511`**：
  相对索引下原点从 0 移到 16，texel 5 的含义从「绝对 x=5」变成「绝对 x=21」
  ⇒ **整窗 262144 个 texel 全部失效**，根本不是环形缓冲。绝对索引还让 GPU **不需要原点 uniform**。
  平移清零条带 = **`(originX_OLD & 511) .. +15`**（环形）——
  固定 `[0,15]` 只在 origin ≡ 0 (mod 512) 时对；`((O+16)&511)..+15` **偏了 16**（两种错写都要有用例抓）。
- ⚠️ **绝对索引的副作用：窗外坐标会 wrap 到窗内某个 texel**（装的是 512 格外的别列）
  ⇒ 高度可能不对而**不是「未知」**。必须加**水平距离门**（>256 格强制不遮挡，与雾距一致）。
- ⚠️ **有效性用清零而不是哈希**：哈希碰撞会静默读到别的列的高度，而「高度看起来也合理」
  ⇒ 数值判据全绿而遮挡位置错。清零精确无碰撞，且 GPU 读到 R=0 即「未知 ⇒ 不遮挡」。
  ⚠️ **清零必须伴入队**，否则那批 texel 永远停在未知。
- ⚠️ **编码基准取 `WORLD_MIN_Y - 1` 而不是 `WORLD_MIN_Y`**：这样世界底那格的顶面编码为 4 > 0，
  **0 才能当哨兵**。用 WORLD_MIN_Y 当基准会把 stopY=0 编成 0 ⇒ 与哨兵撞车（实测 470/4000 误判 null）。
- ⚠️ **扫描必须缓存 column 引用后直读 `col.blocks`**：实测 **0.0122 ms/column**，
  而逐格 `world.getBlockId` 是 **0.2886 ms/column**（慢 **23.6 倍**，每格要重算 cx/cz + 拼 columnKey + Map.get）。
  ⚠️ **单位口径**：「column」= 16×16×128 区块 = **256 个格列**。混用两者会让同一张成本表内部差 256×。
- ⚠️ **预热不能写成「首帧满预算 tick」**：满预算 8 column 覆盖不了玩家周围 3×3=9 column；
  而整窗 1024 column 全扫 **12.5 ms** ⇒ 爆帧。正解：开档当帧同步扫 3×3（0.11 ms），其余 8/帧渐进（~2.1 s）。
- ⚠️ **上传必须早于本帧所有 render pass**：遮罩纹理是模块级单例，反射替身材质也采样它
  ⇒ pass 中途 `needsUpdate` 会让主画面与 RT 干湿不一致。
- ☠️ **Tier 4 夹具的相机机位必须实测选定，且要加「非退化」前置断言**：
  本轮首版把相机放在屋顶**内**往下看，屋内地面投影退化成 `[0.02,0.98,0.98,0.98]`
  ⇒ 区内 **n=0** ⇒ C3/C4 **恒真**（`frac=0` 看起来像「门没接线」，其实是「没量到东西」）。
  实测 5 个候选机位，只有「南侧远处压低平视」能让屋内地面/露天地面/屋顶顶面三区同时非退化。
  ⇒ 断言 `width > 0.02 && height > 0.002`，否则机位漂移会静默恒真。
- ⚠️ **单遍扫描「遇屋顶即停」会让 `hasWater=0`（屋顶盖住的水面）** —— 这是**有意收窄**，
  不是 bug。已穷举证明不可达：新旧口径不同的 **5684 列全部 `stop > 该列水面`**，
  真·水下且可见的案例 **0**（机制：先撞到挡雨块 ⇒ 它在所有暴露水面之上 ⇒ `wy >= stop > 水面`）。
  ☠️ **判这条时我自己先踩了测量错误**：第一版穷举用**全局** `WATER_SURFACE_Y=-1.5` 当「水下」界，
  得出 **14585 个可达案例**，差点采信审阅意见。那些全是「深坑里高于坑底水面、低于海平面」的
  **合法空气滴**（正是 `aWaterCol` 存在的理由）。改用**该列自己的**水面后归零。
- ⚠️ **像素探针必须先去显示变换、再确认行方向**（本轮连踩三次，全是判据错不是机制错）：
  ① ACES+sRGB 把字节 4→15、136→201 ⇒ 直接比「屏幕字节 == 纹理编码」得出 **64/64 不符**的假结论；
  ② 用 6 点标定 LUT 反查也不行（ACES 压缩段相邻编码映到同一字节，63/64 不符）；
  ③ **WebGPU `screenCoordinate.y` 自顶向下**（与 PNG 行号同向），照 OpenGL 习惯翻行会读到对面那行。
  等差编码序列下它表现为「R 恒偏 +112」，而 0/255 交替的 G 通道因 SIZE 是偶数**奇偶性不变**
  ⇒ 极易误读成「只有 R 通道坏了」。**只读一行的探针发现不了行错位** ⇒ 要读全部 texel。
- ⚠️ **判据异常时先怀疑测量方法**：上一条「R 恒偏常量」的第一反应是查 colorSpace / 节点缓存 /
  通道 swizzle，全部白跑；把观测值**反查编码表**才一步定位到行错位（8 个采样点全落在 `ty=7`）。
- ⚠️ **`textureLoad` 自带 `setSampler(false)`**（vendor: `texture(...).setSampler(false)`）
  ⇒ 直接喂普通 `DataTexture` 即可，**不需** `storageTexture`、不需 `unwrap`。
  但 `flipY=false` / `generateMipmaps=false` / `min=mag=NearestFilter` 要显式写死；
  高度场**不能用 Linear** —— 相邻列高度差可达十几格，插出来的中间高度是物理上不存在的面。
- ⚠️ **负坐标索引必须先 `int` 再 `bitAnd`**：int 位与是二进制补码 ⇒ `-1 & 511 = 511`，与 JS 的 `&` 同构；
  先 `uint` 会把负 float 转成未定义值 ⇒ 读到垃圾 texel。

- ⚠️ **空岛不需要单独识别**：岛体是石头/泥土（会挡雨），但岛底 Y ∈ [40,70] 都在
  雨幕上界（34）之上 ⇒ 被高度门整体排除。给岛体加名字白名单是多余的。
- ⚠️ **高度上界必须派生自 `CLOUD_CLUSTER_Y`**（=35−1=34）：写死 34 会在云层高度
  改动时静默漂移（雨跑到云上面）。雨幕**盒心**也要钳（`rainBoxCenterY`），
  否则玩家飞到云上时盒子跟着上去。
- ⚠️ **「盒心不动」不是高度钳制的正确判据**：低空时盒心本该跟着玩家。
  正确判据是**盒顶 ≤ 上界**（玩家 y=80 时盒心钳在 25 = 34−18/2）。
- ⚠️ **室内判据是「头顶有盖」而不是「四周有墙」**：只有顶棚的凉亭同样不该下雨；
  四面墙但无顶的天井应该下雨。扫描上界同样钳在云层之下（云不算盖）。
- ⚠️ **雨天档的反射门不能沿用「水面可见性」**：既有 `reflectVisible` 要求相机在
  水面之上 ∧ 朝下看；玩家站陆地抬头时它是 false ⇒ 反射 pass 不跑 ⇒
  **湿地面采到空 RT（静默不反光）**。雨天档要放宽成「视野里有地面」。

## 离线音频烘焙的确定性（v3.30）

- ⚠️⚠️ **`OfflineAudioContext` 的节点图在长产物上逐次运行输出不同字节**：
  12s 雨声床与 6.4s 雷声不稳定，≤0.62s 短音效恰好稳定。去掉 DynamicsCompressor、

- ⚠️ **共用一条 RNG 流时，新增任一配方会让其余产物变字节**：雨声的噪声取决于
  它前面所有配方消耗了多少随机数。每产物独立流（种子 = 全局种子 XOR id 的 FNV）。
- ⚠️ **卷积混响必须做 IR 能量归一化**（ConvolverNode 的 normalize=true 默认语义）：
  lp 0.45 的一阶低通使相邻抽头强相关，不归一时雷声峰值冲到 **1.95**（削顶）。
- ⚠️ **模板字面量内的注释不得用反引号**（会提前终止字符串）：本仓 settings-panel
  已记过同一条，烘焙脚本的 SYNTH 字符串又踩一次（SyntaxError 指向注释里的标识符）。

## 循环脚步声素材的制作与判据（v3.37）

- ⚠️⚠️⚠️ **「首尾样本落差 ≤ 内部相邻落差 p99」对循环接缝零判别力**（本轮负向验证当场抓出）：
  注入「尾部 30ms 硬切成静音」后它**照样 PASS** —— 末样本变成 0，落差反而从 0.0248
  **降到** 0.0210。有判别力的是**能量**，两条：
  · **首尾连续近零样本串 ≤ 2ms**（硬切 30ms / mp3 padding 20ms 两种形态都真红）；
  · **接缝两侧 20ms 窗的能量比须落在内部各步边界量级**（正常 0.0771 ∈ [0.0539, 0.2685]，
    硬切与补静音都是 **0**）。
- ⚠️⚠️ **无缝性判据的两侧口径必须一致**：颗粒尾巴跨圈 + biquad 有状态 ⇒
  「产物平铺 N 圈 ≡ 长渲染」里的长渲染**必须前置一整圈预热**。第一版没预热，
  得出误差 0.18，那是**判据本身错**不是产物缺陷（预热后实测误差恰好 **0**）。
- ⚠️⚠️ **选「像不像某种声音」的素材片段要按频谱，不能按峰值**：踩湿泥录音里峰值最大的
  几步能量全在 **<200Hz 的泥闷低频（40~57%）**，听起来是踩厚泥不是踩水。
  按泼溅带（0.5~5kHz）占比排序才对。EQ 去低频要**两遍 180Hz 高通** ——
  单遍 110Hz 后 80~200Hz 仍占 8~19%（实测），两遍 180Hz 才压到 0.36%。
- ⚠️ **步频要用「左右整步态」的自相关 lag ÷2，不是单步 lag**：单步峰会被左右脚强弱差
  带偏，实测 `running_land` 单步细化 0.28369 而整步态 ÷2 = **0.27991**（差 3.8ms）。
- ⚠️ **循环步数必须偶数**：奇数会让左右脚在圈与圈之间对调，重音永远落同一只脚。
- ⚠️ **颗粒窗长必须 > 步长**（0.340 > 0.2799）：否则每步之间是纯静音，
  听感是断续的「哒哒哒」而不是连续跑动。
- ⚠️ **循环音效产物不能用 mp3**：编码器首尾补静音（encoder delay/padding）⇒ 接缝多空档。
  实测某个长度的 libmp3lame 往返样本数恰好不变，但那是**那一个长度的巧合**不是格式保证。
- ⚠️⚠️ **wav 解析必须逐 chunk 找 `fmt ` / `data`，不能写死 44 字节偏移**：ffmpeg 会插
  `LIST/INFO` chunk（本仓三个音频素材全都有）⇒ 写死偏移会把 chunk 头当样本读，
  分析出的「步频」全是噪声（第一版直接 `Invalid typed array length: -1`）。
- ⚠️ **换素材 / 改文件名都不等于新增音效**：文件名走 `soundFileName(id)` 派生 ⇒
  改 id 即可（`running_water` → `running_wet`），**不另立「id→文件名」映射表**。
  但扩展名必须进 `SOUND_EXT_OVERRIDES`：**漏那一行 = 水中走路彻底没声**
  （按 .mp3 fetch 拿 404，被 `preload()` 的 catch 吞成一句 warn）。
  **改 id 必须同步全部消费方**（本轮两处：`player._updateFootsteps` / `audio-fx.spec`）——
  漏一处的形态是「计数与状态机全对、就是不出声」，负向验证实测该 E2E 真红。
- ⚠️⚠️ **用户点名「就用那个试听文件」时不能直接转码它**：试听件通常已按**游戏播放音量**
  导出（本轮预览 rms = 母版 ×0.2426），而运行时 `playLoop(id, 0.25)` 会**再乘一次**
  ⇒ 有效 0.0625、比参照音低 **12 dB**。正确做法是交付**无损母版内容**改名，
  并核对与试听件是同一份音频（相关系数 0.99994 + sha256 逐位）。
- ⚠️⚠️⚠️ **源素材不入库时，烘焙门禁的口径必须反转**（用户裁定「只提交产物」）：
  其余烘焙产物**可重烘** ⇒ 钉产物哈希期望值会把产物变成改动放大器，故只钉
  「清单 hash == 磁盘 hash」+「输入指纹 == 当前配方指纹」。但**素材删掉后产物不可重烘**，
  那两条都失去判别力（清单与产物可以一起被换掉）⇒ **必须钉死产物自身的 sha256**。
  实测 N8：把产物**整段循环移位半步**，长度 / 峰值 / RMS / 步频 / 无缝性**全部逐位不变**，
  只有产物 sha256 与两条样本级判据（重→轻交替 / 逐步冲击）抓到。
- ⚠️ **素材缺失时烘焙脚本要硬失败并打印取回办法**，不得静默跳过或产出别的声音；
  门禁则相反 —— **素材不在磁盘是正常状态、不报错**（只在它恰好存在时核对是否同一份）。
  把「素材必须在库」留在门禁里 = 用户删完素材后 `npm run check` 恒红。
- ⚠️ **「重跑烘焙 ≡ 磁盘产物」这条判据在素材不入库后恒走跳过分支** ⇒ 必须另补
  **直接量产物**的无缝判据（平铺 N 圈步频恒定无漂移 / 每步都有起音且冲击不悬殊），
  否则那条用例变成永远 pass 的空壳（policy §2.7「静默不跑」）。

## 按地表切换 footsteps 的四条实测坑（v3.38）

- ⚠️⚠️ **「按格缓存」必须由编辑事件也能失效，跨格失效不够**：玩家可以**原地不动**
  给自己头顶盖屋顶（或把脚下挖空）—— 那时缓存键（`floor(pos)`）一个都没变，
  只按跨格失效的形态是「盖了屋顶仍然一直踩出踩水声」，而 `playing` / `volume` 类
  判据全绿。正解：`editor.subscribe` 里 `this._wetGroundCache = null`，
  并配一条**玩家不动、只改世界**的专测（本轮负向③注入后只有那条抓到）。
- ⚠️⚠️ **脚底共面口径**：玩家站稳时 `physics.pos.y` **恰等于支撑块顶面**
  （y=21.0 对 block y=20）。写 `Math.floor(y - 1e-4) - 1` 会取到 21−1 = 20…
  **只有当 y 带小数时才碰巧对**；本轮第一版写成 `floor(y - 1e-4)` 再 −1 的顺序错位，
  在 y=21.0 时得 19（空气）⇒ 全部露天草地判成干地，**9 例里 4 例当场红**。
  正解 `Math.floor(y) - 1`（21.0 与 21.42 两种口径都对）。
- ⚠️ **E2E 造地形必须留出「跑动距离 × 窗口数」的余量**：玩家 8 格/秒，40 帧≈15 格。
  第一版铺 5×5 石台、只在起点盖屋顶 ⇒ 玩家跑出覆盖区，后面窗口实际在自然地形上跑
  （实测第 5 个窗口 `walking` 只剩 **2 帧**，被前置判据抓到）。正解：**72 格长走廊**
  + 每个窗口前把位置/朝向/速度重置 + 整条走廊盖屋顶。
- ⚠️ **开关生效值必须在「关档那一刻」采样**：一个 evaluate 里跑完「关档→再开档」后，
  末尾读 `g.stormLighting` 恒为 true（本轮第一版就是这样，被判成「关档失败」）。

## 冻结阈值绑死了「用户可调的位置参数」（v3.30f）

- ⚠️⚠️ **判据里写上游的绝对几何值 ⇒ 用户调参后必然假红**：`carbine-tracer-origin` 两条断言
  `gap > 0.5 格` 与 `dTip < 2px` 都是按上游枪口锚点 `z=-0.7` 标定的。用户把锚点调成
  `z=-0.5`（功能代码已调好、明确不改）后，真实间距变成 **0.481673 格**
  （= √(0.04²+0.003²+0.48²)）、轴向差 0.19 格投影 **30.204px** ⇒ 两条**几何上必然红**。
  ⇒ 这不是缺陷，是**判据把「用户可调的位置」也钉死了**。
- ⇒ **重标原则：把「位置」判据换成「关系」判据**，保留原缺陷的判别力：
  · 「距枪管末端 ≤2px」→ **「锚点在枪管轴线上」（横向偏差 <0.01 格）**：
    沿轴前后移动不假红，而「偏到枪管旁边」（原缺陷的横向分量）仍必红；
  · 「两锚点间距 >0.5 格」→ **「两次取值各自等于独立基准」+「间距等于几何真值」**：
    直接钉「没被覆写」这个语义，不随锚点位置变；
  · 「起点远离抛壳口」→ **相对阈值**（占两锚点屏幕间距的一半），不写绝对像素。
- ⚠️⚠️ **重标后必须做负向验证，且要注入「真实缺陷」而不是「历史写法」**：
  本轮先注入 v3.30c 的原始写法（两个 scratch 共用），结果**只有 1 条红、前 3 条仍绿** ——
  因为 `player.js` 已在 v3.30c 加了「立即快照数组」，单靠 scratch 共用不再穿透到 GPU。
  改注入**真实串位**（`muzzleWorld` 里读 `this.port`）后 **4 条全 FAIL**
  （distToMuzzle 0.4817 / dMuzzle 280.9px / dPort 0.018px）⇒ 判别力确认完好。
  **教训**：多层防御下，注入上游那一层的缺陷可能已被下游挡住 ⇒ 负向验证要注入
  **能真正到达被测产物的**缺陷，否则会误判「判据失效」。

## 雨天的「CRT 扫描线在动」与四项水下排除（v3.30g，用户实玩报告）

### 第三个根因：three 的 TSL `hash` 是**标量** PCG，喂 vec2 会静默取 `.x`

- ⚠️⚠️ **同名不同签名 —— 把上游自定义 `hash(vec2)` 换成 vendor 的 `hash` 就错了**：
  three r185.1 的 `hash` 是 PCG **标量**哈希（`seed.toUint().mul(747796405)…`）。
  `toUint()` 对 vec2 走 `ConvertNode` → `builder.format()` 的
  `fromTypeLength > toTypeLength` 分支 ⇒ **`snippet.x`**，**y 分量整条丢掉、零报错**。
  ⇒ 颗粒只随屏幕 x 与时间变、沿 y 恒定 ⇒ **整列同亮同暗的竖纹**；
  `fract(uTime*7.31)*113` 每帧重掷种子 ⇒ 竖纹逐帧乱跳（用户：「像老式电视雪花，扫描线还在动」）。
  上游 `FXAA_FRAG` 自带真二维 `hash(vec2 p){ vec3 p3 = fract(vec3(p.xyx)*0.1031); … }`
  ⇒ **上游没这个问题**。正解：显式合成标量种子 `gp.x.add(gp.y.mul(65536))`
  （65536 远大于任何屏幕高度 ⇒ 不同行不撞种子）。
- **实测（真实 GPU 像素，grainOn − grainOff 差分消掉场景内容）**：
  | 判据 | 缺陷态 | 修后 |
  |---|---|---|
  | 列内沿 y std / 行内沿 x std（天空） | **0.072** | **0.983** |
  | 同上（中带 / 地面） | 0.130 / 0.216 | 0.964 / 1.000 |
  | 列均值的时间 std | **1.54~1.98** | **0.18~0.19** |
  | 整幅列均值时间 std（grain 开/关单变量） | **5.192** vs 关 **0.048** | — |
  | 同一列内像素完全相同的比例（天空带） | **85.7%** | 15.0% |
- ⚠️⚠️ **判据选型：竖纹要量「列内 std ÷ 行内 std」，前两条判据对它都零判别力**：
  v3.30d 的「相邻像素差为 0 的比例」是抓**硬格子**的；v3.30e 的「符号翻转次数」是抓
  **走样**的。竖纹的定义是「沿 y 恒定、沿 x 变化」⇒ 只有两方向 std 的**比值**能刻画它。
  用整幅符号翻转会把场景纹理算进来（缺陷态与修后都 ≈26%，完全分不开）。
- ⚠️ **颗粒必须在显示空间加**（上游在 FXAA 之后、暗部权重读 `m.a` = 显示 luma）：
  加在 ACES **之前**的线性空间时，暗部 col≪1 的同样绝对增量会被 ACES 放大 ⇒ 暗处格外脏。
  ⇒ 本仓把它从 `gradeNode` 移到 `gradeTailNode`（renderOutput 之后）。
- ⚠️ **独立场景探针验不了它**：自建 `Scene` + 正交相机 + 全屏 quad 读像素实测**全 255**
  （无 renderer 的 toneMapping/色彩空间上下文）⇒ 四个变体读数完全一样。
  正解：在**真实后处理链**上做单变量 A/B（`page.route` 换模块内容）。

### 四项水下排除：水面是「截停面」但不是「屋顶」

- ⚠️⚠️ **不能把水写进 `blocksRain`**：它同时被**室内判据** `isUnderRoof` 消费
  ⇒ 水算屋顶会让「站在浅水里」被判成室内 ⇒ **整片雨停掉**（用户只要水下个体不画）。
  ⇒ 新增 `rainStopY = max(rainShelterY, waterSurfaceYAt)` 单独收口，
  `blocksRain` 的「水不挡雨」语义一字不动。
- ⚠️⚠️ **两个扫描的起点必须同口径**（本轮实测的真缺陷）：`rainShelterY` 内部
  `start = min(floor(fromY), RAIN_CEILING_Y)`，而首版把**未钳的 fromY** 传给水面扫描
  ⇒ 玩家 y=40 时水面扫描从 41 往下 24 格只到 17，**永远到不了 −2 的水体**
  ⇒ water=null ⇒ 截停面静默退回湖底。两边都要 `min(fromY, RAIN_CEILING_Y)` 起、同深度。
- ⚠️⚠️ **判「雨滴在不在水下」必须逐滴按它自己的 (x,z) 列判**（本轮假红）：
  `aMinY` 是**逐列**截停面，雨幕盒 24×18×24 覆盖**水陆混合**区 ⇒ 陆地列的截停面
  天然低于 −1.5（实测 629 滴），而那些滴**不在水下**。
  写「所有 aMinY ≥ −1.5」是假红（实测 2572 滴「越线」里只有 918 真在水下）；
  写「盒心那一列」是假绿。正解：按 GPU 同式算该滴世界位置，再查**那一列**的水面。
- ⚠️⚠️ **雨丝的水下门必须在 GPU 逐顶点判，不能交给 10Hz 采样的 `aShelter`**
  （本轮实测 994 滴漏网）：雨丝在 **18 格高的循环盒**里跑，盒底实测 −11 远低于湖底；
  `aShelter` 是 10Hz 分批写的 ⇒ 某滴采样时在盒顶（水上、sh=0），下一帧已绕到盒底
  ⇒ sh 仍 0 ⇒ **水下雨丝照样上屏**。⇒ 新增逐实例 `aWaterCol`（该列有无暴露水面，
  变化慢、可 10Hz）+ uniform `uWaterY`，GPU 算 `mix(1, step(uWaterY, p.y), aWaterCol)`。
  **分工是要点**：列的水陆属性交 CPU（慢），滴的 y 交 GPU（每帧）。
- ⚠️⚠️ **不能无条件把「y < 水面」当成水下**：本仓地形有低于海平面的**干坑/峡谷**
  （实测 29 滴在无水列且 y < −1.5）—— 那里的雨是合法的，无条件门会把它们一起杀掉。
- ⚠️⚠️ **判据要量「可见性」而不是「位置」**（本轮两次假红）：
  ① `aMinY` 是逐列截停面，盒 24×18×24 覆盖水陆混合区 ⇒ 陆地列天然低于 −1.5
  （实测 2572 滴「越线」里只 918 真在水下）；② 循环盒底远低于湖底 ⇒ 总有滴的**位置**
  在水下，关键是它有没有**被画出来**。⇒ 量 GPU 真实 fade：
  `(1−aShelter) × aboveWater × step(aMinY, y)`，并配一条「可见总数 > 50」防恒真。
- ⚠️ **负向验证要注入「能真正到达产物」的缺陷**（本轮又踩一次多层防御）：
  只把 GPU 的 `aboveWater` 退为恒 1 **判据仍绿** —— 实测分解：2046 滴位置在水下，
  1003 被 `aShelter` 拦、剩 1043 被 `step(aMinY, y)` 拦（aMinY 已是 −1.5）⇒ visibleBelow=0。
  ⇒ 要**同时**退回两道门（`rainStopY` 的水面项 + GPU 的 aboveWater），那才是旧行为。
- ⚠️⚠️ **验落叶水下门的两个机位坑**：① 浅水高台的湖是 **SWAMP** biome，
  而落叶池的 biome 门（`=== 'FOREST'`）**先 early-return** ⇒ 水下门根本跑不到；
  ② 既有森林机位（−393.5,−399.5）实测在 **y=56**（山地），把水写在 `SEA_Y=−2`
  根本泡不到玩家。正解：在 FOREST 列上按**玩家当前 y** 造水面，并读回体素确认写入。
- ⚠️⚠️ **水面扫描不能拿全局 `WATER_SURFACE_Y`（−1.5）做下界**（本轮实测两次）：
  那个常量只对**天然地形**成立（三处写水以 SEA_Y 为上界），而**玩家造的水 /
  山顶水池可在任何高度**（实测森林机位 y=56）。`max(py, −0.5)` 会把扫描窗口
  拉到水下 ⇒ 门恒 false。而只从 `py+1` 起也不够（潜水 4 格时水面在更上方）
  ⇒ 从 `py + birthMax` 起、深度同步加大。
- ⚠️ **「头顶有水面」≠「我在水下」**：湖底下的**干洞穴**头顶确实有水，但中间隔岩层
  ⇒ 必须加一条「**玩家身体那一格真的是水**」（同 `physics.inWater` 口径，
  取脚底与脚底+1 两格）。否则玩家在干燥洞穴里也会被关掉落叶。
- ⚠️ **湿地面反光的水下门必须是逐片元，不能只靠 CPU 的 `uWet` 总强度**：
  站在岸上看湖底是「**相机在水上、片元在水下**」⇒ 总强度门零判别力。
  正解：`step(uWetWaterY, wp.y)` 乘进 **wet**（不是只乘 reflTerm —— 只关反射会留下
  「湖底被压暗 + 涟漪」）。实测湖底带 86.1% 像素回到原色。
- **水面共面性是常量门的前提，要用真实 `fillColumn` 钉住**：三处写水
  （`fillColumn` / `fillShallowTarnBasin` / `fillTarnPlateau`）都以 `SEA_Y` 为上界，
  mesher 统一下沉 `WATER_SURFACE_SINK` ⇒ 所有暴露水面恒 = −1.5。
  `test-water-surface.js` 扫 13×13 column 断言「暴露水面只有一个高度」——
  **不是拿常量互推**（那样恒真）。将来出现非共面水面时该断言先红。
- ⚠️ **`WATER_SURFACE_SINK` 已从 mesher 提级到 `voxel/constants.js`**：
  水面高度有两个消费方（mesher 几何 / `water-surface.js` 判据），各写一份 0.5
  会漂移出「雨停在半格空气里」。提级后 mesher 175 例逐位不变。
- ⚠️ **落叶的水下门是「出生带无处可放」而不是逐叶可见性**：落叶出生带 =
  「**玩家所在那层地面** + [3,13]」⇒ 玩家潜水时那层地面是湖底 ⇒ 整段在水下 ⇒ 一片不生。
  改用水面当基准会让叶子出生在潜水玩家**头顶 8 格**之上（语义错，本轮单测 RED 抓到）。
  而站在水上时落点钳在水面 + **y 单调不增** ⇒ 全程不可能入水，无需逐帧扫描。
- ⚠️⚠️ **验落叶水下门不能在湖里验**：浅水高台的湖是 **SWAMP** biome，
  而落叶池的 biome 门（`=== 'FOREST'`）**先 early-return** ⇒ 水下门根本跑不到
  （实测 `dbg.underwater` 恒 false、biome='SWAMP'）。正解：在**FOREST 列**上用
  `editor.setBlocks` 按玩家当前 y 造一片水（同既有「头顶造屋顶」用例的手法）。
- ⚠️ **两种雨都要改**：`rain.js`（循环雨滴）与 `storm-rain.js`（持续雨）共用截停语义。
  只改持续雨会留下「关掉雨天光影后循环雨滴又掉进湖里」。

## 屏幕竖纹「粗糙」与关档后雨声残留（v3.30e，用户实玩报告）

### MSAA 不能替代 FXAA —— shader 内高频纹理必然走样

- ⚠️⚠️ **「本仓开了 MSAA 所以不用 FXAA」这条判断只对几何边缘成立**：MSAA 在光栅化阶段
  对**三角形覆盖**多点采样，而 shader 内部 `texture()` 采出的高频内容**每个像素只算一次**
  ⇒ MSAA 对它**完全无效**。移植上游后处理时按这条判断删掉 FXAA，就把上游赖以避免走样的
  那一环抽掉了 ⇒ 上游能看的层在本仓必然粗糙。
- **实测根因链（单变量，全部走真实 GPU 像素）**：远景雨幕把 512² 细丝纹理按柱面投影铺满
  屏幕，三层 tiles=12/25/50 ⇒ 横向密度 **1.37 / 2.85 / 5.69 texel/像素**（上游 4.91，同样欠采样）。
  | 单变量 | 天空竖纹（符号翻转/行） |
  |---|---|
  | 原图 512² | **83.5** |
  | 只留纵向渐变（无横向高频） | **33.5**（= 无雨幕基线） |
  | 只留横向细丝 | **144.9** |
  | 横向 box blur R1 / R2 / R4 / R8 | 72.2 / 64.3 / 52.3 / **40.4**（单调） |
  | mip 开 / 关 / Nearest | 83.4 / 75.5 / 95.5 |
  ⇒ 竖纹 100% 来自纹理的横向高频；mip 只帮一点忙，解决不了欠采样。
- ⇒ **用户裁定整层去掉**（「感觉还不如去掉」）。雨感由真实几何承担：近景雨丝 5200 条 +
  水花 + 体积雾 + 湿地面反光。连带删掉条纹图产物/烘焙脚本/加载器/`uRainGain`/`uRainSheetOn`/
  `setRainSheet`/`checkRainSheet` 门禁/`npm run rainsheet`。
- ⚠️ **判据选型：走样要用「符号翻转次数」，不能用「相邻像素差为 0 的比例」**。
  后者是 v3.30d 抓硬格子用的，对走样**零判别力** —— 走样恰恰是处处都不同（那个比例反而更低）。
  同一行内相邻像素 luma 差的符号翻转次数直接刻画横向高频。

### 换纹理内容做 A/B 必须换整个 Texture 对象

- ⚠️⚠️ **改 `tex.image = 新canvas` + `needsUpdate = true` 不生效**：three 按
  `source.version` 决定是否重传，换 image 不动 source ⇒ GPU 上还是旧图。
  **实测证据**：连换 64²/16²/纯灰三档，像素读数**逐位不变**（83.8/157.6 三次完全相同）。
  正解：造新 Texture 走 `setRainSheet()`（或直接改 `TextureNode.value`）。
  ⚠️ 读数逐位相同就是「注入没落地」的信号 —— 不要把它读成「这个变量没影响」。

### 开关型档位必须还原它改过的全局状态

- ⚠️⚠️ **开启时 `weather.force('rain')`，关闭时只停自己的音轨 ⇒ 旧雨声接管**：
  天气状态机被永久推成 rain，而帧循环的 `_syncRainSound()` 按 `weather.intensity` 驱动
  旧的 `rain` 循环 ⇒ 用户听到「关掉雨天光影后声音还留着」。
  实测：开启前 `loops={}` → 关闭后 `rain` 音量 **0.12** → 4 秒后 **0.2**。
  ⇒ 正解：**首次开启时快照** `{kind, intensity, phase}`，关闭时还原（用户裁定）。
- ⚠️ **快照只能在首次开启时存**：重复调用 `setStormLighting(true)` 若覆盖快照，
  第二次开就会把自己推成的 rain 当成「原状态」⇒ 永远还原不回晴天。判据要跑**三轮开关**。
- ⚠️ **还原不能只调 `force(prev.kind)`**：那会走 5 秒过渡，期间 intensity 仍 >0
  ⇒ 雨声还响几秒（用户要求「关掉就应当关闭」）。必须**直接写回稳态值**并复位
  `_phase/_timer/_startIntensity/_targetIntensity/stateSeconds` —— 只改 kind/intensity
  会留下「稳态但计时器停在过渡中」的不一致状态，下次自动切天气的时机漂。
- ⚠️ **关闭分支要立即对齐另一条音轨**（`_syncRainSound()`），不能等下一帧。

## 雨雾「光栅扫描」与湿地面「地下透射」（v3.30d，用户实玩报告）

### 光栅感 = hash(floor(uv)) 硬格子

- ⚠️⚠️ **`hash(floor(uv * k))` 造不出雨丝/雾，只能造矩形块**：每个 cell 整体亮或整体暗
  ⇒ 屏幕上是一片轴对齐色块。实测「雨幕层」相邻像素**完全相同 82.06%**（场景本身 4.6%）。
  上游用的是 **900 条亚像素宽、带纵向渐变的细丝纹理** + 双线性/mip 采样。
  ⇒ 当时烘焙 `assets/effects/rain-sheet.png`（上游 makeRainSheet 逐字），
  雾改**连续 perlin 两层 octave**。修后雨幕层 15.9%、雾层 16.7%（接近场景水平）。
  ⚠️⚠️ **条纹图那条结论已被 v3.30e 推翻**：换成双线性纹理解决了「硬格子」，
  却暴露出**第二个根因 —— 欠采样走样**（柱面投影 1.4~5.7 texel/px）。
  用户裁定**整层移除**，条纹图与烘焙脚本已删。详见下一节。
  **雾改 perlin 那条仍然有效**（它是独立修复）。
- ⚠️ **块状度判据**：量「相邻像素差为 0 的比例」，而不是看截图。硬格子 ⇒ 该比例极高；
  连续噪声/双线性纹理 ⇒ 接近场景本身。⚠️ 必须量**效应层自身**（开-关差分放大），
  量整幅会被场景内容淹没。
- ⚠️ **视线方向必须转世界空间**：旧实现用固定 fov 常量近似且**没过 cameraWorldMatrix**
  ⇒ 雾与雨幕的柱面坐标跟着屏幕而不是世界 ⇒ 转镜头时雨幕贴着屏幕转。
  正解：screenUV → inverse projection → cameraWorldMatrix（上游 uInvProj + uCamWorld 同口径）。

### texture(uniform(Texture)) ⇒ 整条链 build 失败 ⇒ 全屏黑

- ⚠️⚠️ **`texture(GRADE_UNIFORMS.uRainSheet, uv)` 会抛 NodeError**：第一个参数是
  **UniformNode** 而不是 Texture，`TextureNode.setup` 要求 `value.isTexture === true`
  ⇒ `THREE.TSL: texture(value) function expects a valid instance of THREE.Texture()`
  ⇒ **整条后处理链 build 失败 ⇒ 全屏黑（只剩 HUD/面板）**。
  正解：用**真实 Texture 实例**构造 TextureNode 一次（占位图），加载完成后改 `node.value`。
- ⚠️ 这个缺陷**只在收集 console 错误的探针里可见**：画面全黑但 `worldReady` 仍 true、
  所有 uniform 值都对。⇒ 新增后处理项必须配一条「无 console 错误」判据。

### 湿地面反射：复用海平面 reflector 在几何上不可能正确

- ⚠️⚠️ **上游的「压平到镜面再投影」是 no-op，本仓不是**：上游地面就在 y=0、镜面也在 y=0；
  本仓地面是起伏体素（实测 y≈22），而既有水面 reflector 镜面固定在 −1.5
  ⇒ 压平把地面点**推低 23.5 格** ⇒ 投影出画：**近处完全没反光、远处采到错位内容**
  （用户读作「地下一层模糊的透射」）。**与采样坐标怎么写无关**。
  ⇒ 正解：**独立地面反射 pass**，镜面 = 玩家脚下地面顶面（平滑跟随，瞬移吸附）。
  修后近/中/远三带反光占比 0.38 / 0.55 / 0.79（缺陷态 near=0）。
- ⚠️ **rfade 是涟漪的距离衰减，不能乘进反射项**：旧实现把 `rfade`（8~26 格）乘进 reflTerm
  ⇒ **26 格外完全没反光**（用户：「有的方块并不是呈现反射效果」）。上游只把它用在 nxy 上。
- ⚠️⚠️ **两条 reflector pass 必须各自套 multi-draw 守卫**：都走 `renderer.render`
  ⇒ 都覆写 BatchedMesh 的 `_multiDraw*` / `_indirectTexture` ⇒ 第二条覆盖第一条
  ⇒ 主 pass 读到反射视锥的剔除结果 ⇒ 天空撕成黑多边形（v3.17 同一机制）。
  新增 `renderWorld.beginReflectGuard()/endReflectGuard()`，每条 pass 前后成对调用。
- ⚠️⚠️ **采样节点必须是 `node.clone()`**：`base.textureNode === node`（同一对象），
  reflector 内部 `update()` 会把真 RT 写回它 ⇒ pass 前设的占位图**立即被覆盖**
  ⇒ 同 pass 读写同一张 RT ⇒ WebGPU 验证错误 ⇒ **整个 CommandBuffer 作废 ⇒ 全屏黑**。
  clone 共享 base（同一条 pass / 同一张 RT）但 value 独立 ⇒ 可安全换占位图。
- ⚠️ **WET_UNIFORMS 是 `Object.freeze`** ⇒ 不能 `wetU.uWetReflMatrix = 别的 uniform`
  （抛 `Cannot assign to read only property` ⇒ **启动期就挂，worldReady 永不 true**）。
  正解：让写入方持有目标 uniform 的引用，往它的 `.value` 里 copy。

### 分级必须在正确的色彩空间

- ⚠️⚠️ **冷调与 S 曲线必须在 ACES 之后（显示空间）**：上游 GRADE_FRAG 顺序是
  「暗角 → **aces()** → 冷调 → S曲线 → gamma」。本仓 renderer 已设 ACES，
  若保持 `outputColorTransform = true`，three 在**最外层**接 renderOutput
  ⇒ 冷调与 S 曲线落在**线性空间** ⇒ 暗部 col≪1 被 `col²(3−2col)` **平方级压暗**
  （0.02 → 0.0012）⇒ 天空/暗部近黑（实测近黑占比 0.1436 vs 关分级 0.0064）。
  正解：`outputColorTransform = false` + **自己调 renderOutput**，分级拆成
  线性段（bloom/曝光/暗角/色差/颗粒）→ ACES+sRGB → 显示段（冷调/S曲线）。
- ⚠️ **暗角强度要按本仓亮场景重标**：上游 0.62 是夜景（天空 luma≈20）标定；
  本仓正午天空 luma≈190 ⇒ 边缘被压到近黑。取 **0.34**（实测边缘近黑 0.30→0.157）。

### 预热帧数不能写死 —— 要按「输出收敛」判

- ⚠️⚠️ **后处理链的预热在单跑时够、批次高负载时不够**：RTTNode 首帧才定 RT 尺寸/建缓存。
  写死「预热两帧」的用例实测**单跑 3 轮全 diff 0、全 spec 跑也 0，只在 9 个 spec 的批次里
  diff 0.373**（而相机/世界/uniform 状态逐位相同）。
  ⇒ 正解：**轮询到连续两次截图逐位一致**再取样（上限 12 轮），不依赖机器负载。
  ⚠️ 这不是放宽阈值 —— 阈值仍是 diff<0.005，改的是**取样前的收敛条件**。
- ⚠️ 一般化：**任何「等 N 帧/N 毫秒就好了」的前置都是负载敏感的**。
  能写出收敛判据的就写收敛判据（本仓既有口径：等 `slotMap.size` 连续 3 次不变）。

### 三条判据坑（本轮实测，全部是测量方法错而非实现错）

- ⚠️⚠️ **「天空近黑」不能量整条上带**：本机位左侧 10% 是**建筑/地形**（无链时 luma 54），
  分级把暗部进一步压暗是正常的 ⇒ 量整条带会把「建筑被压暗」误判成撕碎。
  正解：量**中心天空区**（x∈[0.35,0.65], y∈[0,0.2]），无缺陷时那里是纯天空。
- ⚠️⚠️ **后处理链必须预热两帧再取样**：RTTNode 首帧才确定 RT 尺寸/建缓存，
  首两次渲染输出不同（实测 diff 90%→37% 逐次变化，而相机/世界/uniform **逐位相同**）。
  预热后 diff **0**。⇒ 「同姿态重渲必须稳定」的判据要先预热。
- ⚠️ **两次取样之间不得推进 player，也不得让世界继续 streaming**：
  多调一次 `player.update` ⇒ 相机再走一帧（viewBob/stepLift/sway）；
  帧循环停了但 Worker 回调仍在发布 section ⇒ 地形还在长。两者都会造成 diff 90%。
  正解：等 `slotMap.size` 连续 3 次不变再冻帧，两次取样都**只重渲**。
- ⚠️ **颗粒按 uTime 逐帧变**（上游同口径）⇒ 量「雨幕是否稳定」必须先关 uGrain，
  否则量到的是颗粒在动。

## 共享 scratch + 延迟求值 ⇒ 锚点串位（v3.30c，用户实玩报告「曳光起点偏右」）

- ⚠️⚠️ **两个 getter 共用同一个 scratch Vector3，调用方延迟求值 ⇒ 前一个被后一个覆写**：
  ```js
  muzzleWorld(out = this._v) { … }   // 两个方法默认同一个 this._v
  portWorld(out = this._v)   { … }
  const mw = view.muzzleWorld();
  const pw = view.portWorld();        // ← 此刻 mw 已被 port 覆写
  fx.spawn({ muzzle: [mw.x,…], port: [pw.x,…] });   // 对象字面量到这里才求值
  ```
  ⇒ **曳光从抛壳口射出**。实测偏移 `+0.0908x / −0.0132y / +0.675z`
  （≈ `port.z − muzzle.z = 0.68`），屏幕上从 (697,437) 跑到 (954,614) —— 右下偏 **257px**。
  用户看到的是「稍微向右偏了几像素」（远处曳光起点在屏幕上的投影差随距离缩小）。
- **两道防线都要做**：① 渲染层给每个锚点**独立 scratch**；② 调用方**取完立即展开成数组**
  （`const muzzle = [mw.x, mw.y, mw.z]`），不持有 Vector3 引用跨越下一次调用。
- ⚠️ **判据必须读真实 GPU 属性**（曳光池的 `aA`）与**真实几何投影**：
  锚点局部坐标、rig 姿态、`effect.start` 全都正确 —— 只有写入 GPU 的那个值错了。
- ⚠️ **容差要按 Float32 量化定**：`aA` 是 Float32Array，世界坐标 ≈283 时量化误差约 **2e-5**
  ⇒ 写 `< 1e-6` 会把「正确的 float32 存储」判成缺陷（实测 1.96e-6 假红）。取 `1e-4`。
- ⚠️⚠️ **连射判据必须在开火瞬间取样，不能在帧末**：曳光起点是**开火那一刻**冻结的，
  而视图模型每帧还在摆动/后坐。在 `v.update()` 之后才取枪口比对 ⇒ 差一帧的摆动量
  （实测 **0.0445 格**，与 1/120s 的摆动量同量级）—— 那是**测量时机错**不是实现错。
  正解：包一层 `fx.spawnFromEffect`，在它被调用瞬间同步读枪口（修后 maxDist **1.4e-5**）。
- ⚠️ **无人消费的共享 scratch 导出是同类缺陷的温床**：本轮顺手删掉
  `carbineFxScratch` / `stormRainScratch` 两个死导出（全仓零消费点）。

## 视图模型 quad 的 uv 口径（v3.30b，用户实玩报告「火光是方块」）

- ⚠️⚠️ **`PlaneGeometry(w,h)` 的 `position.xy` 是真实尺寸（±w/2, ±h/2），不是单位 quad**。
  拿 `positionGeometry.xy.mul(2)` 当 uv 用，在 0.24×0.24 的 quad 上只到 **±0.24**
  ⇒ `r = length(vUv) ≤ 0.34`，**永远到不了 0.7~1.0 的边缘门** ⇒ `edge≡1`、
  `core=exp(−r²·9)≈1` 恒亮 ⇒ **整片 quad 满亮 = 白方块**（用户读作「纸片一样的方块」）。
  上游 `vUv = uv`（∈[0,1]）、片元 `c = vUv*2−1`（∈±1）⇒ r 真正覆盖 0..1.41。
  **正解：`vUv.assign(uv().mul(2).sub(1))`**。
  ⚠️ 本仓粒子池的 `QUAD_POS` 是 x∈±0.5 / y∈[0,1]，`x*2` 恰好 ∈±1 ⇒ 那些池**没有**这个 bug；
  只有直接用 `PlaneGeometry` 的视图模型 quad（火光/reticle）踩到。
- ⚠️⚠️ **暖色 HDR + additive 在亮背景上必钳白**（本仓 fire-ring/cinder 已记的同一条）：
  上游是 WebGL **夜景**（背景近黑）故 `vec4(col*power, 1)` + additive 成立；
  本仓正午天空 luma≈200 ⇒ `dst+src` 必削顶。**改 NormalBlending 但 alpha 恒 1 仍是白方块**
  （整片不透明覆盖）⇒ 必须 **NormalBlending + alpha = gain**（边缘 gain→0 自然羽化 = 柔光）。
  实测三档：additive+alpha1 → fill 1.00/warm 0；normal+alpha1 → fill 1.00/warm 0；
  normal+alpha=gain → fill 0.63/warm 2342。
- ⚠️ **量「火光面积随功率衰减」不能用绝对 luma 阈值**：火光变暗时亮天空露出来，
  `luma>150` 的计数反而**变大**（实测 13756→16641 的假象）；绝对暖色阈值（r>140）
  在 power<1 时又全部落空（2325→0→0）。**正解：先拍 power=0 基线，数相对基线的增量**
  （实测 3274→2538→1394，单调）。
- ⚠️ **自发光粒子材质要显式 `lights = false`**：`MeshBasicNodeMaterial` 默认
  `lights = true`，场景有双灯时 colorNode 会被 BasicLightingModel 的 indirect 乘上
  irradiance。本仓其余粒子池全部显式关了，视图模型的两个 quad 漏了（本轮补上）。

## reflector.clone() 的 value 不跟住真 RT（v3.30b，用户实玩报告「湿地面没反光」）

- ⚠️⚠️ **`ReflectorNode.clone()` 只共享 base，`value` 是独立的**：reflector 内部
  每帧只把真 RT 写进 `base.textureNode.value`，clone 永远停在构造时的**默认占位 RT**
  （从未被渲染过）⇒ 湿地面采到空图 ⇒ **反射项恒黑**（单变量 A/B diff = 0）。
  实测取证：`clone.value.uuid ≠ base.textureNode.value.uuid`，且 clone 不在
  `base.renderTargets` 里；手动把 clone.value 指向真 RT 后 diff 立刻 0 → 860002。
  **正解：反射 pass 后把 `clone.value = base.textureNode.value` 同步一次**。
- ⚠️ **不能同步成 `savedTex`**（pass 前存的旧值）—— 那正是占位图，等于没修。
- ⚠️ **为何仍要 clone**：反射 pass 期间要把**湿分支的**采样源换成占位图（避免同 pass
  读写同一张 RT 的 WebGPU 验证错误），而水面自己的采样不受影响。两个需求缺一不可。
- ⚠️ **这个缺陷的判据必须是像素 A/B**：uniform 值（uWet=1 / uWetReflect=0.35）、
  节点存在性（hasUvNode / valueIsRT=true）、RT 尺寸（896×504）、refreshes=51
  **全部正常** —— 只有「反射项开/关的画面差分」能抓它。

## 湿地面复用反射 RT 的两个硬坑（v3.30）

- ⚠️⚠️ **同一 pass 里读写同一张 RT ⇒ WebGPU 验证错误**：反射 pass 把 RT 当渲染目标（写），
  而挂了湿分支的体素 opaque 材质在同一 pass 里采样它（读）⇒
  `Texture … usage (TextureBinding|RenderAttachment) includes writable usage and another
  usage in the same synchronization scope`。
- ⚠️⚠️ **「反射期间藏掉 opaque 通道」能消错，但是错的修法**（本轮单变量 A/B 实测）：
  藏掉后反射 RT 里没有地面 ⇒ **水面倒影映的全是天空** ⇒ 水色真的变了
  （morning 130→127 / noon 99→146 / share 4600→12000，撞冻结色阶）。
  那是真实观感回归，不是测量误差。**上游反射时也藏 groundMeshes，但它的湿地面
  不采样同一张 RT**（它用独立的 env cube 兑底）—— 照抄会错。
- ⚠️⚠️ **正解：给湿分支一个 `reflector.clone()`，反射 pass 期间把 clone 的 value
  换成 1×1 占位图**。clone 与原节点共享同一个 base（同一条 pass / 同一张 RT），
  但 value 独立 ⇒ 水面自己的采样不受影响，地面仍在反射里可见。
  ⚠️ **直接改原节点的 value 无效**：reflector 内部每帧把它写回真 RT
  （`this.textureNode.value = renderTarget.texture`）⇒ 你的替换被覆盖。
- ⚠️ **uniform 乘 0 不能消除「节点被采样」的事实**：WebGPU 仍会绑定该纹理 ⇒
  读写冲突依旧。必须换采样源本身，不能只把贡献乘零。
- ⚠️ **`createWetGroundNode` 在 `makeMaterial` 里直接调（不在 `Fn()` 体内）⇒
  不能用 `.toVar()` + `.assign()`**：TSL 的 assign 要求当前有 stack，否则报
  `No stack defined for assign operation`。**而且画面照常渲染**—— 只有收集 console
  错误的 spec（water-reflect）能抓它，其他全部全绿。正解：用普通 JS 变量持有节点（三元选）。

## 资源与目录

- ⚠️ **「新方块必须是数组最后一项」这类断言会被下一次正当追加推翻（v3.19）**：
  真意图是「旧方块的 id 不得位移」⇒ 钉**绝对下标**（如 bush_grass ≡ 154）+ 「新增项在它之后」，

- ⚠️⚠️ **末尾追加方块不得清档（v3.19）**：`registry.fingerprint()` 是「名字有序清单」的哈希，
  在 `BLOCKS` **末尾追加**时既有 id 逐位未变（旧 edits 完全可读）而指纹会变
  （实测 155→159 项：`fc6212f5 → 16d99151`）⇒ 旧判据（全等）会白白清掉玩家手工建造。
  正解：meta 行记 `blockCount`，用 `registry.fingerprintOfPrefix(oldCount)` 判「旧清单是当前清单的前缀」。
  **中间插入/删除/换序仍必须清档**（前缀指纹会变，单测逐条钉）；旧存档无 `blockCount` → 回落全等口径。
  哈希算法只得一份（`fingerprint()` 转调 `fingerprintOfPrefix(count)`）。
- ⚠️⚠️ **从放大图还原 16×16 贴图必须带「众数一致性」自检（v3.19）**：用户给的 512×512 图
  不透明 bbox 是 `[25,486]²`（462×462，每 texel **28.875px 非整数**）。origin/span 取错时
  产物仍是「16×16 的紫色图」，**尺寸/色数/均值都可能看着合理**而图案整体错位。
  判据 = 逐 texel「中心取样色 == 该区域不透明像素众数」（实测 0/256 不符，区域纯度 98.29%）。
  ⚠️ **单测里用整数 step 造「错一格」拓不到**（step=8 时 origin+4 仍是每格正中心，分区跟着平移）
  ⇒ 要用**奇数 step** 造半格漂移。
- ⚠️ **「等色重映射」类烘焙要钉图案分区签名，不能只比色数（v3.19）**：blockrender 的 vanilla
  贴图与 wiki 现版渲染图**图案逐格一致、色板差一层**（mossy 的 `8b898b` vs `888688`）。
  反解口径：wiki 300×300 等轴测图的**顶面**三角 `tv=(148,0) / rv=(282,66) / lv=(14,66)`
  （实测拟合；换成「看着对」的 (150,2)/(284,76)/(16,76) 会让每个源色映到 9~24 个渲染色）。
  判据两条：① 每个源色**只能映到一个**渲染色（否则 throw）；② 重映射前后 `patternSignature` 逐格相等。
- **资源路径只能走 `resourceUrl()`**（`src/core/resource-url.js`），禁止站点根绝对路径（`'/assets/`、
  `'/src/`、`'/vendor/`）—— 仓库挂子路径部署时会全 404，而本机 dev server 恒为根路径所以测不出来。
  HTML 的 import map 无法调函数：`index.html` 写 `./vendor/...`，`src/tests/*.html` 写 `../../vendor/...`。
- `assets/textures/` 被 `build-atlas` **递归扫描** → 任何源图/中间物/logo 放进去都会变成一个巨型 tile。
  烘焙输入放各自的 `assets/<topic>/src/`，UI 素材放 `assets/ui/`。
- 被 node 工具 import 的路径常量（如 `sky-config.js` 的 `SKY_DIR`）保持仓库相对字符串，URL 转换只在消费端。

- **转身限速只能接 `_applyIntent`，不得接 `setIntent`**（与 v2.40「避障探针只能接 `_applyIntent`」
  同一条边界）：后者是通用意图写入口，物理用例/调试代码直接下令，限速长在里面会偷换
  「想让它朝哪就朝哪」的语义。dt 用 `aiPeriod`（0.05s）**不用帧 dt**（它由 20Hz 导航驱动）。
- **行为层的 `nowMs` 必须由 `update()` 一路转发**：不转发时 `_stepNavigator` 落回
  `performance.now()`，与单测的仿真时间**混用两个时基** ⇒ 滚动窗口永铺不满、卡住判据恒不成立
  （纯函数全绿而接线完全失效）。同理：**单测里循环调 `update()` 必须同时推进 `nowMs`**，
  否则 N 拍在同一毫秒内跑完 ⇒ 起步加速因子恒 0 ⇒ 速度永远起不来。
- **速度包络只乘导航分量，排斥力全额叠加**；乘到「导航+排斥力」合成向量上会把排斥力一起缩小
  ⇒ 20 只同点生成散不开。**转向减速每拍独立算，不得累乘**（累乘会让丧尸在连续绕行中越来越慢）。
- **写「倍率不累积」类断言要用绝对值，不能用比值**：比值会约掉衰减（实测：注入「lastDir 只设一次」
  后倍率 0.999→0.874→0.749→0.699 逐拍下滑，而比值判据仍全绿）。且**用例不得自己写 `b.lastDir`**
  —— 那会掩盖「生产代码是否每拍更新它」这个被测行为。
- **判「replan 真的清了缓存」不能用 `cachedPathOf(id) === null`**：不可达场景的 `_path` 本就是 null
  ⇒ 清与不清都读到 null（恒真）。用 `pathCache.debugState().size === 0`。
- ⚠️⚠️ **`backoff` 必须有硬超时，两个「自然」退出判据在封闭死胡同里会同时失效**（v3.11b 用户实玩）：
  ① 「退够目标距离」—— 口袋里退 1.27 格就撞墙，`walked` 永远卡在 1.268 < 1.5；
  ② 「本拍没动 ⇒ 撞墙」—— `steerIntent` 把撞墙意图修成**沿墙侧滑**，每拍都在动（vx ±0.66 交替）。
  实测 backoff 持续 **27.13s**、占 94% 帧，永不 replan/wander ⇒ 用户看到「一群丧尸卡在胡同里循环」。
- **后退要「面朝玩家倒着退」**（用户明确要求）：行为层 backoff 相位给 `faceYaw`，`_applyIntent` 拿它当限速目标。
  ⚠️ **yaw 覆写判据只能与 `cur.state.yaw` 比**：`setIntent` 已先把 yaw 写成速度派生值（后退时 180°、侧滑时 ±60° 摆），
  用 `limited !== targetYaw`（一步到位时跳过写入）或 `limited !== prevYaw`（结果等于旧朝向时跳过）**都会把脏值留下**，
  实测两种写法都仍单帧跳 180°。这条我改了两次才对。
- **朝向类判据要跳过转身过渡段**：540°/s 转 180° 需 0.33s，进入 backoff 首帧本来就背对；
  实测残留背对帧全在 ≤0.1s 内且角度单调收敛 ⇒ 判「稳定段（>0.5s）不得背对」，不是从第一帧就要 0。
- ⚠️⚠️ **「N 轮失败后进入某状态」的功能必须直接钉那个状态真的出现过**（v3.11 final review 实测）：
  `behaviorPhases.hesitate/backoff > 0` 全绿，而 **wander 从未发生**（40s 相位 wander=0、failCount 恒 0）。
  根因：replan 结算紧跟 backoff，backoff 自己刚走 1~2 格 ⇒ 滚动窗口仍显示「在动」⇒ 误判「有路」⇒ 计数归零。
  ⇒ **「有没有路」要问 A\* 的 `step.reachable`（几何可达性），不能问「这几秒动没动」**；
  同理 wander 的退出判据**不得叠 `!stuck.stuck`** —— 它自身小范围踱步 ⇒ 净位移天然 <0.35 ⇒ 永远出不来。
- ⚠️ **`cruiseScaleMin` 不被既有 12s 绕墙 E2E 守住**（实测 0.92→0.70 仍 PASS）：那个探针量的是
  「**全程恒定倍率**」，而真实包络是正弦漂移×起步×转向，只在波谷瞬时接近下界。调它要自己重测。

  正解：运行期搜索「墙高≥5 + 相机到墙脚全干燥无建筑遮挡 + 抬升列≥4 + 每步≤1」，
  seed 12345 选出 z=21 / (-214,4,238)（裙边 T 从 1 逐级抬到 10，每步恰 1 格）。
- ⚠️ **对照组必须同机位单变量**：旧 spec 用「远处森林 (40,30,40)」当对照 —— 不同机位不同地形，
  灰石占比不可比。改用 `page.route` 换 baseY/R/BW 后**重拍同一机位**：
  俯瞰 base 0.2488 vs 埋回 0.0304（8.2×）、裙边视廊 base 0.3877 vs 无裙边 0.0464（8.4×）。
- **墩格不需要单独进植被让位索引**：它们恒在「该列屋顶下方」，已被 `jfCellFreeAt` 的②挡住
  （实测 763 个树冠意图∩墩格零穿模）；**裙边格必须进**（实测 1 格穿模）。
- **`anchor.floorY` 语义 = baseY（75 分位）**，五处消费方（光栅化/瞬移/植被/单测/spec）同改；
  `minH` 保留旧语义。`percentile75` 是**独立纯函数**，单测喂合成数组钉住，不硬编码 9。
- **层序：先光栅化 → 后墩 → 后裙边**（裙边读墩顶作为包络源）。
- ⚠️⚠️ **重活必须在 `world-worker.js` 的 layout 入口预热**（仓库已有四个锚点的同款手法）：
  裙边包络场首次 **130~209ms**，不预热就落进首个 GEN（genP95 门 10ms）。
  且**缓存要在函数入口**：只在 `surfaceYAt` 侧缓存、让位索引侧直调 ⇒ 再全量重算 40ms。
  实测修后一次性成本 **82.4ms → 1.8ms**（A/B 交替 3 轮）。
- ⚠️⚠️ **Worker 脚本不走 `page.route`**：用它换 GEN 模块做对照组**完全无效**
  （实测 base/noskirt 五个机位读数逐位相同）。GEN 类对照要用**不依赖注入的独立真值**
  （如「同一列的 `generateHeight`」），或在主线程侧用 `registerHooks` 注入跑同构 GEN。
- ⚠️ **像素阈值必须在 spec 的真实 viewport 下标定**：Playwright 默认 **1280×720**，
  探针自设 960×600 会因视野更宽而稀释占比（同机位 0.3736 vs 0.0397，差 9.4×）。
- ⚠️ **`gotoAndView` 类夹具在 STABLE 后必须重钉一次位置**：等 column 加载期间物理已在跑，
  玩家会从未加载的空中坠落（实测 y 从 4 掉到 −23）⇒ 截图机位与请求不符、像素判据随机漂。
- ⚠️ **「世界地面」判据要钉「T 那一格是否实心」**，不用「从高处向下扫第一个非空气」
  —— 后者会命中树冠/树干（实测把 T=2 读成 4，假红）。

## 确定性

- `seededRandom` 的 salt 占用必须**程序化扫描**，grep 字面量抓不到 `seed + N` 形式的区间占用。
  已占 1020~1040 段（1028 是被跳过的洞，保守避开）。用错 salt 是静默的确定性污染。
- 结构写入无占用格守卫（`makeColumnSetter` 后写胜，与 mc-lite 先写胜不同；未注册名字**静默 return**
  → 那格变 air）。**写结构类断言不得假设「每个结构都完整」**。

## UI 布局

- **瞬移行的按钮文案上限随按钮数递减**（v2.89 实测）：左列 375px + `.mc-btn-group` 平分，
  六按钮 4 字、七按钮 3 字（靠本行专属 `gap:4px`）、**八按钮只剩 2 字**（每只文字可用 31.4px，
  3 字 36px 折行，即使 gap 收到 0px 也只有 34.9px ⇒ 无解）。加按钮前先量真实布局
  （`Range.getClientRects()` 行盒数），`scrollWidth <= clientWidth` 对折行无判别力（折行时两者仍相等）。
- ⚠️ **`PANEL_CSS` 是 JS 模板字面量，注释里不得出现反引号**（v3.25 实测踩了两次，形态是
  `SyntaxError: Unexpected identifier` 让整页白屏）。写完 `node --check src/ui/settings-panel.js`
  一秒能拓。
- ⚠️ **设置弹窗的高度改成固定值后才能做「切 Tab 尺寸不变」**（v3.25）：旧布局是 `auto` 高度（内容
  决定），两 Tab 内容高不同 ⇒ 切换必跳。定高（用户定 **560px**，content-box ⇒ 外框 818×608）后
  内部三段为 Tab 栏 40+14 / 页内容区 `flex:1` / 底栏 58，可视高 **448px** 恰好容下两页（436 / 441）。
  判据只能用 `getBoundingClientRect` **逐位相等**，不能用「看着没变」；同时要量 `scrollHeight ===
  clientHeight`（压过头时盒子尺寸照样"不变"，只是多出滚动条）。
- ⚠️ **大图（14MB）不得在面板构造时设 `src`**：把 `src` 延迟到首次切到该页（`_aboutImageSrcSet`
  只设一次），否则每次开游戏都在后台拉一次。路径必须走 `resourceUrl()` —— 站点根绝对路径在
  子路径部署下 404，而**只在切到那页时表现为破图，零报错**。
- ☠️☠️ **屏外方位指示不得用相机空间（含 pitch）—— v3.42 的 `|cz|` 方案已被用户实玩推翻**（v3.43）：
  箭头表达的是「敌人相对玩家**身体**的方位」，不是「相对镜头的投影」。v3.42 用真实相机空间
  （含玩家俯仰）+ `|cz|` 算方位 ⇒ 实测同一只身后丧尸：pitch 0° → 下边；**+30° → 上边；+60° → 上边**。
  用户原话：「显示在上方，就给人感觉好像在空中一样」。那不是参数问题，是把镜头朝向当成了方位。
  **正解（v3.43）**：可见性判据用含 pitch 的相机空间（`arrowNdc`+`isOffscreen`），
  **方位另走只吃 yaw 的双轴模型**（`arrowDirection`）：
  `sx = sin(b)·W`；`sy = back·D − sin(elev)·H − sky·1.2H + deep·1.2H`。
  判据 = **俯仰无关性**：同一世界位置在 7 个俯仰角（0,±30,±60,±80）下必须落同一条边。
  ⚠️ v3.42 那条「前后共用一套符号」仍适用于**可见性判据**，但**不再用于算方位**。
- ⚠️ **方位模型的「身后偏置」必须带 0.7 次幂，且不得用 floor 代替**（v3.43 实测）：
  `back = max(0,−cos b)^0.7`。pow=1 时刚过正侧方 3°（bearing 93°）的高台敌人 back 仅 **0.052**，
  而高度项达 **1.58** ⇒ 身后高台敌人被归到上边（实测 110/1261 样本）。改用「给 back 加下限 floor」
  虽能消泄漏，但引入不连续点，转身跳变从 48px 恶化到 **108px**（floor=0.25 时 280px）。
  ⚠️ **`D` 与 `H` 必须成对标定**：单独把 D 调到 5 会把「身后高空 +20 格的飞龙」全部推到下边，
  直接违反用户「头顶上空的飞龙该在上边」那条诉求。
- ⚠️⚠️ **「转身连续」的判据是「位移随步长等比缩小」，不是「位移 < 某绝对值」**（v3.43 实测踩到）：
  首版写「15° 步长位移 < 300px」，实测 **327px** 真红 —— 但探针查明那是**沿同一条边滑动**
  （两点 x 都是 62，y 从 624 到 297），是平滑移动而非闪现。步长 15°→5°→1° 实测 **327→149→48px**
  ⇒ 连续。分带方案的 645~735px 是跨边闪现，**缩小步长也不会变小** ⇒ 比值判据才有判别力。
- ⚠️ **边缘求交要用按屏幕比例内缩的矩形，不是 margin 矩形**（v3.43）：
  margin 矩形 578×330（宽高比 1.75）≠ 屏幕 1280×720（1.78）⇒ 斜方向被误判。
  正解：求交矩形 hw/hh **等于屏幕 aspect**，落点再钳进 margin 安全带。
- ⚠️ **连续性探针必须跳过「箭头本就不显示」的帧**（v3.43）：敌人转到正前方时箭头不画，
  把那些帧也算进去等于在量「不存在的箭头」的位置。实测不跳过读 **78.8px**（发生在 bearing 180°），
  跳过后是 **48.1px** —— 后者才是玩家真实看到的移动。
- ⚠️ **手算 bearing 造夹具会错，要用 `at(bearingDeg)` 生成**（v3.43 设计期踩到）：
  我手算的「100°/110°」夹具实际是 80°/70°，据此得出的「模型不符」是假结论，白白多试了几轮模型。
- ⚠️ **`dragons.summon(mapKey, cx, cz, slot)` 的参数是「轨道中心」而不是落点**（v3.42 实测）：
  盘旋半径 24 ⇒ 中心放玩家 +Z 14 格时，龙当场在**前方** cz=−9.35 且在视口内。拿它做「背后敌人」
  夹具会得到「箭头本就不该出现」的假红。中心要放到 +60 格（整圈最近点仍 +36）。
- ⚠️ **远处落点夹具必须先看视距**（v3.42 实测）：`vd=4` 时 **80 格外的 column 根本未加载**
  ⇒ `isSolid` 恒假 ⇒ 向下扫地面找不到落点（报 `no ground`）。要测 150 格外的敌人就开 `vd=12`
  并等目标列 `hasColumn` 为真（实测 vd=12 下 150 格外列已加载、groundY=5）。这不是实现缺陷。

## 门禁与测试

- `src/tests/test-*.js` 必须同时出现在 `src/tests/index.html` 的 import 里 —— 漏注册是
  **测试静默不跑**（全绿假象），`check:data` 的 `[测试注册]` 环节双向钉住。
- **地牢可达性不得把台阶当可通行**（守卫 v2.91 实测推翻了直觉）：本仓台阶族一律 `solid:true`
  ⇒ `isSolid` 恒真 ⇒ 身体不能进入（楼梗是装饰，不可爬）。把台阶当 air 会算出「27,992 格连通」
  的假结论；真实口径下废弃堡垒三层房间**互不连通**（ny30/37 全层零 air，ny37 唯一开口是遭丢弃的
  `iron_trapdoor`）。另：洪泛探针的竖直移动必须**逐格检查通道**，否则会算出穿墙的假路径。
- **`HEADROOM` 与房间净空耦合，取 `ceil(height)` 而不是 `+1`**：上层房间净空只有 5 格，
  守卫高 3.8 ⇒ `ceil(3.8)+1 = 5` 会把落点判死而**静默召到下一层（差 8 格）**，所有计数/状态全对。
- **`maxStep` 在现有实现下是死值**：`zombieStepUpY(y) = floor(y+0.01)+1` 恒抬 1 格，
  `maxStep` 只做「抬升量 ≤ maxStep」的门控 ⇒ **1.75 与 1.0 逐位等价**。写 1.75 只得到一个看着生效
  实际无效的值；「验证 >1 格台阶」的探针两侧都无判别力。真要支持得改 `zombieStepUpY` 本身
  （影响丧尸/焰魔/玩家三方，是独立改动）。
- **判定器顺序用例的 seed 清单不能跳结构照搬**：大竞技场那八个 seed 在废弃堡垒上**零重叠**
  （净距 64~98 格 > 盒半宽 28）⇒ `checked > 0` 直接红。堡垒用 2096/2644/3740/4151/4973。
- **推出距离不是「最大绝对半宽 + 玩家半宽」**（守卫 `EJECT_MAX` 复核）：推出走**最近的一个面**，
  四方向取 min 后再对盒内站位取 max。守卫实测 **1.900**（yaw 42°），而「最大绝对半宽 1.905 + 0.3」
  算出 2.205 会误报超限。核心盒不对称（`center.z ≠ 0`）时两个口径差很多。
- **`_collides()` 漏加新 Boss 判据的形态很隐蔽**：`_collides` 返 false 而 `overlapsAabb` 返 true
  ⇒ 玩家走进盒内，再被 `_ejectFromBoss` 每帧外推一点、下一步又走回来 ⇒ 净效果是「停在盒内
  0.12 格深处」而不是盒外（守卫实测踩到）。新 Boss 必须同时接 `_collides` 顶部与 `_ejectFromBoss`。
- Playwright 必须 `channel: 'chromium'`：默认 headless shell 零 flag 拿不到 WebGPU adapter。
  `playwright.config.mjs` 全局 timeout 200s 必须 ≥ 各 spec 自己的等待窗口（`harness.spec` 等 150s、
  `harness-slow.spec` 等 600s 并自设 `test.setTimeout(700s)`）。
- 计时型 spec 在高负载下会贴线 flaky（`m1-acceptance` 放挖 p95、`m3-rain` 截图差分、
  `weapons-world-edit` 计数、bench 的 frameP95）。**判据看交替对照的分布，不看单次红绿**（不改阈值）。
- 写像素类断言必须**同时钉上下界**（只钉「变暗」抓不到「纯黑」），且先测同状态重复截图的噪声底。
- **像素颜色判据必须带对照组校准**（废弃堡垒 v2.89 实测）：
  · 「末地石主色」用 `g>=r && g>b*1.25 && lum>60` —— `g>=r` 排除沙漠沙（sand_side 193,183,144
    是 r>g），否则「只是沙漠没有结构」也命中，断言失去判别力（实测判别力 18×：0.419 vs 0.023）；
  · 「水体」用 `b>r+25 && g>r+12 && lum∈[95,150]` —— 漏 `g>r+12` 会让**紫色方块**误报
    （void_stone 120,31,225；v2.90 前 amethyst 141,103,197 也是，现已改映 deepslate 120,120,145
    —— 但 deepslate 的 g−r 恒为 0，等比缩放后仍被 `g>r+12` 排除），漏亮度门会让**雾化天空**（168,208,216，
    lum 197；`skybox=0` 的纯天蓝是 135,206,235，±30 容差抓不到它）与**暗 obsidian**（32,72,120，
    lum 75）误报（实测分别误报 11.83% 与 0.82%）。
- ⚠️⚠️ **命中实体类招式的「落点」必须截到实体表面，不能只看方块 DDA**（Storm Lance v3.20 用户实玩）：
  旧口径 `length = 轴线方块 DDA 距离`、实体命中只用于扣血 ⇒ 光柱/闪电**穿过 Boss 身体**、
  在它身后的方块上炸（用户原话：「而不是穿过身体到 boss 身体后方的方块触碰处爆炸」）。
  正解：`length = min(轴线方块距离, **五条射线全部命中里最小的实体 dist**)`。
  ⚠️ **必须取五条最小值而不是只查轴线**：Boss 盒大且随 yaw 旋转，偏移射线常更早碰到它。
  ⚠️ **落点仍取轴线上的截断点**（拿偏移射线自己的命中点会让爆壳画歪到束的一侧）。
  另需透传 `impactKind`（entity/block/air）—— **冲击环朝向要按它分流**（命中实体时环面法线朝玩家，
  否则贴地），丢掉它会让打 Boss 时环画在脚下地面上。判据要钉「落点到相机距离 ≈ 实体到相机距离」，
  并配一条**拆掉截断的负向对照**（否则「只看方块」的旧写法也可能碰巧绿）。
- ⚠️⚠️ **做发光光晕先抄仓库里的火球，别自己写 shader**（v3.20c 用户第三次反馈才纠正）：
  `fireball-renderer.js:57` 的 `makeFireballHaloTexture` = **canvas 径向渐变（最后一停 alpha=0）
  + CanvasTexture + MeshBasicMaterial(additive) + PlaneGeometry + billboard**，**零 shader**。
  边缘柔和完全来自渐变本身。我为蓄力球自写了一个 TSL 噪声光晕（衰减指数+噪声侵蚀+三层配色，
  7 个常量），**画面上没读出来**：外缘梯度 87~110，而换成火球式贴图后是 **11.6~12.5**（好 8 倍）。
  ⇒ **简单方案这里不只是省事，是更有效的那个**。billboard 靠装配层传 `camera.quaternion`
  （渲染器不持有相机）；`haloTexture` 留注入口让单测免 canvas。
- ⚠️⚠️ **「发光鸡蛋」= 实心 + 亮轮廓边 + 法线位移，且闭合网格的硬边调参数消不掉**（Storm Lance v3.20b 用户实玩）：
  三个成因各自可定位：基础 alpha 0.2（整球不透明⇒实心）、rim·0.9（轮廓比中心亮⇒亮硬边）、
  噪声沿法线位移 0.24（把球捏成蛋形）。但**球网格的几何轮廓本身是硬截断**
  （轮廓外根本没有片元）⇒ 无论怎么调 alpha 都有一条边。
  **正解：另加一层屏幕对齐的 billboard quad 光晕**，半径归一后 `pow(1−r, falloff)` 连续衰减到 0，
  quad 比可见光晕大一圈 ⇒ 几何边界落在完全透明处。再叠噪声侵蚀边缘（否则是完美圆盘）。
- ⚠️⚠️ **「边界清晰度」的像素判据：量外缘梯度绝对值，别用径向剖面**（v3.20b 三次实测推翻）：
  ① **找最亮像素定中心**会被同量级的粒子抢走原点（同一实现两轮 tailRatio 0.130/0.164，
  退化实现 0.190/**0.019**，方向都反了）；
  ② **相机投影定中心**会撞上 viewBob 每帧重写姿态（`player.js:380`）⇒ 新姿态配旧手点，
  实测偏 **59px/96px**（峰值 700→197）。⚠️ 不是 pixelRatio 问题（实测=1）。
  ③ **整场梯度分位数**被巨大光晕的内部平缓区主导（光晕直径实测 **454px**，占屏高 63%）
  ⇒ 柔和与退化完全重叠。
  **正解**：先圈亮区，只在「自己亮、四邻有不亮」的交界像素上取梯度均值，**用绝对值不用比值**
  （比值的分母 peak 随呼吸在 372~709 摆，会让两态撞车）。实测柔和 **87~110** vs 旧 **170~184**。
  ⇒ **凡以「最亮点」或「投影」为原点的统计量，先问它稳不稳；能不用中心就不用。**
- ⚠️⚠️ **负向对照必须还原「用户真正看到的旧参数」，不是只拆新增的那一层**（v3.20b）：
  只藏光晕 ⇒ 剩下的核心也已被软化 ⇒ 与正向重叠，复现不出缺陷。

  速度恒 0、`nav.decisions=0`。真实帧序是 `soldiers.update`（编排/寻路拍）→
  `entities.update`（Agent 决策 + 60Hz 物理），**两处都调**才有效。
- ☠️☠️ **验「士兵朝目标推进」时玩家必须远于站定环上界 20 格**：放 10 格外落在环 `[8,20]`
  内 = 纯侧向游走，实测士兵沿 −Z **走出地板掉进虚空**（y → −930），根本不会朝台壁走。
  取 24（Node）/ 26（E2E）格才触发径向推进 `towardFar`。
- ☠️ **「N 格墙必须 blocked」不能用无限长墙做夹具**：±90° 沿墙方向本来就通 ⇒ 3 格墙也返回
  `blocked=false`（假红）。正解：只留 1 格宽走廊 + 前方 N 格台壁，并配一条**同夹具低一级
  必须通行**的反向断言（否则 blocked 可能只是「夹具全堵」）。
- ☠️ **`StepLift` 的滞后上限必须按实体传**（缺省 1.0）：士兵一次抬 2 格时不传会被截断成 −1
  ⇒ 画面是「瞬时跳 1 格 + 缓动 1 格」。⚠️ 断言**不能写「偏移恰等 −2」**：`_writeSlot` 里
  `trigger` 之后同帧就跑了一次 `update(dt)` ⇒ 实测 **−1.6506**。阈值取衰减后的理论值
  `−2·e^(−12·0.016)`（截断版 −0.8253），另加 `off < −1.5` 作判别力下界。

  **不检查该 slot 是否仍被占用** ⇒ 指针绕回时新实体覆盖活实体的 7 个实例矩阵；
  新实体死后差集回收又把该 slot 清零 ⇒ **仍在场的那只也跟着不画**。
  用户看到的是「画面上的士兵数与数字对不上」，读作「计数器残留」。
- **触发条件是累计 spawn 次数 ≥ 池容量（2×maxAlive = 20）且此刻仍有 ≥2 只在场**。
  前三个探针（每轮全杀完再召、或只空转不留长命实体）**全绿** —— 指针绕回时池恰好是空的。
  ⇒ 复现必须「留两只长命的 + 让第三只不断进出」，纯 Node 最小复现第 18 轮即红。
- **判据只能是真实实例矩阵的非零 scale 数**：撞车时 `_slots.size` 与 `activeCount()`
  仍等于实体数（3 条 slot、报 3），而 GPU 侧只有 2 个非零实例 ⇒ 那两个判据零判别力。
- 修法：渲染层改用**显式空闲 slot 栈**（与 `SoldierService` 同口径），回收时归还。
  不要用「扫描跳过已占」代替归还 —— 池会被曾用过的 slot 占死。

### HUD 读数的 250ms 节流会造成整批假红（v3.39）

- 新用例在 spawn 后只等 **120ms** 就读 `#mc-enemy-counts-soldier`，26 拍**全部**失配
  （hud=2 / alive=3）。那不是缺陷：`ENEMY_COUNTS_INTERVAL_MS = 250`，夹具没跨过节流窗口。
  ⇒ 读 HUD 文本前必须等 **> 一个完整刷新周期**（取 320ms），**不得放宽断言**。

### 一次性音效的单槽 = 「枪声滞后」（v3.39，用户 2026-11-25）

- 用户原话：「soldier 射击时的声音有时候滞后发出，是有队列吗？我不要队列……
  声道挤占就丢弃掉，不要延迟或者滞后再补发」。
- **没有队列**，真因是 `AudioManager.play()` **每个 id 一个 `THREE.Audio` 单槽**，
  同名再播先 `stop()` 再 `play()`。真实 AudioContext 探针：3 只士兵 6s 内
  **47 次开火请求 → 46 次是「打断上一声从头重播」**。素材 `carbine_bullet.mp3`
  长 **0.519s**（ffprobe）而发间隔 0.105s ⇒ 每声只响 0.1s，听感就是「响声迟到」。
- **`playRequests` 对两种实现读数完全相同（47 vs 47）⇒ 零判别力**。
  有判别力的判据：包一层 `context.createBufferSource`，记每个 source 的 start/stop ⇒
  ① 打断次数必须 0；② 真的并发过 >1 路；③ 声道满时起播数不增（丢弃，不排队不补发）。
- 修法：`_voices` 改 `Map<string, THREE.Audio[]>` 声道池，上限权威在
  `audio-config.SOUND_VOICE_LIMITS`（缺省 1 = 旧行为，其余音效听感逐位不变）。
  ⚠️ 改 `_voices` 形状必须同步 `test-bgm.js` 的 teardown —— 它原来遍历单槽读
  `v.isPlaying`，在数组上恒 undefined ⇒ 声道不停、下个用例前置失真。

### 计数字段不一定是计数

- `CarbineFx.counts.tracers` 是 **0/1 的可见性标志**，不是条数 ⇒ `> before` 在已可见时恒真。
  判据要落在真实 GPU 属性（`aA`/`aB` 的起点/终点/出生秒/速度）。
- 失败探针写 `!t.passed` 而 runner 的字段是 `status:'failed'` ⇒ 把 2480 例全列成失败。
  **探针字段名必须核对被测结构**。
- `run-unit-node.mjs` 的参数是 **`--only=FILE`**（等号）；写成 `--only FILE` 不被识别 ⇒
  **静默跑全量**。发现方式：单文件跑的例数与全量相同。

## 跨 Epic

（值得背下来的几条，全部是静默失效型）

- 岩阶族的东西（台阶 AO、倒置台阶、栏杆臂）的**形状权威只有 mesher 的 `TEMPLATES` / `STEP_BOXES`**，
  与 `orientation.js`（放置期朝向）是两套语义，不得互推。
- 台阶亚体素 AO：纳入集合 = `STEP_BOXES` 的键（**半砖与装饰几何刻意不纳入**），采样点
  `顶点 + 0.25×(法线+两切向)`，第 4 样本 `front` 不能删 —— 改任一项都要跑 `test-mesher` 的四条台阶用例。
- `SHADOW_FLOOR ≡ SUN_AMBIENT`（同一语义两个名字）；`SUN_INTENSITY` 必须从 `noon.sunDirection`
  派生，使 `SUN_AMBIENT + SUN_INTENSITY × noonSunY ≡ 1.0`（= 「正午顶面亮度与加方向光之前相同」）。
  改任何风格的太阳方向后必须重算它，否则这条零回归不变式静默失效。
- `uSunStrength = 0` 必须让 `sunTerm ≡ 1`（而不是退化成 `SUN_AMBIENT`）；半球环境光 `HEMI_GROUND`
  与太阳无关，关方向光时仍生效。
- 体素材质是 unlit：面的朝向差异只能来自 packed 的法线位，不要试图用 `skyDim`/`blockBoost` 这类
  全局乘数调出「迎光面亮、背光面暗」。
- 两套「能否被穿透」的判定刻意不同：视线/炮塔 LOS 用 `solid && opaque`（玻璃透得过），
  火球遮挡只看 `solidTable`（玻璃挡得住）。混用任一侧都会撕裂。
- 火球爆炸走 `_applyExplosion`，**不走 `explodeTnt`** —— 后者的按格去重集合会被污染，导致之后同格
  放的 TNT 静默不爆。
- ⚠️⚠️⚠️ **抛物线招式的「射程」是瞄准点，不是安全上限 —— 不得照搬直线弹丸的「超距先早退」**
  （Cinder Fall v3.21 浏览器实测，33 条纯函数单测全绿）：`judgeProjectile` / `judgeFireball` 的
  「① 超距 → ② 方块 → ③ 实体」成立的前提是 `maxDistance` **远超正常射程**；而抛物线招的
  `distance` 就是瞄准点、`update` 又把 traveled 钳在它上 ⇒ **抵达瞄准点的最后一步永远先命中
  超距分支而 return**，方块/实体判定根本没跑 ⇒ 用户看到「球飞到了但没炸」（t≈150ms despawn
  而 blasts=0）。正解：先判本步线段，都没命中且已飞满 ⇒ `end-of-flight` 在末端自爆。
  **必须专门写「命中物恰好站在瞄准点」的单测**（只测途中命中拓不到）；假 raycast 的距离上界
  要与真 `raycastAabbSlab` 同口径（它判 `tEnter > maxDist`，**闭区间**），写严格 `<` 会制造假红。
- ⚠️⚠️ **抛物线的判定线段取 `prevPosition → position`**，不能用直线弹丸的
  `position − direction×stepLen`（抛物线下方向每步在变，会算出与实际轨迹不同的线段 ⇒ dt 尖峰穿墙）。
- ⚠️⚠️ **分段蓄力的阶段门要用「跨越标志」，不能对浮点时间取裸边界**（v3.21）：
  实测 `60×0.05 = 2.9999999999999973`（落在 3 **下方**）、`40×0.05 = 2.000000000000001`。
  controller 用 `was < 边界 && now >= 边界` 置标志（对累积误差免疫），纯函数侧留 1e-9 容差，
  **两侧必须同侧**（单测钉）。另：第二段起步那一帧 p2 恰好是 0，**尺寸进度要传 `max(p1,p2)`**，
  否则蓄力球在第三秒开始时**闪断一下**（静默观感缺陷，数值判据拓不到）。
- ⚠️ **新增效果事件必须接 `player._applyWeaponEffect` 的分流支**（v3.21 实测）：
  漏了 `cinder-fall` 那一支时，**事件发了、音效响了、但天上没岩石**（落到只认 tracer/impacts
  的通用分支）。只断言「事件存在」的用例零判别力 ⇒ 必须断言**松手同帧真的生成了实体**。
- **`_ignitingTnt` 的键必须在 `explodeTnt` 出口无条件释放**（v2.97）：只在该格「确实是 tnt」时删
  会让连锁幽灵项 / 枪击落空 / column 未加载的分支把键永久留下 —— 该格之后放的 TNT 被
  `has(key)` 静默拒爆（方块永远炸不掉、也永远不消失，用户报告的正是这条）。
  另外连锁入队必须按格去重，且去重不能只扫 `_tntChain`：`_updateTntChain` 逐项引爆前把本帧到期的
  项**整批**抽走 ⇒ 同批两项互相看不见。权威集合是 `_tntScheduled`（「已排期未引爆」），
  `explodeTnt` 若命中已排期格要撤掉它的排期项（否则多一次空爆炸）。
  ⚠️ **不要用「到期时先验证该格仍是 TNT」来替代去重** —— 那是 mc-lite 刻意没有的偏离，且会顺带变成
  「玩家能在延迟窗口内拆引信」这个没被要求的玩法变更。
- 所有玩法服务在 `EntityManager.update` 之外改 `state.position` 时，必须显式 `reindexColumn(id)`，
  否则实体停在旧 column 索引上不自愈。
- 击退（剑砍中）的**权威位移必须瞬时**，观感滞后只许落在渲染位置（`render/knockback-ease.js`，
  与上台阶只缓动渲染 y 同一分工）。触发必须走服务层的**显式上报告诉实际位移**，不能用
  「渲染位置与物理位置差得多就补间」—— 丧尸 AI 每帧 0.02 格与 0.9 格击退分帧后同一量级，阈值两侧都会误伤。
- 「绑定在某个 column 的派生 controller」的装配必须早于 `_waitForColumn`，否则首个 ready 回调
  拿不到 service（形态：装置不工作，而锚点、索引、方块全对）。多格结构的 origin 用命中格
  `blockPos`，单格实体（矿车）用 `prevPos`。
- **多格结构的 origin 必须先归一到地面格**（v3.13 炮塔悬空）：主射线对「非空气且非水」一律命中
  ⇒ 地面长草时 `blockPos` 是**草格**，直接当 origin 会让底座落在「草格+1」= 地面+2 而悬空。
  归一（`isPlant` 则下沉一格，**只一格**）与「蓝图格允许覆盖植物」都写在**服务层** `place()` 入口，
  不写 `Player.placeBlock()` —— `game.placeTurret()` 与背包分流是两个入口，写 player 里只修一条。
  `registry.isPlant` 派生自 `solidTable=0 && cullTable=cutout`（不写名字白名单，新植物自动纳入）；
  水与 alias 刻意不算（否则炮塔会沉到水底）。⚠️ 巢穴的同类判据尚未改。
- 玩家位置/设置的持久化字段写进既有 `meta` 行并 **merge** 后整行 put；`_discardEdits()` 必须把
  「位置写盘」置为未启用，否则换世界/清档后 `beforeunload` 会把旧世界坐标写回新世界。
- 翻转一个设置的**默认值**时要带 `settingsVersion` 迁移：旧存档里那个值是「默认值为旧值时顺带写下的」，
  只改 `DEFAULT_SETTINGS` 对所有点过面板的人都不生效。新增字段（旧存档没有它）则不需要迁移。
