## 1. 意图

用户原话：「我想进一步优化炮塔的炮头和枪管的颜色渲染，现在我用的贴图实在太难看了，
我想把现在炮塔的炮头贴图去掉，改成颜色渲染……都是偏深灰色的有金属光泽的样式，
你参考他们的颜色进行重新着色设计。」

炮管与副武器已在 2026-11-18 改成深灰金属 TSL（`turret-metal.js`）。本轮把**剩下 6 个
装甲部件**（颊舱 / 中央炮座 / 平台中段 / 转台环 / 鼻段 / 裙板）的贴图也去掉，改成
**按面朝向分三档的冷灰金属颜色渲染**，与炮管共用同一套金属材质。

**这不是烘焙新美术资源**：不新增贴图、不新增方块，反而是**删掉**一套贴图管线。
新增的只有产物里一列逐顶点的档位数据（0/1/2）。

## 3. 关键约束：基色 ≠ 最终像素

`turret-metal.js` 的四项叠加（漫反射 + Blinn-Phong 高光 + 环境反射 + 菲涅尔）会把基色
**提亮约 2 倍**，真实游戏还要再过一道 **ACES 色调映射**（`game.js:258`）。
所以**不能直接抄参考图的 hex 当基色**，必须反解。

CPU 参考实现（与 TSL 逐项同构，含 ACES）在正午太阳方向 `[0,0.8,0.6]` 下实测：

| 基色 | 顶面 | +Z 面 | +X 面 | −X 背光 | 底面 |
|---|---|---|---|---|---|
| `#8c949c` | 183,191,201 | 168,175,183 | 138,146,156 | 191,197,203 | 141,148,155 |
| `#767c84` | 158,167,179 | 141,148,158 | 111,118,128 | 167,173,182 | 113,119,128 |
| `#626870` | 129,139,155 | 112,120,132 | 85,92,103 | 138,146,158 | 87,93,102 |
| `#434952`（炮管现值） | 76,88,107 | 64,72,86 | 45,52,63 | 84,94,109 | 47,53,62 |

⇒ 三档基色 `#8c949c` / `#767c84` / `#626870` 落地后的像素范围是 **85~200**，
覆盖参考图的 40~200 区间的中上段，且**保持冷调**（B−R 恒 +15~20）。

**反解依据**：装甲面积加权的三档权重实测 **top 18.9% / side 55.7% / bottom 25.4%**，
令加权均值 ≈ 参考图物体均值 (124,131,137)，解得上述三档（线性空间比例 1.5 : 1 : 0.65）。

## 4. 用户已裁定的两条

### 4.1 明暗层次：按面朝向分三档

参考图的「顶面亮、侧面中、暗面深」是**烘焙进模型的光照**，本仓是实时光照，
需要选一种表达方式。用户选**按面朝向分三档**（而非单一基色靠光照、也非按部件分档）。

分档判据复用既有的 `zoneNyThreshold = 0.85`（`turret-top-parse.mjs`，实测标定值）：

| 档 | 判据（几何法线 ny） | 基色 | 语义 |
|---|---|---|---|
| 0 = top | ny > 0.85 | `#8c949c` | 顶面 / 上表面 |
| 1 = side | \|ny\| ≤ 0.85 | `#767c84` | 侧壁 / 斜面 |
| 2 = bottom | ny < −0.85 | `#626870` | 底面 / 下表面 |

⚠️ **与现有 UV 三区不是同一套语义**，不得互推：UV 区是 `front/side/top`
（按主轴分，底面归 top），色调档是 `top/side/bottom`（按 ny 符号分）。
两者阈值相同但分类不同 —— 实测 nose 的 front 区有 215 面，而色调 side 档有 277 面。

## 5. 目标与非目标

**目标**
- 6 个装甲部件去掉贴图，改三档冷灰金属颜色渲染。
- 炮头（亮）与炮管（暗）保持层次，整体观感对齐参考图的冷灰金属。
- 明暗随太阳方向 / 视角实时变化（复用现有金属材质，不新写着色器）。
- draw call 与现状持平（9 个 InstancedMesh，不增不减）。
- 弹道、玩法数值、放置 / 索敌逻辑、几何形状**零改动**。

**非目标**
- 不改炮管 / 副武器的现有色值（`#434952` / `#353b43`，用户上一轮已验收）。
- 不改 `TURRET_METAL` 的任何材质参数（shininess / specular / env / fresnel / ambient）。
- 不改几何：顶点位置、法线、索引、封口面全部逐位不变。
- 不新增贴图、不新增方块、不改背包图标（炮塔图标是 mc-lite 手工原图，与塔顶渲染无关）。
- 不做 PBR / 不接场景灯光（全场景 unlit 设计，见 `turret-metal.js` 文件头）。

**反目标（做成了也算失败）**
- 整机变成一片均匀灰（失去三档层次）。
- 变成暖色或银白（参考图是冷调深灰，`turret-metal.js` 文件头记着「白色加项 = 塑料感」的反例）。
- 装甲与炮管同色（失去炮头 / 炮管的层次）。
- 几何或弹道发生任何变化。

## 6. 方案

### 6.1 被否决的两条路（记录以免后人重走）

**A. 每档一个 InstancedMesh（9 → 最多 21 个）**
按档拆几何、每档一个 mesh。否决理由：draw call 从 9 涨到最多 21，与「常驻实例池」
预算口径冲突；且同一部件被拆成 3 个 mesh 后，`sync` 的差集驱动 slot 分配、
`__TT_INFO__.meshNames` 等既有契约全部要改，改动面远大于收益。

**B. 顶点色（`vertexColors: true` + `color` 属性）**
把三档颜色直接烘成顶点色。否决理由：`turret-metal.js` 的金属项要**乘基色**
（文件头要点 ①：金属反射被自身基色染色），而 `vertexColors` 是在 `colorNode`
**之后**乘上去的（`three.webgpu.js:21611`）⇒ 高光 / 环境 / 菲涅尔项会用**材质基色**
而不是顶点色去染色，三档的反射色调全错。且颜色被烘死进产物后，改配色要重烘焙。

### 6.2 采纳：逐顶点 `tone` 属性 + TSL `select` 链选基色

产物每部件加一列 `tone: number[]`（逐顶点，值 0/1/2），渲染层建
`Float32BufferAttribute(tone, 1)`，金属材质用 `select` 链按档位选基色 vec3。

**为什么这样最小**：
- 几何 / UV / 法线 / 索引**一个字节都不改**，只追加一列数据 ⇒ 既有的
  「逐面拆顶点 / 切口封口 / UV 零退化 / 各区面数 / 炮口 z / 埋入量」判据全部原样保留。
- 材质仍是**一个** `MeshBasicNodeMaterial` / 部件 ⇒ draw call 不变。
- 三档色值写在 `turret-config.js`（单一权威），改配色**不需要重烘焙**。
- `select` 链与 `materials.js` 的面法线解码同手法（`materials.js:91`），是本仓已验证的
  TSL 写法（避免 GLSL 动态索引常量数组的便携性问题）。

**接线**：`createTurretMetalMaterial` 增加可选参数 `tones: number[]`（三档色值）。
不传时逐位回到现状（炮管 / 副武器走这条），传了则基色由 `attribute('tone')` 选。

### 6.4 `textured` 字段的处置

`textured` 是渲染层贴图 / 纯色分支的唯一依据，也是 `check:data` 的集合关系式判据。
贴图路径删除后它**失去意义**。处置：**删掉 `textured` 字段**，改用
`TURRET_TOP_ARMOR` / `TURRET_TOP_SOLID` 两个集合直接表达「装甲（三档）/ 纯色（单色）」。

- `turret-config.js`：`TURRET_PART_DEFS` 每项去掉 `textured`；装甲项加 `tones: true`
  语义标记？**不加** —— 渲染层直接判 `TURRET_TOP_ARMOR.includes(part)` 会与
  `tools/` 的烘焙侧常量形成跨层依赖（`src/` 不得 import `tools/` 的 node 模块）。
  故在 config 里新增导出 `TURRET_TONED_PARTS`（= 那 6 个部件名），
  `turret-top-parse.mjs` 的 `TURRET_TOP_ARMOR` 改为**从 config 派生**（它是纯函数模块，
  已被浏览器单测 import，可以 import config）。这样集合只有一份权威。
- `check:data` 的「textured 集合关系式」改判「toned 集合关系式」（产物 ↔ config ↔ 烘焙侧三方）。
- 产物 JSON 的 `textured` 字段改名 `toned`。

### 6.5 产物格式变更

`assets/turret/turret-top.json` 每部件：
- 新增 `tone: number[]`（长度 = 顶点数，值 0/1/2）
- `textured: boolean` → `toned: boolean`
- 其余字段（position / normal / uv / index / zone / color）**不变**

⚠️ **UV 保留不删**：虽然不再采样贴图，但 UV 是几何的一部分，删掉会让
「UV 零退化 / 各区面数 / 逐面拆顶点」三条既有内容级判据失去载体，
而那三条正是「切口封口」缺陷的防线。保留 UV 的代价只是产物体积（已在库里的 807KB）。

**指纹**：`turretTopInputFingerprint()` 的参数哈希加入色调阈值与档数 ⇒ 改阈值会触发重烘焙。
**冻结指标**新增逐部件三档顶点数（内容级判据，防「tone 恒 0」这类静默退化）。

## 9. 实施期实测抓到的静默缺陷（已修，记录以免后人重踩）

### 9.1 ⚠️⚠️ `vec3(new THREE.Color(hex))` 在 WebGPU 后端输出纯黑且零报错

**症状**：装甲 6 部件**整片消失**（三档取样点像素全 0），而炮管正常。
**零报错零警告**，且以下判据**全部通过**：tone 属性存在 / 长度 == 顶点数 /
值域 {0,1,2} / 三档顶点数冻结表 / 材质无 map / 材质有 colorNode / 集合关系式 / 指纹。

**定位过程**（systematic-debugging，逐层取证而非猜）：
1. 同一几何同一相机下逐变体读非黑像素数 ⇒ 发现**纯常量色 `vec3(Color)` 也全黑**，
   而 `uniform(Color)` 正常 ⇒ 问题不在 select 链、不在 tone 属性、不在四项叠加。
2. 逐写法对照（非黑像素数 / 中心均值）：

| colorNode 写法 | 非黑像素 | 均值 |
|---|---|---|
| `vec3(new Color(hex))` | **0** | — |
| `vec3(...Color)`（spread） | 10455 | 118,124,132 |
| `vec3(c.r, c.g, c.b)` | 10455 | 118,124,132 |
| `color(hex)` | 10455 | 118,124,132 |
| `uniform(new Color(hex))` | 10455 | 118,124,132 |

3. 读 three 源码定根因：`vec3` 单参数走「转成 vec3」路径，而
   `getValueType(Color)` 返回 **`'color'`** 而不是 `'vec3'`（`three.webgpu.js:1146`）
   ⇒ 转换拿不到分量。节点内省确认：`vec3(Color)` 的内部 ConstNode 仍持有 Color 对象，
   而 `vec3(r,g,b)` 的内部是 Vector3（分量已展开）。

**修法**：显式拆分量 `vec3(c.r, c.g, c.b)`。修后三档像素
**184.6 / 131.4 / 85.1**（炮管 65.2），重复截图逐位相同。

**防回归**：① Tier 4 的「三档均非黑 > 40」直接钉它；② Tier 1 钉可用写法的节点形状；
③ 负向验证 D 把这个写法注回去，确认真红。

### 9.2 两个判据要按新语义改写（不是放宽）

- **「高光随太阳方向变」不能只看 p90**：cheek 是大平面集合，换太阳方向时高光带
  位置滑动但 **p90 几乎不变**（187 → 186.7，差 0.33），而 median 167.7 → 131（差 36.7）。
  barrel 是曲面，p90 差 7。⇒ 取 **median 与 p90 的最大差**，两类几何都有判别力。
- **「关方向光后是均匀色」只对单色部件成立**：barrel 关光后 p90 == median == 74；
  cheek 走三档色调，即使关掉方向光三档基色仍不同（median 124.7 / p90 148，差 23.3）
  —— 那是**正确行为**。装甲侧改钉「max − p90 < 3（无超出三档之上的高光尖）」
  与「p90 − median > 5（三档层次仍在）」。

### 9.4 夹具绕序的假红

### 9.5 ⚠️⚠️ 像素亮度递减对「tone 恒 1」零判别力（负向验证抓到）

**实测**：注入「产物 tone 全部改成 1」后，三档取样点的亮度仍为
**155.97 / 131.38 / 101.86**，相邻差 **24.6 / 29.5**，均 >20
⇒ 「三档亮度递减」判据**仍绿**。

**根因**：三个取样面的**法线不同**（顶面 ny≈0.966 / 侧壁 ny≈0.144 / 底面 ny=−1），
即使基色完全相同，四项叠加的 N·L / 环境反射 / 菲涅尔仍会造出亮度差。
⇒ **亮度差不能证明色调分层生效**。

**修法**：夹具新增 `__TT_INFO__.toneCounts`（从 **GPU 上传的几何属性**读三档分布），
spec 直接钉逐部件冻结表。该判据**不依赖光照**，分类退化即红。

**第二个同根因的盒子**：注入「三档色值全等」后像素亮度判据**也仍绿**（同样的 24.6 / 29.5）。
故另加**同法线单变量对照**：`__TT_SET_TONE__(part, t)` 把**同一个面**的 tone 依次改成 0/1/2，
几何/相机/太阳全不动 ⇒ 唯一变量是档位。实测基线 **184.56 / 155.97 / 131.49**
（差 **28.59 / 24.48**）；注入色值全等后三个读数**逐位相同**（差 0.00）⇒ 真红。

**教训**：多档着色的像素判据必须同时有（a）**不依赖光照的内容级判据**（tone 分布）与
（b）**同法线单变量对照**（只差档位），否则几何法线自带的明暗会同时掩盖
「分类退化」与「色值全等」两类缺陷。
