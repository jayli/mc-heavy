## 1. 目标与验收口径

把当前的「每块沙漠一个孤立高台」升级成一张**新地图地带「高台地带」**：
一块由水池 + 8 座高台（11 个变体里选 8）+ 拱洞 + 紫晶巨柱 + 巨型云组成的固定景观，
按 region 级规则稀疏出现在世界里；**沙漠里的孤立高台彻底下线**。

用户裁定（2026-10-26，三轮问答）：

| 决策点 | 结论 |
|---|---|
| 地带形态 | **region 级整块地带**（不是新 biome、不是全球唯一一处） |
| 高台数量 | ~~11 座~~ → **8 座（随机减 3）**（2026-10-26 第三轮裁定，见 §3 DR-5f） |
| 水池尺寸 | ~~直径 256（半径 128）~~ → **改为直径 180（半径 90）**（2026-10-26 第三轮裁定，见 §3 DR-5f） |
| 高台落位 | **单环 + 抖动环绕水池中心**，每座「长边切向、短边径向」朝心 |
| 高台顶部材质 | 原 `moss` → **`grass`** |
| 台地材质 | **`grass` + `stone` 按确定性噪声镶嵌**，起伏不大 |
| 拱洞 / 巨柱 | `ARC-1~5` = 拱洞，`ARC-6~11` = 紫晶巨柱，**全部 12 个都放** |
| 巨型云 | 素材里 12 个，**随机取 4 个**渲染在地带上空 |
| 空岛 | **地带上空不渲染空岛**；原有云朵（Y=55 单云层 / Y=35 云簇）照常 |
| 水面实现 | **体素水（逻辑层）+ `ocean.js` 平面渲染**，不向 transparent 通道发面 |
| 地带密度 | **每 ~3 个 region 一个** |
| 沙漠孤立高台 | **完全删除**（代码 + 产物 + 门禁环境一并移除） |
| 城市 region | **排除出地带判定**（`isTarnZone(0,0,*) ≡ false`）——城市是全世界唯一地标 |
| 邻域雪原 | **雪原让路**（雪原生成条件加一条「不得与地带圆相交」） |
| 新方块 | **零新增**，全部复用现有的 |

验收判据（Tier 1 + Tier 4 + 数据门）：

1. 同一 seed 同一 region，地带布局两次调用逐字段相同（红线 2）；
2. 地带 region 内 8 座高台全在位、**轴对齐 AABB 互不重叠**、**四角全部落在水池内**，
   且相邻 **AABB 真实间距 ≥ 4 格**。
   ⚠️ **这条判据的口径被用户第六轮裁定改过**（原为「净空隙 ≥ 10 格」）：轴对齐摆放下
   真实间距只有 ~5 格，10 格在「8 座 + 池半径 90」下几何上达不到。完整推演见 DR-7
   「轴对齐的固有代价」。**改这个阈值前先读那一节。**
3. 拱洞 / 巨柱全部落位且不与高台/彼此重叠（同一 AABB 口径）；
4. 水池只有 1 层水体方块，水面视觉由平面渲染承担；
5. 地带 region 内**不出现**金字塔 / 冰封山 / 雪原 / 平地 / 海岛 / 巨树 / 撒布结构 / 空岛；
6. **未受地带影响的** world 内容逐位不变（零回归）。
   ⚠️ 口径必须收窄：**地带 region 的邻域雪原会因让路而消失**（DR-6，约 24%），
   那些雪原就在「地带外」。⇒ 零回归的判据是「非地带 region **且** 其雪原未被地带波及」。
7. 三通道容量零扩容（`bench --check` 不阻断）；
8. `npm run check:data` 的 `[高台地带]` 环节全绿。

⚠️ **「离池心最远点」必须逐角算**：
`max over (sx,sz)∈{±1}² of hypot(ring·cosθ + sx·halfX, ring·sinθ + sz·halfZ)`。
两个常见的错误口径（实测都会让断言失去判别力）：
- ~~`ring + halfX + halfZ`~~ —— 把两个半宽相加，每座多算 10~34 格（实测 L1：119.9 vs 正确 85.9）；
- ~~`ring + min(halfX, halfZ)`~~ —— 那是矩形**边的中点**，不是角。实测 ringR=58 的 L3：
  边中点 80.0 而**角 88.88**，差 **8.9 格** —— 少算这一项就会让高台伸出池外而断言全绿。

### 2.6 环形布置的几何解（历史推演，**算法与参数均已被 DR-7 取代**）

⚠️ **本节整段是历史推演，不要再照它实现。** 它的两个前提都已作废：

1. 「每座高台长边切向、短边径向**朝心**」—— 轴对齐摆放下做不到（DR-7 致命 1）；
2. 「令占角总和 = 2π **反解**环半径 R」—— 反解会让净空隙恰好等于 gap，
   叠加任何抖动就破断言（DR-7 「三轮 A2 修正」第一版）。

历史实测（poolR=128，11 座，gap = 10 格）：

```
可用环半径上界 94，11 座的最大 gap = 17.1 格
  高台最外缘 124 格，距池边 4 格
  L1↔L2 中心距 80.1 → 净空隙 27.1 格
```

**现行定稿（DR-7）**：poolR = **90**、保留 **8 座**、**轴对齐摆放**、
`ringR = 58`（实测标定：59 起 L3 四角出池）、固定 R + 剩余角均分 + 微抖动 0.57°。
实测：四角最远 **88.88** ≤ 90、AABB 最小间距 **5.05**（抖动后最坏 **4.21** ≥ `TARN_GAP` 4）。
⇒ 拱洞（最宽 19 格）**放不进高台之间的缝**，改放池外台地环带（DR-8）；

## 3. 决策记录（DR）

### DR-1 地带是 region 级整块地带，不是 biome

用户裁定。三条实测理由：

1. **容量**：高台环布需要直径 200 级的水池（实测 180 是可落地的尺寸）；biome 块跨度不稳定
   （实测 DESERT 最大 368 / PLAINS p50 只有 8 而最大 3200 / FOREST 400），
   无法保证容纳固定尺寸水池 → 必须加「装不下就退化」的兜底，复杂度换不来收益。
2. **让路**：地带是占满整个 region 的固定景观，必须**压制该 region 的原生地标**。
   biome 叠加做不到这一点（地标在 biome 之上生成）。
3. **确定性**：region 级候选是既有米级范式（scatter / giant-trees / mesa / giant-pyramid
   四路同构），候选在 `computeRegionLayout` 里算一次（DR-13），不新建 Worker（红线 3/8）。

**为什么「每 3 region 一个」而不是「每 region 一个」**：地带占满整个 region 且压制全部地标，
每 region 一个会让金字塔/冰封山/雪原基本消失。实测 ±6 region 169 个，概率 1/3 → 53 个地带（31%）。

### DR-2 地带判定的唯一权威 = `isTarnZone(regionX, regionZ, seed)`

用**粗格哈希**（`seededRandom(regionX, regionZ, seed + TARN_ZONE_SALT) < TARN_ZONE_CHANCE`），
与巨树 `patchChance` 同手法。三个理由（巨树 v1.71 实测沉淀，逐条适用）：

1. ⚠️ **不能用 `noise()` + 标定阈值**：`noise()` 把 seed 直接加进坐标（`gen/noise.js:18`），
   `seed×scale` 相位随 seed 漂移 → 固定阈值跨 seed 不稳。
2. ⚠️ **不能按候选点哈希**：那会得到斑点式零散，而地带必须是整块。
3. 粗格哈希的输入是**整数 region 下标** ⇒ 通过率恒等于 `chance` 且与 seed 无关。

**这是地带的唯一判定入口**（红线 1）：候选层、`apply.js` 的让路、雪原让路、
`pointContext`、巨树 `allowedAt`、海面遮罩全部调它，不得各写一份。
它是 `(rx, rz, seed)` 的纯函数、无状态、跨 region 无缝。

### DR-3 地带中心固定为 region 中心，不做偏移搜索

⚠️ **实测否决了「偏移搜索」**（先试后否，记录理由）：在 region 内网格搜索一个
「避开所有邻域地标圆」的位置，能放下的最大半径实测量：

| seed | min | p10 | p50 | p90 | max | ≥160 的占比 |
|---|---|---|---|---|---|---|
| 12345 | 88 | 96 | 120 | 146 | 156 | **0%** |
| 424242 | 88 | 96 | 112 | 124 | 136 | **0%** |
| 777 | 123 | 128 | 166 | 176 | 183 | 62% |

即：需要半径 160 的地带，**偏移搜索在多数 seed 下根本找不到位置**。故固定中心。

### DR-4 地带半径 160，池半径 90 —— 两个数是耦合的

- 池半径 **90**（直径 180）由 DR-5f 的容量可行性表现标定（128 会超容量 151%）。
- 地带半径 160 = 池半径 90 + 岸带 70（岸带比原来宽：池小了，台地要给足草石镶嵌的空间）。
- **必须显式判据**：`TARN_ZONE_RADIUS ≥ TARN_POOL_RADIUS` 且
  `TARN_ZONE_RADIUS + 2 ≤ REGION_SIZE/2`（= 200）—— 后者保证地带不越 region 边界
  （越界会导致相邻 region 不为它算候选 → 地带半边永久消失，与高台/金字塔踩过的坑同源）。
- **岸带宽度随池半径变**：池 128 → 岸带 32；池 **90** → 岸带 **70**。后者是拱洞的落位空间
  （DR-8 修正：5 个拱洞放池外台地），所以岸带不能压缩。

实测：圆边缘距 region 边界 40 格，安全。

### DR-5 水池走「体素水（逻辑）+ 平面（视觉）」——但体素水必然发面

⚠️ **这一节记录了本设计最重要的一次错误判断与它的纠正**，保留完整推演链，
因为它直接决定了容量预算。

**初始假设**（用户第二轮裁定）：给体素水配一个水面平面，体素水就**不向 transparent
通道发面** → 容量不动。

**实测推翻**：`mesher.js` 的 `WATER_LIKE`（`:408`）只做**同类互剔**（相邻两水格之间的共享面），
对「水格 ↔ 空气格」的边界照样发面。所以只要池面上方是空气，每个水格就发 4 个顶点。
实测 poolR=128 的水格 34,171 → transparent used **150,804**（不是 0）。
⇒ **根本原因**：本仓没有「某个方块不发几何」的开关（除了 `cullMode:'none'`，
而那个是 `collider`，会堵住玩家）。在**零新增方块**的约束下，体素水必然占透明通道。

⇒ **结论**：平面渲染只能改善**观感**（复用现有海面的着色器与波纹），与**容量无关**。
容量问题由 DR-5c/5e 处理。

**⚠️ A3 修正：平面必须抬到池面高度（审阅实测发现的核心缺陷）**

原稿只写了「池圆内一律渲染」的门控，**漏了平面高度**：`ocean.js:243` 的
`plane.position.y = WATER_LEVEL_OFFSET` 是写死的 **−1.5**（= `SEA_Y + 0.5`），
而水池水面在 `plateauY + 0.5 = 2.5`。门控通过后那块 800×800 平面仍躺在 **y=−1.5**，
即池底（y=1）**下方 2.5 格**、被池底挡住 → 玩家看不到任何水面平面。

**实测事实（决定了修法）**：体素水的顶面经 `mesher.js` 的 `WATER_SURFACE_SINK = 0.5`
下沉后，**本身就在 y = 2.5**（水方块占 y∈[2,3) → 顶面 2.5）。也就是说池面几何上
**已经被体素水渲染出来了**，平面只是要贴上同一高度提供波纹与高光。

**用户裁定（2026-10-26 第四轮）：平面抬升到 y=2.5**，做法：

- 用 `material.positionNode`（TSL 顶点阶段）按「该顶点是否落在池圆内」选择高度：
  池内 → `2.5`，池外 → `WATER_LEVEL_OFFSET`（−1.5，保持既有海面**逐位不变**）。
- `positionLocal` 可用（`vendor/three/three.tsl.js` 导出），`positionNode` 被
  `three.webgpu.js` 支持（42 处引用）。
- ⚠️ **抬升后与体素水顶面共面**（都是 2.5）—— 这与既有海面**刻意共面**是同一手法
  （海面平面 −1.5 与体素水顶面 −1.5），靠 `renderOrder = 1` + `depthWrite = false`
  避免 z-fighting。**不要**为了「避让」把平面抬到 2.51 之类，那会与体素水之间露出
  一条缝（俯视时看到水下）。
- ⚠️ **平面仍是 800×800 且跟随相机**（`plane.position.x/z = camera.position`）——
  抬升只改 y，横行跟随逻辑不动。池外的顶点必须留在 −1.5，否则整片海面被抬到 2.5。
- ⚠️ **法线**：既有着色器用固定的 `vec3(0,1,0)` 参与 Fresnel（`ocean.js:205`），
  抬升不改变平面朝向（仍水平），故**法线无需改**。

**平面接线的具体做法（用户裁定：扩展现有平面，不新建 Mesh）**：

- 给 `ocean.js` 的 colorNode 加一组 uniform：`uPoolCenter`（vec4 = 池心 xz + 池半径 + 水面 y）。
- 门控：池圆内一律渲染水面；池外走既有的地形遮罩逻辑（不新增分支）。
- 与城市门控的关系：城市门控 `Discard(inCity)` 是「bounds 内一律不渲」，
  水池门控是它的**反向**（circle 内一律渲）。两者**互斥顺序无关**（地带 region 不可能在城市内，
  DR-6 会保证），但代码上仍按「城市先 Discard、水池再 Discard 池外」写，避免将来判据漂移。
- **CPU 版同步改 `src/render/ocean-mask.js`**（红线 1：判据的 CPU 版与 GPU 版必须同源）。

⚠️ **体素水仍需填充**（不能省）：池底要能站、能挖、能存档，

### DR-5b 零新增方块下「体素水不发面」的两条尝试，都失败

本节保留本设计最重要的一次**错误推演链**（先想错、再实测推翻），因为其中两条
禁令很容易被后人重新提出来。

**尝试一：用 `collider` 当水体载体**
`collider` 是 `cullMode:'none'`（不渲染）但 **`solid:true`** ⇒ 玩家会撞在池水上。
直接否决。

**尝试二：干脆不放 `water`，做「干池」**（池底下沉、水面层是空气、水面全靠平面渲染）
观感上成立，但 `physics.js` 的游泳语义是**显式查 `water` 方块**
（`:74` `getBlockId(...) === idOf('water')`）⇒ 干池里玩家只能**踩在池底走**，不会游泳。
这直接违背「水池」的基本玩法语义，用户不可能接受。

⇒ **两条路都堵死** ⇒ 体素水必须放、放了就必然发面 ⇒ 只能扩 `transparent` 容量（DR-5c/5e）。

### DR-5c 扩大 `CAPACITY.transparent`，并同步复核它是否真的是瓶颈

1. 零新增方块 ⇒ 水面层必然要放 `water` 方块；
2. 放了 `water` ⇒ mesher 必然发面（本仓没有「跳过某个方块的面」的开关，
   而 `WATER_LIKE` 只做同类互剔，见 `mesher.js:408/634`）。

⇒ 于是问题变成**容量**而不是「要不要发面」。各 poolR 的透明通道开销见 DR-5e 的精确权衡表。

⚠️ **用户在第二轮问答里选了「体素水 + 平面渲染」**，其潜台动因是「不占 transparent 通道」。
DR-5/5b/5d 的推演与实测证明那个收益在零新增方块约束下**拿不到**，
**该选择的容量部分因此退回为 DR-5c**（观感部分仍然保留：平面渲染照做）。

### DR-5d 水面视觉走平面，体素水只作逻辑层

### DR-7 高台环形布置：轴对齐摆放 + 固定环半径 + 剩余角均分 + 微抖动

#### ⚠️ 前置：高台是**轴对齐**摆放，不旋转（致命 1 的最终裁定）

**实测事实**：`rasterizeStructure`（`structure-json.js:134`）是**轴对齐**写入：

```javascript
setBlock(Math.floor(x + b.x), Math.floor(y + b.y - 1), Math.floor(z + b.z), b.type, b.direction || 0);
```

`b.direction` 是**逐格方块的 0–3 朝向元数据**（给台阶/门用），**旋转不了整个结构**。
原设计写的「高台长边切向、短边径向朝心」在本仓**没有实现机制**。

**曾试过的方案 A（给 `rasterizeStructure` 加 4 向旋转）已被实测否决**，理由是一条
几何矛盾：`orientation = (w ≤ d) ? 0 : 1` 这类档位公式**只依赖素材的 w/d，与高台在环上的
角度 θ 无关**；而「短边沿径向」要求每座对齐**各自的** θ。一个与 θ 无关的档位不可能让
8 座都对齐各自的径向。实测后果（ringR=64）：**L3 的四角最远 94.44 > 池半径 90**，
仍伸出池外 4.44 格；而 spec 曾声称的 `hypot(ringR+径向, 切向) = 89.29` 是**按「已转到
短边严格沿径向」算的，轴对齐机制达不到那个姿态**。

**用户裁定（2026-10-26 第六轮）：方案 1 —— 接受轴对齐，缩 ringR 到 58。**

⇒ **不新增旋转机制**（原 Task 12 已删除）。8 座以素材原始朝向摆放，环半径缩到
「最远角落回池内」的上限。代价见下面「轴对齐的固有代价」。

#### 轴对齐的固有代价（用户已知悉并裁定接受）

放弃旋转后，**「净空隙 ≥ 10」这条原验收判据在几何上达不到**，三条路都试过：

| 尝试 | 实测结果 |
|---|---|
| 缩 ringR | ringR 越大高台越伸出池外（ringR=60 时 L3 最远角已 90.73 > 90）；**ringR=58 是「全在池内」的上限**，此时 AABB 最小间距 5.05 |
| 重排环上顺序（大小座交替） | 最好只到 **5.36**（`L3,L9,L5,L10,L6,L11,L4,L8`），仍 < 10 |
| 加大抖动 | 任何角度抖动都让相邻两角**更近**，间距 5 时抖动预算几乎为 0 |

根因：旧的「净空隙 ≥ 10」是按「长边切向朝心」的**旋转假设**定的（口径 = 弦长 − 切向半宽）。
放弃旋转后**这个口径本身失效**，轴对齐下的真实间距就是 ~5 格。

**用户裁定（2026-10-26 第六轮）：验收判据改为「AABB 真实间距 ≥ 4 格」+ 微抖动 0.57°。**
既保证高台不贴死，布局又有一点自然错落，不至于完全机械等距。

#### 算法

1. **每座高台的占地是轴对齐矩形**：`halfX = width/2`、`halfZ = depth/2`（世界 X/Z 轴，
   与环上角度无关）。布局层记录这两个值，**不再有 `radialHalf`/`tangentialHalf`**
   （那是旋转假设下的概念，轴对齐下无意义）。
2. **占角用保守的角向半宽**：`占角ᵢ = 2·asin(max(halfXᵢ, halfZᵢ) / ringR)`。
   ⚠️ 这只是**排序用的保守角向度量**（保证 8 座在环上不打架），**不是**真实 AABB 占地；
   真实间距由第 5 步的 AABB 判据单独算。
3. **环半径取「最远角落回池内」的上限**：`ringR = 58`（实测标定，见下表）。
   ⚠️ **不要写成 `TARN_POOL_RADIUS − max(half) − 4` 这类公式** —— 轴对齐下最远角是
   `max over 四角 of hypot(ringR·cosθ ± halfX, ringR·sinθ ± halfZ)`，与 θ 有关，
   没有闭式解。58 是对定稿组合穷举实测出的上界（59 起 L3 出池）。
4. **剩余角度均分给 8 个缝**：`缝角 = (2π − Σ占角) / 8`。
5. **微抖动**：每缝偏移取 `(rand−0.5)·2·jitterMax` 后**减去均值**（零和，保证 Σ缝角守恒）。
   `jitterMax = jmMax × 0.8`，`jmMax` 是二分出的「AABB 真实间距仍 ≥ `TARN_GAP`」的最大值。
   ⚠️ **`TARN_GAP` 已从 10 改为 4**（用户第六轮裁定，理由见上「固有代价」）。
   实测 `jmMax = 0.71°` → `jitterMax = 0.57°`（环上约 0.6 格位移）。
   ⚠️ **不要把 `jitterMax` 写成 `缝角/2`**：实测 `缝角/2 = 7.62°` 会让相邻高台**直接重叠**
   （AABB 距离变负）。

#### 紫晶柱内环半径 = 20（轴对齐后重标，原公式已失效）

原稿的公式 `max(12, ringR − max(radialHalf) − 30)` 在 ringR=58 下算出 **12**，
而实测内环 12 时 **7 个紫晶柱互相重叠 3 对**（最小距 **−1.86**）—— 环太小，
12×11 / 11×10 / 10×13 这些占地在周长 2π×12 ≈ 75 格上排不下 7 个。

穷举实测（300 次抖动抽样，高台环 ±0.57° + 紫晶柱环 ±3°）：

| 内环 R | 紫晶柱互最小距 | vs 高台最小距 | 重叠 | 判定 |
|---|---|---|---|---|
| 12（原公式） | **−1.86** | 12.80 | 3 对 | ❌ |
| 14 | −0.50 | 10.80 | 1 对 | ❌ |
| 16 | 0.86 | 8.80 | 0 | ⚠️ 贴死 |
| 18 | 0.93 | 6.52 | 0 | ⚠️ 贴死 |
| **20** | **2.14** | **4.53** | **0** | ✅ **定稿** |

#### B3 修正：重叠判据必须用真实 AABB，不是外接圆

原稿的「外接圆保守判」（中心距 ≥ 两半对角和）与内环公式**数学上不相容**：实测
内环半径 12、`ringR`=55.93 → 中心距 43.93，而外接圆判据要求 ≥ 53.48 → **断言必红**。
但真实 AABB 其实**不重叠**。

⇒ **判据改为轴对齐 AABB 相交**（轴对齐下就是逐轴比较，**不需要 SAT** ——
原稿写的「按各自旋转角投影后判」是旋转假设的残留，轴对齐下没有旋转角）。
这条同时适用于「拱洞 vs 高台」「拱洞 vs 拱洞」「紫晶柱 vs 高台」「紫晶柱 vs 紫晶柱」
四类检查。

⚠️ **间距口径统一为「AABB 真实最短距离」**（与 DR-7 同一个函数）：两轴分离量都 > 0 时
取 `hypot(dx, dz)`，否则取正的那个；两者都 < 0 即重叠。**不要用外接圆近似** ——
它会把「实际不重叠」判成重叠（假失败），也会把「实际重叠」判成不重叠（漏报）。

#### 拱洞落台地的约束

拱洞占地最宽 19 格、最深 36 格（轴对齐，不旋转）。台地环带内缘 90、外缘 160
→ 可用宽度 70 格。**5 个拱洞沿中线半径 125 等角分布**时，相邻两座的 AABB 最小间距
实测 **114.94 格**，远大于最大的拱洞跨度 36 —— 间距充裕。

⚠️ **拱洞必须整块落在台地环带内**（实现时断言，逐角算）：
- 最近角 **111.66** > 池半径 90 ✅（不会压进水池）
- 最远角 **138.94** < 地带半径 160 ✅（不会压出台地边缘）

⚠️ 这两条必须**逐角**算（`hypot(R·cosθ ± halfX, R·sinθ ± halfZ)` 取极值），
不能只看 `R ± max(half)` —— 后者在 θ 接近 45° 时会少算。

### DR-9 台地地形：草 + 石噪声镶嵌，起伏不大

- 台地 = 地带圆内、水池圆外的环带（半径 **90**~160）。
- 高度：`plateauY` 是常量（不随位置变），起伏来自**方块镶嵌**而不是高度 ——
  用户明确说「高低起伏不是很大」。
- 材质：`seededRandom(wx, wz, seed + TARN_TERRAIN_SALT)` 决定 `grass` / `stone`，
  阈值取 `0.5`（各半），并用**低频噪声**做「成片」而不是逐格斑点
  （逐格随机会读成噪点，观感是「花屏」）。
- **池底（半径 ≤ 90）**：`grass` 为主（水下草底），边缘 8 格用 `stone` 做过渡。

⚠️ **必须做「成片」而不是「逐格随机」**：实测教训见巨树 `patchChance` ——
逐点独立抽签会产生斑点式零散。台地镶嵌用 `noise(wx, wz, seed + SALT, scale)` 取阈值，
scale 标定到「每片 8~16 格」。

### DR-10 巨型云：素材 12 个里确定性取 4 个，放在地带上空

## 7. 已知盲区与风险

1. **✅ 已裁定（2026-10-26 第三轮）：不扩容。** 代价是池半径 128 → **90**、高台 11 → **8**
   （DR-5f 的穷举实测：128 必超容量 151%，而 110 下没有任何保留座数能装进现容量）。
   最终 landed 在 reserved **98,235 = 现容量 78.6%**（DR-7 定稿组合 + 紫晶柱占地 560 格
   + `glass_block` 180 格均已计入），留 21.4% 余量。
2. **⚠️ 城市与地带的互斥**：`CITY_REGION` 固定 [0,0]。若该 region 恰好掷到地带，
   城市会消失。**必须显式把 `CITY_REGION` 排除在地带判定之外**（`isTarnZone` 对 [0,0] 恒 false）。
3. **35 个 JSON 的预载成本未实测**：既有教训是 7 个撒布 JSON 让 genP95 +30%。
   实施第一步必须先测「地带 region 首个 GEN 的 genP95」，超 8ms 就要做分帧或合并产物。
4. **存档**：旧高台会在该 region 重生成时消失（用户已接受）。
5. **`.bp` 文件不入库**：它们只是「给分量起名 + 缩略图判族」的工具，不是烘焙输入。
   烘焙读 `.schem`，因此 `.bp` 不需要进仓。
6. **35 个产物 JSON 总体积约 3.78 MB**（按现有产物实测的 9.83 B/格估算）。
   这些是**运行期资源**，只在地带 region 惰性预载。仍建议先实测首次加载耗时。
7. **紫晶柱的 180 格 `glass_block` 走 transparent** —— 与 DR-7 的容量合并计算，
   不要各算各的。
8. **⚠️ 轴对齐摆放的观感代价（用户第六轮裁定接受）**：8 座高台朝向一致（都轴对齐），
   不朝心；相邻真实间距只有 ~5 格（比旋转假设下的 18 格窄）。若实玩后觉得「太挤/太机械」，
   可选方向：减座数、换更小的变体、或扩池 —— 但都要重跑 DR-7 的穷举表。
