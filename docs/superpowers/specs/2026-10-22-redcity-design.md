## 2. 模型实测分析（决定方案的硬数据）

全部数字来自对 schematic 的逐方块解析（`Blocks` + `Data` 各 38,286,592 字节，
尺寸 347×431×256，`materials = Alpha`）。

### 2.1 这是一座**浮空岛**，不是地面建筑群

这是本次设计最关键的事实，它推翻了「在地面上盖一批房子」的直觉：

| 类别 | 方块数 | 说明 |
|---|---|---|
| **岛体（skin）** | **1,265,807** | v1.0 口径。**v1.1 注**：skin 的判定清单文档未给出，评审无法复现该数字——烘焙脚本必须显式声明（§13.5.4）。总非空气方块实测 **1,445,290** = 屏障 `barrier`(166) 17,804（不可见，烘焙丢弃）+ 1,427,486 | 
| 岛体主材（**v1.1 勘误**） | 实测 | light gray wool（`35:8`，是**浅灰**不是 white）402,188 + `252` concrete_powder **381,256**（其中 `252:8` 376,841）+ clay(`82`) 205,259 + stone(`1:*`) 194,476 + `251` concrete **16,142**（`251:6` 粉 13,520 / `251:15` 黑 1,926 / `251:8` 693）。v1.0 把 251/252 的数字写反了 |
| **地上建筑与装饰** | **161,679** | 塔、树、庭园、道具、玻璃、山石表层 |
| 最高点 / 最低点 | y=148 / y=36（v1.1 勘误，v1.0 写 37） | **没有任何一列触底**（y=0 处零方块） |

```

y45-54  footprint 177×234
y55-64  footprint 191×260
y65-74  footprint 200×262   ← 最宽
y75-84  footprint 198×261
```

### 2.3 岛面高差

岛体表层（skin 顶面）的高差分布：

```
p2 = 73  p50 = 88  p98 = 132   →  p2~p98 落差 59 格（全量 91 格）
```

59 格落差如果原样落地，就是「一进 RedCity 先爬 59 格台阶」—— 与 R4 直接冲突。
故需**竖向压缩**（§6.2）。

### 2.4 拱洞与挑檐：39.4% 的列有多层表面

实测 14,545 个列（占所有有表面列的 **39.4%**）存在**不止一层** skin 表面
（`isAir(x, y+1, z)` 成立的 skin 方块有多个 y）。这是拱门、挑檐、悬空台阶造成的。

**这条数据直接决定投影算法**：如果只取「最上面那层表面」，所有拱洞都会消失
（拱洞的上方是桥面，取最上面就会把拱洞填成实心）。必须保留**每个表面的下方 K 层**
（§6.1）。

> ⚠️ v1.1：评审用显式 skin 清单 +「skin 方块且上方为空气」重算，多表面列占比约 **14%**（3,746 / 26,691），
> 与 39.4% 的差异来自 skin 与「表面」的口径（是否把室内地板、雪层等算入）。口径必须在烘焙脚本里固定并写进
> `redcity.json`（§13.5.4）。另外「每个表面往下 K 层」的字面规则会把 skin 材质的竖直结构掏空，见 §13.5.4。

### 2.5 与 City 的距离

City 核心建筑范围实测（seed=12345）：x[174,391] z[-15,212]。
RedCity 紧贴 City 东界（x = city.maxX + 6）时，两者核心区中心距约 **290 格**，
但**边缘距仅约 160 格** → 在 vd=8（272 格视距）下**可以同屏可见**。
§7.3 给出同屏最坏情况的实测顶点数，结论是仍有余量。

> ⚠️ v1.1 勘误：① 落点 `city.maxX + GAP` 用的是 City 的 **bounds**（seed=12345：x[0,566] z[-166,400]，halfSize 283），
> 远大于「核心建筑范围」；离最近的 City 建筑约 170~190 格、中心距约 414 格（不是 160 / 290）。
> ② vd=8 的半径是 8 个 column = **128 格**（272 格是窗口全宽）。City 建筑与 RedCity 在 vd=8 下**不会同屏**——
> §7.3「City + RedCity 最坏同屏」窗口内与之相交的 City 建筑数为 **0**（建筑最东 x≤399，窗口西缘 x=432）。
> vd=12/16 才可能同屏，且预算未标定（设计文档 §4.10：视距 16 之前须先做 LOD）。

## 4. 总体架构

### 4.1 数据流（复用既有管线，不新增持久化路径）

> ⚠️ v1.1：下图的「阶段 2.8」位置与「随 layouts 下发」作废。核心区的地面在阶段 1 整形、内容在阶段 2.9（空中结构之后）写入；
> `redCity` 随**每个** GEN 任务全局下发；产物是 `redcity.json`（D8），由主线程 fetch 一次后把原文 broadcast 给 Worker。见 §13.3 / §14.5。

```
schematic ──(离线烘焙 tools/bake-redcity.mjs)──> assets/redcity/redcity.bin
                                                        │
                              (Worker: fetch + 模块级缓存，同 structure-json.js)
                                                        ▼
  computeRegionLayout(regionX, regionZ, seed)      ← region 级，确定性
      └─ city 存在时追加 redCity 布局（origin/size/baseY）
                                                        │
                                                        ▼
  applyStructuresToColumn(column, seed, registry, layouts)   ← GEN 阶段
      └─ 阶段 2.8（撒布之后、空中结构之前）：写 RedCity 覆盖层
                                                        │
                                                        ▼
                              fillColumn 地形 → RedCity 覆盖 → 光照 → mesh
```

**为什么走 GEN 覆盖层而不是运行时实体**：RedCity 是**静态地标**（玩家不能搬动，
不刷怪、不射击），按 M9 创造台沉淀的约束「无行为的方块装置别建 controller」，
它只需要「GEN 阶段的确定性写入 + 玩家的 edits diff」。这保证：
- 符合红线 2（无预生成，chunk 进加载半径才算，seed 确定性）；
- 符合红线 3（生成在 Worker）；
- 无新增持久层（玩家改了哪格照旧进 edits store）。

### 4.2 落点计算（`region-config.js` + `redcity-layout.js`）

> ⚠️ v1.1：**整节取代，见 §13.3。** 冲突检测漏了邻区地标（含邻区 0/80 可用）；`redCity` 只挂 region(0,0) 则只能投递到
> x≤799（东侧 39/80 个 seed 越界）；矩形 26–48% 是水域；`SCATTER_FOOTPRINT` 是撒布结构表，不是地标尺寸
> （地标尺寸是 `PYRAMID_SIZE` 等常量）。D5 之后不再有冲突回退。

```js
// 候选：东侧优先，冲突回退西侧（用户决策 D3）
REDCITY_SIDE_ORDER = ['east', 'west'];
REDCITY_GAP = 6;                 // 与 City bounds 的间隙（格）
REDCITY_SIZE = { X: 250, Z: 289 };  // 烘焙产物实测包围盒，写进 redcity.json
```

落点：
- **东侧**：`minX = city.maxX + REDCITY_GAP`，`minZ = round(city.centerZ - 289/2)`
- **西侧**：`maxX = city.minX - REDCITY_GAP`，`minZ` 同上

**冲突检测**（与既有地标，用同 `SCATTER_FOOTPRINT` 的 AABB 口径）：
与 `pyramid` / `frozenMountain` / `snowLand` / `plainLand` / `island` 的占地 AABB 求交。
东侧冲突 → 试西侧 → 两侧都冲突 → **本 region 不生成 RedCity**（不强行挤压，避免与地标打架）。
实测 6 个 seed：东侧 5/6 可用，seed=1 东侧撞雪原但西侧可用 → 覆盖率 6/6。

> ⚠️ **RedCity 只属于 City 所在的 region**（同 `buildCityLayout` 的 `CITY_REGION` 口径，
> 全世界唯一）。它的 bounds 可能跨 region 边界（250 宽 + gap 6 → 若 City 已在东边界附近
> 会溢出）→ 由 `neighborRegionKeys` 的查询域机制自然投递，与 city scatter 的
> 「跨区候选不按 region 裁剪」同一手法（`scatter.js` 口径差异①）。

### 4.3 地形衔接（R4 的实现）

> ⚠️ v1.1：**整节取代，见 §13.4。** 岛轮廓不是矩形（31% 空列）、基准高度未定义、只有填方没有挖方、水体未处理。

RedCity 覆盖层**不是**「把一块地推平再盖」，而是分三层：

| 层 | 内容 | 处理 |
|---|---|---|
| 内部（核心区） | 模型投影后的地表与建筑 | 完全按烘焙数据写；地表由模型自己的表层方块承担 |
| 过渡环（外圈 `REDCITY_TRANSITION = 24` 格） | 模型地表 → 自然地形 | 逐点混合，见 §6.3 |
| 外侧 | 自然地形 | 不动 |

过渡环的混合公式与 City 的 `getCityFinalSurfaceY` 同构（台阶式钳制，每
`TERRACE_WIDTH=3` 格允许 1 格高差），复用其思路但**独立实现**
（City 的公式耦合 `nearbyLandmark` 与 `CITY_MIN_SURFACE_Y`，直接复用会把
海平面下限 +1 的约束带进 RedCity）。

## 5. 烘焙产物与方块映射

### 5.1 离线烘焙（`npm run redcity`）

> ⚠️ v1.1：产物需增补 `ground` 高度场、`spawn`、skin 清单与映射覆盖声明（§13.4.2 / §13.5.4 / §13.6.1）。另：本节「291 KB」
> 与格式描述对不上（仅逐列头 72,250×6 B 就是 433 KB），体积以实际烘焙产物为准。

新增 `tools/bake-redcity.mjs`，输入 schematic，输出 `assets/redcity/redcity.bin`
+ `assets/redcity/redcity.json`（尺寸 + 输入指纹）。

**为什么离线烘焙而不是运行时解析 schematic**：
- schematic 是 76MB 解压体，浏览器端解析要点内存与时间（首屏不可接受）；
- 烘焙产物实测仅 **291 KB**（gzip **55.6 KB**）—— 按 M6/M8 沉淀的「离线烘焙产物 +
  输入指纹门禁」手法，代价极低；
- 符合既有 `npm run icons` / `npm run zombie` / `npm run turret` / `npm run nightsky`
  四个先例（红线：离线产物须有指纹门禁防静默过期）。

**产物格式**（列式 RLE，实测 72,250 列 / 51,284 run / 最多 14 run 每列）：

```
magic 'RCY1' (4B)
width u16, length u16           // 250, 289
dyMin i16, dyMax i16            // -8 .. 140（相对压缩后地表的行号域）
paletteCount u16
runCount u32
per-column: { ox u16, oz u16, runCount u16 },  runCount 个 { begin i16, len u8, pal u8 }
palette: paletteCount 个 mc-heavy 方块名（UTF-8 长度前缀）
```

- `begin` 是**相对该列压缩后地表**的行号 → 天然实现 §6.2 的竖直压缩
  （烘焙时算好，运行时零缩放运算）；
- `pal u8` → 上限 255 种，实测需要 **83 种**（留有充足余量）；
- 指纹进 `redcity.json`，`check:data` 加 `[RedCity]` 环节比对（同夜景/丧尸头/炮塔装甲手法）。

### 5.4 玻璃的关键取舍：映射为**不透明白**

> ⚠️ v1.1：**整节作废**（D6：改用 `glass_block`，§13.5.1）。本节的机理描述也写反了——`mesher.js:475` 对 `cullMode >= 2`
> （含 glass、water）**会剔除同类相邻面**（合成 6×6×6 玻璃块实测 864 顶点，而非 5184）；「互不剔除」是 cutout 通道的性质。

这是**有意偏离模型**的一项，必须先讲清楚：

- 模型里 112,047 块玻璃/玻璃板，实测 43.3% 暴露在空气中，构成大量建筑的**玻璃墙**；
- mc-heavy 的 `glass_block` 走 **transparent 通道**，同类型相邻**互不剔除**
  （`mesher.js:475` 的 `cullMode >= 2` 分支）→ 一整面玻璃墙的每个方块 6 个面全出；
- 实测：保留玻璃 → transparent 通道 **171,472** 顶点；而该通道的冻结上限只有
  **125,000**（当前世界峰值仅 16,000）→ **直接超预算 37%**；
- 映射成 `light_gray_cloth`（不透明白）后 → transparent 通道 **117,496**，回到预算内，
  且视觉上是「白墙 + 窗框」，与模型白墙为主的观感一致。

**结论**：玻璃统一映射为 `light_gray_cloth`。代价是失去通透感；收益是守住
transparent 通道预算（红线 5 的合批容量）。这一点会在验收时明确告知用户，
若观感不可接受，备选方案是「只把**主要 9 座塔**的窗格映射回 glass_block」
（预估 ~20K 顶点，仍在预算内）—— 留作后续微调项。

## 6. 投影算法（D1 的核心）

### 6.1 保留哪些 skin 层

> ⚠️ v1.1：「每个表面往下 K 层」的字面规则会把 skin 材质的竖直结构（塔基、墙、悬挑）掏空成薄壳，而空腔内表面照常被 mesher 出面
> （不可见却占顶点）。保留规则改为「地面往下 K 层 + 地面以上全部」，并要求烘焙脚本显式声明 skin 清单与「地面」定义，见 §13.5.4。

对每个模型列 `(ox, oz)`：

1. 找出**全部** skin 表面 `ys[]` —— 满足「该格是 skin 材料」且「上方是空气」的所有 y
   （§2.4：39.4% 的列有多个）。
2. 保留 `ys[]` 中**每个 y 往下 K 层**的 skin 方格（K = 2）。
   → 这一步保住拱洞（拱顶下方的"桥面"作为独立表面被保留）、挑檐、悬空台阶。
3. 表面**之上**的非 skin 方块（建筑、树、玻璃、装饰）**无条件全部保留**（1:1）。
4. 其余一切（岛体内部、表层以下的非 skin 残留如岩浆/水）**丢弃**。

实测 K=2 的保留量：**254,344 块**（skin 121,980 + 建筑 132,364）。

> K 的取值依据：K=1 时挑檐底部会露空（挑檐只有 1 层厚，K=1 保住了它，但拱洞的
> 下沿会因为"下移一格后邻列没有表面"而出现 1 格空洞）；K=3 只多留 58,554 块
> 但几何成本涨 5%。**K=2 是几何成本与形状保真度的平衡点**（实测量化，非拍脑袋）。

### 6.2 竖直压缩（R4 的关键）

> ⚠️ v1.1：逐列压缩会让跨列的建筑错位（塔座周围地面起伏 8–23 格 → 相对错位 5–15 格）；建筑须按连通体**刚性平移**并平台化脚下地面，
> 见 §13.4.4。`RELIEF` 对预算几乎无影响（0.2~0.5 下 opaque 占比 108~109%），只是观感旋钮。

对每列，定义压缩后的表面高度：

```
sC = round( sMed + (s - sMed) × RELIEF_SCALE )
```

- `sMed` = 全体 skin 表面高度的中位数（实测 88）
- `RELIEF_SCALE = 0.34` → 59 格落差压缩到 **20 格**
- 所有方块的行号由 `dy = y - sC` 决定 → **烘焙时算好**，运行时零缩放运算

> RELIEF_SCALE 的取值依据：0.34 使 RedCity 内部的台阶梯度落在「每 3 格降 1 格」
> 附近（与 City 的 `CITY_TERRACE_WIDTH = 3` 同量级手感），同时保住 9 座塔的相对高差
> （最高的塔仍在 +50 以上）。取 1/3 而非更小，是为了不让宝塔的层叠收分被压扁。

### 6.3 过渡环混合

> ⚠️ v1.1：**取代，见 §13.4.1–§13.4.3。** 原公式里的 `t` 定义后未被使用；24 格环只能消化 8 格高差，必须先把核心边缘高度钉在 `baseY`
> （岛地面下限钳到 -5 + 周边中位数策略），否则 |Δ|>8 处在核心边缘留下断崖。

对落在过渡环 `[coreMin - T, coreMin)` / `(coreMax, coreMax + T]` 的点：

```
T = 24 格（约 1.5 个 chunk）
t = 到核心区边界的距离 / T          // 0（边界）.. 1（环外沿）
targetH = 该点的 RedCity 投影地表高度（由最近核心列取样）
naturalH = generateHeight(wx, wz, seed)
maxDelta = floor((T - 距离) / 3)     // 台阶式：每 3 格允许 1 格高差
blended = naturalH + clamp(targetH - naturalH, -maxDelta, +maxDelta)
```

**为什么不直接做法向量插值**：mc-heavy 的地表是体素，斜插值会造出大量
1 格厚的"瓦片"，mesher 面数与穿帮都变差。台阶式钳制是既有 City 已采用的
手法（`getCityFinalSurfaceY`），复用其思路保持一致手感。

### 6.4 基底填充（防悬空）

> ⚠️ v1.1：**取代，见 §13.4.3 / §13.4.5。** 改为从地面实心填到基岩（同时消掉 rect 下的洞穴），并新增挖方与水体补实；
> 「超过 `REDCITY_FILL_MAX` 改由斜坡过渡环接管」在核心区内部不成立（环只在矩形外圈）。

投影后的 RedCity 是**浮在地形之上的一层壳**（K=2 层的 skin + 建筑）。
在地形低于 RedCity 地表的地方（挖方区），需要从 RedCity 底面往下填到地形，
否则玩家会看到悬空的壳。

填充材料 = **模型自己的 skin 主材**（`light_gray_cloth` / `clay`），
不是 `stone` —— 与 `generateCity` 的「补实材料须用城市岩石材料」同一理由：
让玩家挖下去看到的还是同一套材质。填充深度上限 `REDCITY_FILL_MAX = 12`
（避免在山谷处填出 40 格高的柱子，超过则改为斜坡过渡环接管）。

## 8. 出生点改造

> ⚠️ v1.1：**整节取代，见 §13.6。** §8.3「旧存档沿用旧出生点」做不到：`game.js:573-574` 无条件重算出生点，`hadMeta` 只管 seed，
> `meta.spawn` 只写不读（部分路径写的还是 `[8,8]` 占位）；且玩家位置不持久化。D7 已决定弃用旧存档。
> §8.2 的「向外螺旋搜索」与「保留 `findSpawnY`」也作废：严格判据下最近候选在 22.6 格外，应烘焙选定。

### 8.1 现状

`game.js:573` 的出生点逻辑：

```js
const citySpawn = getCitySpawnPoint(regionLayout.city);
this.spawnX = citySpawn.x; this.spawnZ = citySpawn.z;
...
this.spawnY = findSpawnY(this.world, this.spawnX, this.spawnZ);
```

`findSpawnY` 从世界顶向下找首个非空气方块，返回 +1 —— 它**会把空中结构当出生点**
（既有活跃约束已记录该缺陷）。

### 8.2 改造：出生点优先 RedCity

新增纯函数 `getRedCitySpawnPoint(redCity)`（`redcity-layout.js`，Worker 同构）：
从模型中心向外螺旋搜索，判据 =「该格上方 2 格是空气」+「该格自己是 solid」。

实测模型中心 `(176, 210)` 周围 **3.2 格内**就有满足条件的空地
（`(178, 211)`，地表 y=111），故搜索半径 16 格足够。

> ⚠️ **搜索必须同时检查「上方 2 格空气」与「脚下方块 solid」，只看其一都会出问题**：
> 只看空气 → 可能选中拱洞里（下方是悬空的挑檐）；只看 solid → 可能选中实心山体内部
> （出生后卡在方块里）。这两条正是既有活跃约束「写断言前必须先在真实数据上跑一次」
> 的直接应用 —— 判据来自实测 `(178,211)` 的逐格检查，不是想象。

`game.js` 改为：

```js
const redCitySpawn = regionLayout.redCity ? getRedCitySpawnPoint(regionLayout.redCity) : null;
const citySpawn = getCitySpawnPoint(regionLayout.city);
this.spawnX = redCitySpawn?.x ?? citySpawn.x;
this.spawnZ = redCitySpawn?.z ?? citySpawn.z;
```

**保留 `findSpawnY` 不动**（它仍有「从顶往下找」的缺陷，但那是既有行为，
本次不扩大改动面；RedCity 中心的空地本身就会让 `findSpawnY` 找到正确高度）。
若验收时发现出生点高度不对（例如落到樱花树冠上），再单独修 —— 届时用
「向下扫真实地面而非从顶向下」的修法（既有活跃约束已记录该教训）。

### 8.3 存档兼容

`meta.spawn` 已持久化（`game.js:311/576`）。切换后：
- **新存档**：写入 RedCity 中心；
- **旧存档**：`hadMeta` 为真时沿用旧 spawn（`game.js:306` 的 `meta.seed` 路径）

  「重置出生点」动作 —— **本次不做**（非目标）。

### 13.3 选址与生成优先级（取代 §4.2）

#### 13.3.1 落点：固定东侧，永远生成

```js
// 常量唯一权威 = region-config.js（红线 1：烘焙产物记录其值，check:data 比对）
REDCITY_SIZE       = { X: 250, Z: 289 }   // 烘焙包围盒（redcity.json 记录）
REDCITY_TRANSITION = 24                   // 过渡环宽度 W
REDCITY_GAP        = 24                   // = W：过渡环恰好填满 City bounds 与核心区之间的间隙
core.minX = city.maxX + 1 + REDCITY_GAP   // City bounds 是闭区间
core.minZ = round(city.centerZ - REDCITY_SIZE.Z / 2)
influence = core ⊕ REDCITY_TRANSITION     // 影响域：地形整形 / 吞并 / 避让 / 水面门控的统一范围
```

- 删除「冲突检测 / 回退西侧 / 两侧都冲突则不生成」：D5 之后不存在冲突。`computeRegionLayout` 对 region(0,0) 追加
  `redCity: { core, influence, baseY, size }`，其余 region 为 `null`（与 `city` 同口径：全世界唯一）。
- GAP 从 6 改为 24：过渡环若伸进 City bounds，会与 City 自己的内缘过渡（`getCityFinalSurfaceY`，32 格）叠加；
  GAP = W 使两套过渡首尾相接、互不干涉。City 边缘处地表恒等于自然高度（`edgeDistance=0` → `maxDelta=0`），环的外缘也等于自然高度，天然连续。

#### 13.3.2 `redCity` 全局下发（不走 3×3 查询域）

3×3 查询域只让世界 x,z∈[-400,799] 的 column 看到 region(0,0) 的布局。〔实测〕seed 1–80：v1.0 几何（GAP=6）下东侧矩形在 39/80 个 seed 越界；
**v1.1 几何（GAP=24）下 core 越界 54/80、影响域越界 60/80**（越界宽度中位 64、最大 126 格；seed=12345 影响域 x 到 864，越界 65 格）。
越界部分会被**静默截成一条直边**——这不是边角情况，而是多数世界的常态。City 全世界唯一且 bounds < 800 才碰巧不越界，RedCity 不能依赖这个巧合。

- `StructureIndex` 新增 `redCity()`（= `_layouts.get('0,0')?.redCity ?? null`）；`Scheduler` 的 `gen` 任务 payload 新增 `redCity`（约 200 B）；
  `world-worker.js` 的 `gen` 把它传给 `applyStructuresToColumn(column, seed, registry, layouts, redCity)`（新增可选第 5 参，缺省 `null`）。
- `readyForColumn` / `ensureForColumn` 额外要求 region(0,0) 布局就绪（启动路径本来就先 `waitForRegion(0,0)`，`game.js:568`）。
  否则会出现「早到的 column 不带 RedCity 生成」的永久不一致。
- 不把 region(0,0) 的整个布局塞进每个任务：它含 City 撒布 `Int32Array`，structured clone 开销不值。
- ⚠️ v1.2 实现口径：`StructureIndex._requiredKeys(cx, cz) = neighborRegionKeys(cx, cz) ∪ {'0,0'}`，`readyForColumn` / `ensureForColumn` 都经它；`layoutsForColumn` **仍只含 3×3 域**——`(0,0)` 不随 `layouts` 下发，只走 `redCity()` 全局下发。`Scheduler` 在 `readyForColumn` 放行后取 `redCity()`（此时必非 null；未放行的 column 不下发任务，所以不存在「塞 null 的 gen」）。

#### 13.3.3 吞并规则与避让清单

**优先级**（阶段 1 的 elif 链，`apply.js:139` 起）：`cityInfo → redCityInfo（影响域）→ 地标`。

**整体吞并**（相对 City「按 bounds 裁切」的有意细化）：凡占地（含过渡带）与 `influence` 相交的地标，**整个地标不生成**——地形整形与它的 JSON 结构
（海岛中心塔、平原金字塔岛）都跳过。理由：按 bounds 裁切会在影响域边缘切出半截金字塔/冰山，且过渡环只会向*自然*高度收敛，
切口处留下与地标等高的断崖；City 靠 `detectNearbyLandmark` 在过渡带里向地标高度混合，但那个函数用的是 region 几何中心的估算，不适用。

```js
landmarkErased(kind, center, redCity) = AABB(center ± FOOTPRINT[kind]) ∩ redCity.influence ≠ ∅
```

`FOOTPRINT` 必须取各 `getXxxInfo` 判定的**实际外包范围**，从 `landmarks.js` 导出（`landmarkHalfExtent(kind)`），不得在 redcity 模块里另写字面量（红线 1）。

### 13.4 地表与地形衔接（取代 §4.3 / §6.2–§6.4）

#### 13.4.1 基准高度 `baseY`（layout 层确定性计算）

```js
e(x, z) = max(generateHeight(x, z, seed), SEA_Y + 1)          // 有效自然高度：水域按海平面+1 计
baseY   = max( median{ e(p) : p ∈ core 外圈一格, 步长 4 },     // ≈1,100 次 generateHeight
               SEA_Y + 1 - REDCITY_GROUND_FLOOR )              // GROUND_FLOOR = -5 → 下限 4
```

- 写入 `redCity.baseY`。`REDCITY_GROUND_FLOOR = -5` 同时是烘焙钳制值与此处下限（单一权威在 `region-config.js`）：保证岛最低处是干地。
- ⚠️ v1.2：`baseY` 另有**上界** `REDCITY_BASE_Y_MAX = 8`，**钳制不抛错**（抛错会让极端 seed 的 GEN 整体失败）。与烘焙期 `REDCITY_DY_MAX_BUDGET = 87` 配对：
  `8 + 87 = 95 = WORLD_MAX_Y − 1`（`WORLD_MAX_Y = 96` 是独占上界）。〔实测〕seed 1–1500：1498 个为 4，2 个为 5（599、1491）。
- 〔实测〕seed 1–80、`W=24`：边界一圈台阶>2 的占比 **中位 0% / p90 2.9% / 最差 4.0%**，最大台阶中位 1、最大 4，超过 5% 的 seed 数 **0/80**（⚠️ v1.2：用落地的 `ringSurfaceY` + 真实 `generateHeight` 重测，最差 **3.88%**，同样 0/80 超 5%，见 §14.3）。
  对照 `GROUND_FLOOR=-12`（baseY≥11，按环可消化 8 格估算）时中位约 54%——所以下限必须是 -5。
- 〔实测〕岛列 ground（相对 baseY）分位数 p1/p5/p25/p50/p75/p95/p99 = -5/-3/-2/0/2/6/15；`< -5` 的只占 **0.6%**，钳制几乎不改变观感。
  被钳列的整列内容（壳 + 上方内容）整体上移 `floor - ground`，避免壳与上方内容脱节。

#### 13.4.2 烘焙高度场 `ground[ox, oz]`

`ground`（相对 `baseY` 的整数，`Int8`）覆盖整个 250×289 矩形：岛内列 = 压缩后的「外部可达最低 skin 表面」；岛外列 = 外推。
**岛外外推算法（评审原型验证可行）**：最近岛列的 ground 随距离每 2 格降 1（向 0 收敛），再做 Lipschitz 夹紧。
〔原型〕岛外列占矩形 47–69%（取决于地面口径），相邻最大高差 1，矩形边界一圈全为 0。

烘焙时断言、`check:data` 复核的不变量：

| ID | 不变量 | 作用 |
|---|---|---|
| I1 | 岛外相邻格 `abs(Δground) ≤ 1` | 岛外无断崖 |
| I2 | 矩形边界一圈 `ground == 0` | 核心边缘高度恒为 `baseY`，过渡环只需处理 `baseY` 与自然地形之差 |
| I3 | 岛内 `ground ≥ GROUND_FLOOR` | 岛最低处是干地 |
| I4 | `baseY_max + dyMax < WORLD_MAX_Y` | 内容不被世界顶截断（〔实测〕baseY∈{0,4,8} 时最高方块 y=56–72；`baseY ≤ 16`（噪声上限），最高方块 y ≈ baseY + 56~64 ≤ 80，余量 ≥16）。**拆两半**：烘焙期 `dyMax ≤ 87`；布局期 `baseY ≤ 8` 且 `baseY + dyMax < 96`（§13.5.5） |
| I5 | 同一刚性分量内任意相邻块：烘焙后 `yRel` 差 == 源 `y` 差（**严格，恒 0**） | 守「别退化成逐列剪切」的发射路径。⚠️ v1.2 新增，见下 |
| I5′ | 竖向接触（块与其正下方保留块）平移不一致占比 `< 0.1%` | 刚性平移的固有边缘产物；〔实测〕84 / 151,392 = **0.055%** |

⚠️ v1.2：**旧 I5（只数竖向接触）对逐列剪切完全无感**——同列块共用同一平移量 S，竖向邻居永不破坏；注入「逐列平移」缺陷后 `contactBreaks` 反而从 84 变成 0。
所以拆成**严格 I5**（数同一刚性分量内部全部 6 邻接对，注入实验 504 处）+ **占比 I5′**（保留旧口径，守边缘质量）。**I6 已删除**，见 §13.4.4。

`RELIEF = 0.34` 保留为**观感参数**（进指纹）。〔原型〕它对预算几乎无影响：RELIEF 0.2/0.25/0.34/0.5 下 opaque 占比 108/108/108/109%；地面再做 3×3 平滑两遍也只省 9%。
所以它不是预算旋钮，调它只为观感。

#### 13.4.3 地面整形（core 与 ring）

- **core**（阶段 1 完成，先于撒布/空中结构）：整列 `y ∈ [WORLD_MIN_Y+1, ground]` 实心填 `REDCITY_FILL_BLOCK = 'clay'`；`y > ground` 一路清空到 `WORLD_MAX_Y-1`
  （挖方：自然树、残丘、水体都清掉；云/空岛在其后写入，不受影响）。City 的 `generateCity` 同样「填 + 清残丘 + 水体补实」（`landmarks.js:806-849`）。
  ⚠️ v1.2：实现只清到 `max(自然高度, SEA_Y)`（其上在阶段 1 时本来就是空气——自然树由阶段 3 生成，已被 `pointContext` 的 core 避让挡掉），不必一路清到世界顶；见 §14.3。
- **ring**（与 `getCityFinalSurfaceY` 同构的台阶式钳制，**独立实现**，不带 `nearbyLandmark` 与 `CITY_MIN_SURFACE_Y` 耦合）：

```js
d        = 到 core 边缘的距离 (1..W)          // 边缘 ground 恒为 0（I2），故 coreH = baseY
natural  = e(wx, wz)                          // 已按 SEA_Y+1 下限：水域被补实成陆地
maxDelta = floor((W - d) / 3)                 // 外缘 0（= 自然），向内每 3 格多允许 1 格高差
surfaceY = natural + clamp(baseY - natural, -maxDelta, +maxDelta)
```
  ~~ring 的岩石基底用 12 层（不需要全深度）~~；`naturalH < SEA_Y` 的水体按 `generateCity` 手法用 `clay` **补实**（不得清成 air，否则地下出空洞）。
  **⚠️ v1.2：ring 的构造细则以 §14.3 为准**——填方从自然地表一路填到 `s−2`（不是「12 层基底」），`s−1` 写次表层、`s` 写表层，表层/次表层取该点 biome；挖方清到 `max(自然, SEA_Y)`。
- 水域一律变陆地。ring 外缘接湖时会在 `SEA_Y+1` 与湖床之间形成一道岸壁——与 City 现状一致，接受（§13.10 R4）。

#### 13.4.4 建筑刚性平移（取代逐列压缩；**⚠️ v1.2：删除「脚下平台化」与 I6**）

- 把「地面之上的内容」按 6 邻接连通体分组（建筑清单 `isBuildingMat`；块数 `< minComp = 30` 或贴包围盒边 `borderKeep = 8` 以内的**不刚性**），
  每个连通体取**一个**平移量 `S_C`（继承它脚下逐列目标平移 `S` 场，涂色范围 = footprint ⊕ `pad = 1`），**整体刚性平移**；不得逐列平移（会把垂直墙面剪切成台阶）。
  〔实测〕134 个连通体里 125 个刚性、9 个贴边、1,237 个小件不刚性。
- ~~连通体 footprint（外扩 1 格）内的 ground 取参考高度（平台化）~~ **v1.2 作废**：烘焙**不压平建筑脚下的地面**——footprint ⊕ pad 内地面保持源模型的起伏 1:1
  （`ground′ = g − sMed + S_C`，`g` 仍是逐列的），只是整体用同一个平移量。〔实测〕旧 **I6**「footprint 内 ground 极差 ≤ 1」在 125 个刚性分量里有 **104 个违反**
  （极差中位 8、最大 **40**）——它描述的是一个没有被实现、也不该被实现的算法：平台化会把塔座周围的岩丘铲平，改变模型造型。**I6 删除**，由 I5 / I5′ 取代（§13.4.2 表、§14.2）。
- 〔实测〕5 座有效样本的塔座周围地面（1–4 格环带）p5–p95 起伏为 8、12、13、21、23 格 → 逐列压缩会让建筑内部产生 5–15 格的相对错位。
- 〔原型〕预算数字用的是逐列压缩（保守）；刚性平移让玻璃/墙面保持完整（transparent 略升）。**以真实实现的真实页面实测为准**（§14.7）。

#### 13.4.5 core 内全深度实心（不留洞穴）

core 内从 `WORLD_MIN_Y+1` 一路实心到 `ground`，不再留下自然洞穴。〔原型〕seed=12345 中心窗口 opaque used 2,895,784 → 2,508,064（**-387,720**，折算 reserved 约合 opaque 容量的 **17 个百分点**），

保留的只有 `check:data` 的三条**关系式/覆盖率**门禁（不依赖真实色值）：

#### 13.5.5 产物格式：JSON（**D8，2026-10-22 用户裁定**）

用户质疑「为什么要烘焙」后实测澄清：**本设计的「烘焙」不产生任何新方块或新贴图** ——
映射表用的全是 registry 现有方块，实测仅 **28 种**（`light_gray_cloth` / `clay` / `pink_wool` /
`glass_block` / `oxidized_cut_copper` / `stone_bricks` / `planks` / `leaves` …）。「烘焙」只是
**离线把 76 MB 解压体的 schematic 转成紧凑数据**，与 `npm run icons` / `nightsky` 那种产 PNG 的
美术烘焙不是一回事。

**为什么这一步不能放运行时**〔实测〕：gunzip+NBT 解析 109 ms + 投影/刚性平移/地面场计算 796 ms
= **924 ms**，峰值 **RSS 643 MiB**（arrayBuffers 257 MiB）。冷启动预算 < 2 s（设计文档 §1）被吃掉 46%，
且 Worker 池有 14 个（`hardwareConcurrency-1`），每个独立算一遍 = 14 × 924 ms。

**产物格式选 JSON 而非自定义二进制**，形状经实测三选一：

| 形状 | raw | gzip | parse | heap |
|---|---|---|---|---|
| ① 对象数组 `{x,y,z,type}`（`castle.json` 同款） | 10.19 MiB | 0.75 MiB | 18.2 ms | +18.8 MiB |
| **② 扁平 `[col, dy, pal]` + palette（选定）** | **2.85 MiB** | **0.62 MiB** | **4.6 ms** | **+6.4 MiB** |
| ③ 列 run `[col,dy,len,pal]` + palette | 2.07 MiB | 0.42 MiB | 5.9 ms | +11.8 MiB |
| （对照）RCY2 自定义二进制 | 1.0 MiB | — | 0.64 ms | +2.8 MiB |

选 ②：体积/解析/堆三项都远优于 ①，且**不需要自定义编解码器**（删掉整个 RCY2 codec 与其 7 条单测）。
③ 体积更小但堆占用反而更高（嵌套数组），且少一层 run 合并逻辑更好维护。14 个 Worker 各持一份：
② 约 6.4 × 14 ≈ 90 MiB（可接受），① 则要 263 MiB。

**产物 = 单文件 `assets/redcity/redcity.json`**（数据 + 指纹 + 不变量实测值同居，同 `icons.json` /
`head.json` / `armor.json` / `night-sky.json` 四个先例的「产物 + 伴随指纹」口径）。形状：

```
{ format:'redcity-json', version:1, width:250, length:289, dyMin:-6, dyMax:80,
  spawn:{ox,oz,dy}, palette:string[28],
  ground:number[72250],        // 每列地面高度（相对 baseY，Int8 范围 -5..43）
  island:string,               // 每列是否岛内，'0'/'1' 串（比数组省 3 倍体积）
  blocks:number[],             // 扁平三元组 [col, dy, pal]，按 (col, dy) 升序
  stats:{...}, params:{...}, spawnParams:{...}, invariants:{...}, fingerprint, bakedAt }
```

⚠️ **`dy` 是相对 `baseY` 的行号，世界 y = `baseY + dy`** —— 不是相对该列地面的偏移。
实测验证：地面方块恰在 `dy === ground[col]`。**写成 `baseY + ground + dy` 会把内容整体抬高
`ground` 格**（最大 43 格 → 顶穿 `WORLD_MAX_Y=96`，且与阶段 1 整形好的地面脱节）。
`ground` 数组只用于：① 阶段 1 的 core 填充高度；② ring 过渡环混合；③ 出生点。**不参与方块放置**。

⚠️ **`blocks` 必须按 `(col, dy)` 升序** —— 加载器建列索引靠这个前提做单遍前缀和；乱序会让
`colStart` 算错 → 展开时静默错位（方块出现在错的列，肉眼像「地图花了」）。加载器须显式校验并抛错。

〔实测〕烘焙 824 ms；产物 244,647 块 / 28 palette；加载磁盘产物 + 建列索引 **1.3 ms**；
展开 1 个 column（16×16 格，1,608 块）**0.11 ms**；往返全量展开 244,647 块 **0 不一致**。

**I4 拆两半**（`baseY` 是布局期按 seed 算的，烘焙期不知道）：
- 烘焙期断言 `dyMax <= REDCITY_DY_MAX_BUDGET`（87）；
- 布局期断言 `baseY <= REDCITY_BASE_Y_MAX`（8）与 `baseY + doc.dyMax < WORLD_MAX_Y`。

⚠️ `WORLD_MAX_Y = 96` 是**独占上界**（合法 y 最大 95），故预算须满足
`BASE_Y_MAX + DY_MAX_BUDGET <= 95`，**不是 `< 96` 就算对**。实测 1500 个 seed 的 `baseY`
最大 = **5**（仅 2 个 seed > 4；下限 `SEA_Y+1-GROUND_FLOOR = 4` 几乎总是生效），当前产物
`dyMax = 80` → 余量 ≥ 8 格。

**I5′ 的验收口径是占比而非绝对 0**：实测 `contactBreaks = 84 / verticalContacts = 151,392`
= **0.055%**，都发生在连通体 footprint 边缘（涂色地面与分量 S 的交界处），是刚性平移的固有产物。
门禁取 `< 0.1%`。⚠️ v1.2：另有**严格 I5**（同一刚性分量内部保形，恒 0），两者缺一不可，理由见 §13.4.2 表后注与 §14.2。

**参考实现已入库**（本节的每个数字都可复现）：
`docs/superpowers/specs/2026-10-22-redcity-appendix/appendix-{a,b,c,d,e}-*.mjs`
—— A = schematic/NBT 读取，B = skin 清单与映射表，C = 烘焙核心与出生点，D = JSON 产物与加载器，
E = 主流程与指纹。每个文件末尾带自检，`node appendix-X.mjs` 即可复现上述数字。
⚠️ v1.2：另有 `appendix-f-reference/`（**落地形态**的全部新文件 + 对既有文件的补丁 + 测试，在影子工作树里跑通并做过负向验证，见 §14.11）；
A–E 是算法的独立可复现参考，F 是它们在仓库里的最终样子（常量归位到 `region-config.js`、导入路径改仓库风格）。**实施以 F 为准，A–E 用于对数字。**
schematic 副本入库于 `assets/redcity/src/SakuraSpawn.schematic`（808 KB，小于已入库的

### 13.6 出生点与存档（取代 §8）

#### 13.6.1 出生点：烘焙选定

- 判据（〔实测〕在真实模型数据上跑过）：① 外部可达的地面格；② 其上 **24 格全空**（不被屋檐/树冠遮盖）；③ 5×5 范围内 ground 极差 ≤ 1；④ 取距模型中心最近者。
- 〔实测〕满足者共 **105** 个；半径 16 格内 **0** 个、32 格内 17 个；最近为模型坐标 (197,203)（RedCity 局部 `ox=146, oz=137`），距中心 22.6 格，地面 y=84，材质 `159:8`。
  v1.0 的 (178,211) 是 `168:2` 屋顶块的顶面（该列自上而下第一个方块），「上方 2 格空气」的弱判据选中了它。
- 写入 `redcity.json`：`spawn: { ox, oz, dy }`（相对 core 原点与 `baseY`；`dy` 是相对 `baseY` 的行号，不是相对该列地面）。
  运行时 `getRedCitySpawnPoint(redCity, model) → { x, y, z }`：⚠️ v1.2 `x/z` 取烘焙列的**方块中心**（`+0.5`），`y = baseY + dy + 1` 只是扫描起点的下界提示，真正站立位由下面的向下扫描决定。
- `Game` 不对 RedCity 世界调用 `findSpawnY`（从世界顶向下找首个非空气，会落在塔顶/树冠，既有约束已记录），改为：
  **从 `y+24` 向下扫首个「脚下 solid 且其上两格空气」的格**（`scanDownForSpawn`，返回脚所在的 y）——容忍玩家日后在出生点上方建造，且不会被上方结构遮蔽（烘焙保证其上 24 格全空）。扫不到（数据异常）→ 退回 `getRedCitySpawnPoint().y`，不抛错。
- 所有世界（含 `?seed=` 指定）一律在 RedCity 出生。全深度实心（§13.4.5）使出生点不再依赖自然地形（v1.0 在 seed=12345 的中心处有「壳底到自然地表缺口 15 格 > FILL_MAX」的问题）。

#### 13.6.2 存档（D7）：IndexedDB 升级清库

- `persistence.js`：`DB_VERSION` 2 → **3**；`onupgradeneeded(e)` 在 `e.oldVersion ∈ {1,2}` 时清空 `meta` / `edits` / `entities` 三个 store
  （`req.transaction.objectStore(name).clear()`），其余保持「不存在时创建」的幂等写法。

- ⚠️ v1.2 订正（实测，v1.1/计划里的说法写错了失败形态）：清库的两个典型错误写法**不会**「卡成白屏无报错」，而是 **`open()` 以 AbortError reject**（被调用方吞掉才像卡住）：

| ~~I6~~ | ~~建筑 footprint 内 ground 极差 ≤ 1~~ | **删除，不替换为断言** | 125 个分量里 104 个违反，极差中位 8、最大 40 |

**为什么拆 I5**：旧 I5 只数「竖向接触」，而同一列的块共用同一个平移量 S，竖向邻居**永远不会被破坏**——把烘焙改成逐列平移后，`contactBreaks` 反而从 84 变成 0
（旧门禁在缺陷出现时读数「更好看」）。严格 I5 数的是**同一刚性分量内部的全部相邻对**，逐列剪切必然让它 > 0。

**为什么删 I6**：它要求建筑脚下的地面被压平，但烘焙算法（C）**不压平**——footprint ⊕ pad 内地面保持源模型起伏 1:1，只是整个分量用同一个平移量。
压平会把塔座周围的岩丘铲掉，改变模型造型；而「建筑内部不变形」这个真正想保护的性质，已经由 I5 / I5′ 完整覆盖。

**可见后果（R12）**：塔座周围的岩丘按源模型 1:1 保留（极差中位 8、最大 40 格）——玩家看到「宝塔立在山石上」，与源模型一致；出生点不受影响（出生点判据要求 5×5 内 ground 极差 ≤ 1）。

### 14.3 过渡环构造与地表公式（取代 §13.4.3 的 ring 描述）

对 ring 内一点（到 core 的切比雪夫距离 `d ∈ 1..24`，自然高度 `n = generateHeight`）：

```
e  = max(n, SEA_Y + 1)                         // 有效自然高度：水域按海平面+1 计（水一律变陆地）
m  = floor((24 − d) / 3)                       // ringMaxDelta：外缘 0，向内每 3 格多允许 1 格高差
s  = clamp(baseY, e − m, e + m)                // 环上地表（等价于 e + clamp(baseY − e, −m, +m)）
```

- **构造**（`shapeRedCityRing`，直接写 `column.blocks/meta`，不走逐格 `setBlock` 闭包）：
  - `s > n`（填方，含水域转陆地）：`(n, s−2]` 填 `clay`（**覆盖原水体，不得清成 air**——否则地下出空洞，玩家挖下去会掉进洞里）；`s−1` 写次表层；`s` 写表层。
  - `s < n`（挖方）：`(s, max(n, SEA_Y)]` 清成 air；`s` 写表层；`s−1` 写次表层。
  - `s == n`：不动（保留自然表层）。
  - 表层/次表层 = 该点 **biome** 的 `[surface, subsurface]`（`terrain.js` 的 `surfaceBlocksOfBiome`，`SURFACE_BY_BIOME` 的唯一读出口）——环带与外侧自然地形同色。
  - 因 `s ≥ SEA_Y + 1` 恒成立，`s` 以上不会残留水。
- **core 列**（`shapeRedCityCore`）：`[WORLD_MIN_Y+1, ground]` 全深度填 `clay`（不留洞穴、不留水）；`(ground, max(n, SEA_Y)]` 清空（自然树/残丘/水体）。
- **可证明的高差界**：clamp 对两端点 1-Lipschitz，`m` 相邻差 ≤ 1 ⇒ 相邻两格 **`|Δs| ≤ |Δe| + 1`**——环只会在自然地形的高差上**至多多加 1**。
  〔实测〕20 个 seed：`|Δs| > 1` 的占比 ≤ 2%（最差 0.69%）；seed 1–80：core 边缘一圈对自然地表台阶 > 2 的占比最差 **3.88%**（≤ 5%）。
- 外缘（`d = 24`）`m = 0` ⇒ `s = e`，与外侧自然地形恒等（含水域按 `SEA_Y+1` 计的岸壁，与 City 现状一致，接受，R4）。

### 14.4 吞并范围（取代 §13.3.3 的 FOOTPRINT 估算）

**吞并 = 整个地标不存在**：地形整形 + 它的 JSON 结构 + **植被上下文**三处都当它不存在。被吞并标志每次 `applyStructuresToColumn` 调用**只算一次**（`erasedFlags`），阶段 1 / 2 / 3 共用同一份。

**外包范围唯一权威 = `landmarks.js` 的 `landmarkHalfExtent(kind)`**，取各 `getXxxInfo` 判定所用的同一组常量（`floor(SIZE/2) + TRANSITION`），再并入该地标在阶段 2 光栅化的 JSON 结构占地：

| 地标 | 地形半宽 | JSON 结构占地 | `landmarkHalfExtent` | v1.1 / 计划的说法 |
|---|---|---|---|---|
| pyramid | 28 | — | 28 | 28 ✓ |
| frozenMountain | 48 | — | 48 | 48 ✓ |
| snowLand | 28 | — | 28 | 28 ✓ |
| island | **25**（`getIslandInfo` 入口 AABB） | 塔 (4, 5) | **25** | ~~39~~（`dist<39` 不可达） |
| plainLand | 15 | 平原金字塔岛 (17, 20) | **(17, 20)** | ~~15~~（漏了结构占地） |

- 测试用**暴力扫描**钉死「`getXxxInfo` 非空 ⇒ 点在 `landmarkHalfExtent` 内」（防漂移），而不是复述常量。
- **R1 吞并代价表**（冰山 91 / 金字塔 80 / 雪原 63 / 海岛 19 / 平原岛 4，80 seed 累计）用真值复核**无误**（表里的「海岛 19」本来就是按真值 25 计的，**不是**按 39 算的，表无需订正）。
- **植被上下文**：被吞并的冰山/雪原若仍按 `snow`/`fm` 判上下文，树基点取地标高度公式 ⇒ 地形已是自然地形，树**悬空**。〔实测〕60 个 seed 里 46 个出现，190 棵雪桦树 149 棵悬空（最高 24 格）。
- **植被避让距离** `REDCITY_VEG_CLEARANCE = TREE_CANOPY_RADIUS = 3`（唯一权威 = `region-config.js`）：`apply.js` 阶段 3 的扫描外扩 `EXT` 与避让距离**同源**（不是「恰好相等」）；
  树冠最大水平半径用 `generateTree` 实测钉（swamp 的 `|dx|+|dz|≤3.5` 取到 3，其余 2，桦树 JSON ±2），加更大树型必须先改这个常量。根在 `d ≥ 4` 的树冠最近只到 `d = 1`，永不进 core。
- **撒布过滤**：候选 footprint 与 `influence` 相交 ⇒ 整体丢弃（连影响域外的那一部分也不生成）。现状对 City bounds 也没有这层过滤（R6），RedCity 自写，不替 City 补。
  **对照实验带宽 ≥ 32 格**（最大撒布半宽 24 + 8 格余量），带宽 24 会因为被丢弃的撒布候选造成伪差异。

### 14.5 接线、降级语义与存档（取代 §13.3.4 / §13.6 的接线描述）

- **全局下发**：`StructureIndex._requiredKeys(cx,cz) = neighborRegionKeys ∪ {'0,0'}`，`readyForColumn` / `ensureForColumn` 都经它；`layoutsForColumn` 仍只含 3×3 域；
  `Scheduler` 在放行后取 `redCity()` 塞进 `gen` payload（约 200 B）；`world-worker` 的 `gen` 传给 `applyStructuresToColumn(..., redCity ?? null)`。
- **产物下发顺序**：`Game.start()` 里 `atlas-meta` broadcast 之后、任何 `gen` 之前：`fetch('/assets/redcity/redcity.json')` → `res.ok` 检查 → 主线程 `JSON.parse + prepareRedCityModel + setRedCityData` →
  `pool.broadcast('redcity-data', { text })`。`postMessage` 保序，后续 `gen` 必拿得到。Worker 的 handler 走**同一条** parse + prepare（红线 8）。
- **三种异常语义**（不是一种）：① **产物未注入**（`getRedCityData() === null`）→ 降级：core 退化为 `baseY` 平地、不写内容、**不抛错**，首次命中 `console.warn` 一次（「静默变平地」是最难发现的失效形态）；
  ② **产物尺寸与布局不符** → **抛错**（不会静默错位放置）；③ **fetch 失败 / 非 2xx** → `Game.start()` 抛错 = **启动失败**（loud）。
- **出生点**：`getRedCitySpawnPoint(redCity, model) → { x, y, z }`，`x/z = core.minX + spawn.ox + 0.5`（方块中心），`y = baseY + spawn.dy + 1`（**仅作扫描起点**）；
  `scanDownForSpawn(getId, x, yTop, z)` 从 `y+24` 向下扫首个「脚下 solid 且其上两格空气」，返回**脚所在 y**；扫不到 → 退回起点 `y`。**不用 `findSpawnY`**。
  `?spawn=city` → 退回 City 中心（`Game` 构造选项 `spawn: 'redcity'|'city'`，`main.js` 解析 URL；**不进设置面板**，与 `?skybox=0` / `?shadows=0` 同类调试入口）。
- **水面门控**：`ocean-mask.js` 的 `isOceanMasked(x, z, seed, cityBounds, redCityBounds)` 第 5 参缺省 = 关闭；`ocean.js` 加第二个 bounds uniform + `setRedCityBounds(redCity)`（取 `influence`，缺字段恢复哨兵）；
  两端用**同一个不等式**（红线 1）。〔实测〕6 个 seed，influence 内关门控时有 765~1203 / 2744 个采样点会渲染水面（≈33~44%），开门控后全部熄灭，外侧不受影响。
- **存档（D7）**：`DB_VERSION = 3`；`onupgradeneeded(e)` 在 `e.oldVersion ∈ {1, 2}` 时 `req.transaction.objectStore(name).clear()`（`contains` 守卫，**先清后建**）；
  `open({ onBlocked })` 的回调由 `Game` 接到 `main.js` 覆盖层，`start()` 成功后撤掉。两种清库错误写法的**真实失败形态是 AbortError reject**（§13.6.2），不是挂起。

### 14.6 烘焙产物契约与门禁

**常量归位（C11）**：`REDCITY_SIZE / TRANSITION / GAP / GROUND_FLOOR / FILL_BLOCK / BASE_Y_MAX / DY_MAX_BUDGET / TREE_CANOPY_RADIUS / VEG_CLEARANCE` **全部在 `region-config.js`**；
`tools/` 单向 import `src/`（`check:arch` 只禁反向）。烘焙参数（`relief/K/decay/pad/minComp/borderKeep`）与 skin/映射清单留在 `tools/redcity-config.mjs`，进指纹。

**`prepareRedCityModel` 的运行时校验**（Worker 与主线程同一入口；坏产物一律抛错）：format / version / `ground` 与 `island` 长度 / `blocks` 非三元组整数倍 /
**`col` ∈ [0, N) 整数**（越界写 `Uint32Array` 会被**静默丢弃**）/ **`dy` ∈ [dyMin, dyMax] 整数** / **palette 下标 ∈ [0, palette.length)** / **`(col, dy)` 严格升序**（同时保证列索引前缀和成立与同格不重复）。

**`check:data` 的 `[RedCity]` 环节**：① 指纹重算比对（schematic 原文 + 参数 + 清单 + 映射）；② `prepareRedCityModel` 自洽；③ 产物尺寸 === `REDCITY_SIZE`、`groundFloor` === `REDCITY_GROUND_FLOOR`、`dyMax ≤ 预算`；
④ palette ⊂ registry；⑤ I1/I2/I3 **从数组重算**；I5′ 占比；⑥ `blocks` 三元组数 === `stats.retained`；⑦ **岛内每列在 `dy === ground` 处都有方块**；⑧ 映射覆盖；⑨ 出生点判据重验（5×5 窗口、头顶 24 格空、贴墙/树冠排除）；
⑩ 颜色关系式：`35:6/251:6/252:6` → `pink_wool`；屋顶贴图平均色 **R < B < G**。

**产物篡改 / 配置漂移的负向验证**（影子工作树实测，全部真 FAIL）：屋顶映射目标改 `stone_bricks`（指纹 + 颜色双红）/ `REDCITY_SIZE.X` 与产物不符 / 樱花粉不再直映射 / 边界 `ground` 非零（I1+I2）/ 出生点 `dy` 被改 /
palette 含 registry 外名字 / 岛外内部格 `ground=9`（I1）/ 相邻不同列三元组交换（列序乱）/ 同列 `dy` 降序 / 同格重复 / 少一个三元组 / palette 下标 99 与 -1 / 岛内列 `ground` 与 blocks 脱节 / `col` 越界 / `dy` 超 `dyMax`（共 16 项：配置漂移 3 + 产物篡改 13）。
⚠️ 其中 4 项（同列 dy 降序、palette 越界、三元组丢失、ground 与方块脱节）在第一版门禁里**漏过**——是负向验证本身发现的盲区，加固后才全红。

### 14.7 预算：U1′（**〔已裁定：U1′-a，2026-10-23〕**，取代 §13.7.5 / §13.7.7）

**为什么方案 A 不够**：方案 A 的数字来自 Node 侧「RedCity 中心 17×17 列窗口」的 A/B 实测（opaque reserved 2,712,730）；真实页面稳态同为 289 列，但 reserved 已是 3,344,190（+23%）——
Node 侧低估的来源本次未逐项分解，所以**容量必须以真实页面实测为准**（这也是预算门禁做成真实页面 spec 的原因）。
真实页面实测（vd=8，出生点稳态，`reservedV = ceil(vertexCount × 1.25)` 对 `maxVertexCount`）：

| 通道 | 方案 A 容量 | U1′ 容量 | 稳态 reserved | 占方案 A | 占 U1′ |
|---|---|---|---|---|---|
| opaque | 3,705,000 | **4,275,000** | 3,344,190 | **90.3%** | 78.2% |
| cutout | 2,200,000 | 2,200,000（不变） | 553,630 | 25.2% | 25.2% |
| transparent | 300,000 | **360,000** | 252,465 | 84.2% | 70.1% |

**为什么要涨——不是「方块总数陡增」，而是顶点在三个通道间的构成变了**（2026-10-23 补测；真实页面，seed=12345，vd=8，289 列窗口，City 出生点 vs RedCity 出生点，同一份统计脚本）：

| 窗口内 | City 出生点 | RedCity 出生点 | 变化 |
|---|---|---|---|
| 非空气方块 | 2,725,461 | 3,179,449 | +45 万（+17%） |
| 暴露方块（列内至少一个邻格不挡面） | 895,145 | 1,059,912 | +16 万（+18%） |
| 预留顶点 · opaque | 2,326,550 | 3,344,190 | **+44%** |
| 预留顶点 · cutout | 1,590,220 | 553,630 | **−65%** |
| 预留顶点 · transparent | 13,290 | 252,465 | **×19** |
| 预留顶点合计 | 3,930,060 | 4,150,285 | **+5.6%** |

- 方块数只多了**十万量级、约 17%**（RedCity 建筑本身 244,647 块）；出生点的顶点**总量只涨约 6%**。
- 但 `CAPACITY` 是**三个通道各自一块固定容量**的预分配缓冲：RedCity 把顶点从 cutout（植被）挪到了 opaque（楼阁、地面、粉羊毛树冠 3 万块）和 transparent（5.6 万块玻璃）——旧容量 opaque 2.85M 在出生点就已不够（需求 3.34M，117%），transparent 125K 更是 202%。按 ×1.5 的扩容兜底规则推算，引擎会在运行时把 opaque 整批扩到 4.275M，**恰好就是 U1′ 预先开的大小**——预开是把这次整批重分配挪到启动期，并让预算门禁能钉死上限。
- 容量要覆盖**每个通道各自的最坏位置**，而三个通道的峰值出现在不同地点（opaque 在 RedCity 本体、cutout 在东南角自然森林、transparent 在 seed=777 的东缘水域），所以容量≈各通道峰值之和（3.95M + 2.04M + 0.30M ≈ 6.28M，U1′ 总容量 6.835M 是它的 92%），而不是「出生点总量」。cutout 虽然在出生点只用了 25%，但森林飞越峰值 92.6%，不能缩。
- `gpuVertexBytes` 是**已分配容量**而非占用：出生点预留顶点 × 30 B，City 约 112 MiB（占旧 148.06 MiB 的 76%）→ RedCity 约 119 MiB（占新 195.55 MiB 的 61%）。占用只涨约 6 MiB，分配涨了约 47 MiB。
- **架构没有变化**：仍是 BatchedMesh 通道级合批、同一顶点格式（30 B/顶点），只改了 `CAPACITY` 里 `opaque.active` 1200→1800、`transparent.avgVerts` 1000→2880 两个常数。

方案 A 容量下（真实页面，12 s）：W 键奔跑 opaque 峰值 98.9%（+z 方向，无扩容但贴线）；无碰撞飞越（seed 12345）峰值 **106.6% → `_capacity.opaque.maxVertexCount` 变化 = 触发 ×1.5 扩容**（3.705M → 5.5575M，顶点缓冲 177.53 → 230.5 MiB）。

**无碰撞飞越峰值**（悬停 y=70、8 格/秒直线 12 s，6 条路线取最大，U1′ 容量，**零扩容**）：

|---|---|---|---|---|
| 12345 | 3,948,035（92.4%） | 2,036,265（**92.6%**） | 257,890（71.6%） | opaque R5 西北→对角；cutout R6 东南角 |
| 777 | 3,909,820（91.5%） | 1,578,365（71.7%） | 299,135（**83.1%**；占旧 300K = **99.7%**） | transparent R3 东缘中点 |
| 31337 | 3,942,490（92.2%） | 1,332,875（60.6%） | 283,845（78.8%） | — |
| 99999 | 3,939,940（92.2%） | 1,204,820（54.8%） | 272,495（75.7%） | — |

opaque 在各 seed 间几乎恒定（3.91~3.95M，由 RedCity 本体决定）；transparent 随 RedCity 周边的自然水域浮动；cutout 随周边森林浮动。

**候选与推荐**（GPU 顶点缓冲 = Σ`maxVerts` × 30 B；冻结基线 148.06 MiB）：

| 选项 | opaque | cutout | transparent | GPU | 最坏余量（opaque / cutout / transparent） |
|---|---|---|---|---|---|
| A（已批准，**作废**） | 3.705M | 2.20M | 0.30M | 177.53 MiB | **−6.6%（超）** / 7.4% / 0.3% |
| **U1′-a（推荐）** | **4.275M**（`active 1800`） | 2.20M | **0.36M**（`avgVerts 2880`） | **195.55 MiB**（+32.1%） | 7.6% / 7.4% / 16.9% |
| U1′-b | 4.275M | 2.40M（`active 600`） | 0.36M | 201.27 MiB | 7.6% / 15.2% / 16.9% |

推荐 U1′-a：cutout 的 92.6% 出现在 seed=12345 东南角，是**自然森林**驱动而非 RedCity 特有（其余 3 个 seed 55~72%），改 cutout 超出本 Epic 的范围；
门禁取「≤ 95%」，余量被侵蚀时门禁会先红，届时再升 cutout（U1′-b，+5.7 MiB）并重新过用户。`CAPACITY` 拆分（已验算 `active × avgVerts × 1.25`）：

```js
const CAPACITY = {
  opaque:      { active: 1800, avgVerts: 1900 },  // maxVerts = 4,275,000
  cutout:      { active: 550,  avgVerts: 3200 },  // maxVerts = 2,200,000（不变）
  transparent: { active: 100,  avgVerts: 2880 },  // maxVerts = 360,000
};
// 顶点缓冲合计 = (4,275,000 + 2,200,000 + 360,000) × 30 B = 205,050,000 B = 195.55 MiB
```

**验收门禁（取代 §13.7.7）**：真实页面、vd=8，`tests/redcity-budget.spec.mjs`：① 出生点稳态三通道 ≤ 95%；② 无碰撞飞越峰值三通道 ≤ 95% 且 `_capacity.*.maxVertexCount` 全程不变（seed 12345 的 R5/R6 + **seed 777 的 R3**）；
③ `gpuVertexBytes ≤ 195.55 MiB` 且等于容量之和。负向验证：容量回退到方案 A → ②真 FAIL；transparent 回退 300K → seed 777 用例真 FAIL（99.7% > 95%）；cutout 擅自加到 2.4M → ③真 FAIL。

⚠️ **这是对「冻结值」的变更**：设计文档 v1.42 写明 `gpuVertexBytes` 148.06 MiB < 150 MiB 且「均不放宽」。采纳 U1′ 必须**先更新设计文档（计划的 Task 0）再改 `CAPACITY`**；
既有 `m3-fullscene.spec.mjs` 的 150 MiB 断言**按设计会红**，须在同一次变更里改成新预算（这是有意变更，不是静默放宽）。

### 14.11 复现方法与局限

- **方法**：在仓库副本（影子工作树）里按计划实现全部改动，用真实函数 / 真实页面复测；每个 Tier 1 断言都做了负向验证，**按 Task 计 83 项、全部真 FAIL**（T1 3 / T2 11 / T3 4 / T4 8 / T5 3 / T6 7 / T7 7 / T8 1 / T9 19 / T10 16 / T11 4；其中 T9 的 19 项 = E2E 10 + 预算 3 + 水面门控单测 1 + 编辑耗时观测 5，T10 的 16 项 = 配置漂移 3 + 产物篡改 13）。每项注入前先断言锚点恰好匹配 1 处、注入后读回确认落地、验证后还原。
  影子工作树的落地形态入库为 `docs/superpowers/specs/2026-10-22-redcity-appendix/appendix-f-reference/`（新文件 + 测试 + spec，**冻结快照**，落地后以 `src/` 为准）。
- **局限**：① 预算数字来自本机（macOS ARM / Metal）单机多 seed 抽样（4 个 seed × 6 路线），不是全 seed 覆盖；② 像素阈值对着本机 GPU 的实测值标定，Linux CI 的 SwiftShader 可能需要重标；
  ③ 全量回归里的计时型 spec 仍遵循既有「交替对照」纪律；④ 版权问题（R11）不是技术问题，未验证。
