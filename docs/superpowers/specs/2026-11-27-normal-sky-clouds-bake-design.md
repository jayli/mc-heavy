# 「普通」天空盒补上云层（烘焙期绘制）

2026-11-27 | 状态：待批准

## 1. 要解决什么

v3.47 落地「普通」环境风格时，我烘的天空盒**只有大气渐变和日轮，没有云**。
用户指出：上游那个游戏的天空是有云彩的（截图 `~/bacht/ttt/bug/cloud.png`：大片积云，
顶亮底灰、边缘有前向散射亮边），而画面里最显眼的东西不该缺。

对照：既有 `assets/sky/day/posx.jpg` **自带云**（上游给那四套提供的是照片），
所以「其余四档有云、只有普通档没有」这个不一致是真实的缺陷。

**用户明确划定了范围**（2026-11-27，纠正我的第一次理解）：

> 「按照原来那个游戏的云层来烘焙出静态天空盒图，而不是把云层算法搬过来」

⇒ 云是**烘焙期的实现细节**，交付物是静态图片。运行时**零新增代码**。

## 2. 非目标 / 反目标

- ❌ 不移植运行时体积云（无 raymarch pass、无动云、无云影投到地面）。
- ❌ 不改 `src/render/sky.js` / `materials.js` / `daynight.js`（运行时零改动）。
- ❌ 不给其余四档加/改云。
- ❌ 不画地面景物（用户红线，v3.47 已定）。
- ❌ 不动玩法、地形、方块、存档。
- 反目标：云把天空糊死（地平线渐变不可见）、云边缘被 JPEG 咬成锯齿、
  立方图接缝因云的高频内容而恶化。

## 3. 已实测的事实（不是推测）

| 事实 | 数值 | 来源 |
|---|---|---|
| 单位 `cloudDensity`（3 次 3D 查表 + 相位） | **22 ns** | 一次性 Node 探针（已删） |
| 1024²×64 步 6 面全量 + 5 步 light-march | **约 13 s** | 同上推算 |
| 既有大气烘焙耗时（无云） | 41 s | `npm run normalsky` 实测 |
| 现有 `normal/posx.jpg` 云 | **零**（grep `cloud` 无匹配） | 代码 + 看图 |
| 现有 `day/posx.jpg` 云 | 有（块均值极差 108） | 像素统计 |
| 立方图方向数学正确性 | 编码前接缝 RMS **0.000000** | v3.47 探针 |
| 现有 `normal` 接缝（JPEG 残差） | RMS 0.353 / max 0.769 | Tier 4 实测 |

结论：**成本是秒级，不是「太重做不了」**。上一轮之所以没做，是漏了不是取舍。

## 4. 三条路线

| 路线 | 做法 | 取舍 |
|---|---|---|
| **A. 烘焙期求值上游体积云公式**（选定） | 在 Node 里逐字复现 `22_sky.js` 的 `cloudDensity` + `G_CLOUD_FRAG`，对每个立方图方向 march，把 `alpha`/`S` 合成进静态图 | 拿到的就是上游那种积云形态（powder + 三 lobe 前向散射 + 5 步自阴影）；烘焙 +13 s；运行时 0 |
| B. 纯 2D 噪声画云 | 在立方图 uv 上叠 fbm 阈值化成白色斑块 | 便宜，但**画不出「顶亮底灰 + 亮边」**——那三条观感特征需要沿光线的自阴影与相位函数，2D 阈值云一眼假 |
| C. 找现成云贴图 | 贴图库下载 | 本仓无此来源；且与用户「按照原来那个游戏的云层」直接冲突 |

选 **A**。B 是唯一真正的替代，但它达不到用户要的形态；C 不满足「照抄上游」。

## 5. 实现

### 5.1 新模块 `tools/normal-sky-clouds.mjs`（three-free，纯数值）

从上游 `22_sky.js` 逐字搬，**不改公式**：

- `CB = 336.0`、`CTOP = 585.0`（云层下/上界，上游常量）
- `cloudWeather(xz)`：`uNoiseTex.b` 两个尺度混合 → `smoothstep(1−cover−0.2, 1−cover+0.26, n)`
- `cloudDensity(p, detail)`：形状骨架（`uCloudNoise` 的 fbm + Worley 加权）→ 高度渐变
  `grad = smoothstep(0, 0.085, h) × (1 − smoothstep(topFall×0.45, topFall, h))` → 细节侵蚀
- `marchClouds(camPos, rd, sunDir, sampleNoise)`：上游 `G_CLOUD_FRAG` 的循环体，
  含 5 步 light-march、三 lobe Henyey-Greenstein、powder、ambTop/ambBot
- `computeSH(...)`：上游同名函数的移植，产出云的 `ambTop`/`ambBot`

**降级处理**（与上游的差异，必须记录）：

| 上游 | 本仓烘焙 | 理由 |
|---|---|---|
| `uHistoryWeight` 时间累积 | 恒 0（无 TAA） | 静态图要的是收敛结果 |
| 每帧抖动 `ign(gl_FragCoord, uFrame)` | 固定分层 jitter 序列 | 无帧概念；固定 jitter 仍能打散条带 |
| `sceneDist` 地形遮挡 | 无（天空无地形） | 天空盒在天上 |
| `uStorm` / `uFlash` | 恒 0 | 本档是晴天 |
| `uMaxDist = 6500` 截断 + `fade` | 保留 | 地平线处云自然淡出 |
| 天空辐射 `uSkyView` 查表 | 直接调既有 `skyRadiance()` | 同源，避免再引入一张 LUT |

### 5.2 噪声输入（三个，全部在 Node 里生成）

| 产物 | 规格 | 生成方式 |
|---|---|---|
| `uNoiseTex` 2D | 256² RGBA | 复现 `shared/texgen.js` 的 `generateWaterTextures(size).noise` 四个通道（`pnoise`/`pfbm`/`pworley` 全为周期函数，天然可平铺） |
| `uCloudNoise` 3D | 96³ RGBA | 复现 `bakeCloudNoise()` 的 `uDetail=0` 分支（4 octave Perlin + 4 层 Worley 混合） |
| `uCloudDetail` 3D | 40³ RGBA | 同上 `uDetail=1` 分支（三层 Worley） |

⚠️ 上游用 `textureLod` + `RepeatWrapping` + `LinearFilter` ⇒ Node 侧必须实现
**三线性 + 环绕**，否则云会以硬边或重复纹理的形式暴露。

### 5.3 插进烘焙脚本

在 `buildFace()` 的「上半：纯大气 + 日轮」分支内，改为：

```
sky   = skyRadiance(dir, ...)          // 既有
{T, S} = marchClouds(camPos, dir, ...)  // 新增
rgb   = (sky × T + S) × bakeExposure    // 线性空间合成，再 srgb
```

天底半（`dir.y < groundBlend`）**不画云**——那里是地面。

**参考相机高度** `camY`：新增参数。它决定云在天空中的视在大小与「地平线处压缩」的程度
（`t = (CB − camY) / sin(elev)`）。取玩家典型眼高，使云底出现在 30~40° 仰角附近，
与用户截图一致。具体值在实现时按像素对照定，写进指纹。

### 5.4 参数（全部进指纹）

```
cloudCover: 0.35        // 用户 2026-11-27 裁定「照搬上游」
cloudDensity: 0.3       // ⚠️ 用户裁定：上游 1.0 实测单点密度 0.73~0.76 ⇒ 实心白块，降到 0.3
cloudGain: 0.15         // 云直射/环境的全局增益（**本仓新增**，上游 1.0）——见 §5.4.2
cloudSteps: 64          // 用户裁定 1024²×64
cloudMaxDist: 6500      // 上游 uMaxDist
cloudCamY: 12           // 玩家眼高量级（实现时定）
cloudGroundAlbedo: [0.13, 0.12, 0.07]   // 云底 ambBot 用（上游从 uBounce 取）
bakeTonemapExposure: 3.5               // AgX 前的前置曝光 —— 见 §5.4.2
CB: 336, CTOP: 585      // 上游常量，也进指纹（改它等于改云层高度）
```

### 5.4.1 ⚠️ `cloudCover` 的两种「覆盖率」必须分清（实测踩过的坑）

实现过程中我先报了一次错数：说「cover=0.35 实测得到 56% 覆盖率」，据此差点把
阈值区间下移。实情是：

| 指标 | 实测值 | 含义 |
|---|---|---|
| `mean(smoothstep 输出)` | **0.284** | **真正的平均覆盖率**（上游 cover 的本意） |
| `cov > 0` 的像素占比 | **55.6%** | 「有多少像素带一点云」（含极淡的） |

上游公式 `smoothstep(1-cover-0.2, 1-cover+0.26, n)` 两端都不饱和 ⇒ 均值被拖低到 0.284。
**这比 0.35 还低，所以阈值区间不需要下移。** 若按「均值 = 0.35」去重标，
区间会移到 0.395..0.855 —— 那是把云做得比上游**更满**，与用户裁定相反。

⇒ 结论：区间保持上游原样，只调密度。此结论已写进
`normal-sky-fingerprint.mjs` 的 `cloudCover` 注释，防将来被「修正」回去。


### 5.5 运行时

**零改动。** `assets/sky/normal/*.jpg` 换掉即可，`setupSky` 照常加载。

唯一需要复核的耦合：`materials.js` 的雾色采样会读这张立方图 ⇒ 云的亮部可能让
远景色偏亮。但雾色只在 `normalBlend=1`（普通档）时取第 5 套，其余档取前四套，
所以**不存在跨档泄漏**；普通档自身的雾色需要在实现后复核一次读数。

### 5.4.2 色调映射：为什么烘焙期必须换曲线

v3.47 的线性曝光 `×bakeExposure(0.55) → srgbEncode` 是**按无云天空标的**
（上半球 max 1.689）。加云后实测：

| 量 | 线性值 | 旧口径下 8bit |
|---|---|---|
| 天空背景 | 0.69 | 165 |
| 云（25° 仰角） | 14.8 | **255（削顶）** |
| 云（40° 仰角） | 25.9 | **255（削顶）** |

⇒ 云「顶亮底灰 + 亮边」的全部层次被压平成一块死白。
**处置**：烘焙期改用 AgX+punch（与运行时 `ASLAR_TONE_MAPPING` 同一条曲线），
并加前置曝光 0.25。曲线常量取自 `src/render/ashlar-tonemap-config.js`，不另立第二份。

⚠️ 运行时会对贴图**再压一次** AgX（贴图已是 LDR）。所以烘焙期取的是
「云刚好处在可分辨区且有可达余量」而非「显得刚好」—— 这是选 0.25 而不是 0.4 的理由。

⚠️ 这同时使 `bakeExposure` **只保留**给天底半的地面色反推（它按旧线性空间定标）。
两个曝光常量含义不同，同名会误导。

#### 5.4.2.1 两次标定失败及其根因（必须记住）

| 版本 | 参数 | 结果 | 根因 |
|---|---|---|---|
| 第一版 | 线性 `×0.55 → srgbEncode` | 云像素 lum **251.1**、整片纯白 | 云的线性亮度是天空 21~50 倍，线性 Exposure 无解 |
| 第二版 | AgX + E=0.25 | 黑得像黄昏（天顶 ~17 灰阶） | 探针拿 `[0.59,0.71,0.73]` 当天空——**那是已乘过 bakeExposure 的值**；真实值跨 0.14~1.21 |
| 第三版 | AgX + E=3.5 + gain 0.15 | 正确（已看图确认） | 用真实 `skyRadiance` 重新扫描；且缩小**云自身**量级而非整图曝光 |

⇒ 两条可复用结论：
1. **标定输入必须是同一函数在当前配置下的真实返回**，不能是「日志里看到的数」——
   日志里的数都已过某道缩放，而那个缩放正是要标的量。
2. 当两个量差 1~2 个数量级而存储只有 8bit 时，**缩小那个绝对的、与背景不同源的量**
   （云），不要继续降整图曝光（那会连背景一起拉黑）。

## 6. 验证策略

### 6.1 新增 Tier 4 用例「普通⑦：立方图里真的有云，且形态正确」

判据（全部基于**交付物文件**，不是实现细节）：

> ⚠️ 取行范围必须是**每面上半的 0~35%**，不能取到 50%。实测教训：旧的无云图在
> `y≈480`（地平面过渡带）有大量「亮且不偏蓝」像素 —— 那是天空→地面色的过渡。
> 取到 50% 会让旧图凭空获得 17.1% 的「覆盖率」与块 SD 33.1，判据几乎失效。

| # | 判据 | 新（有云） | 旧（无云） | 阈值 |
|---|---|---|---|---|
| ① | 云覆盖率（亮度 >130 且 `B−R<22`） | **40.5%** | 16.8% | 25~75 |
| ② | 云比天空亮的差值 | 73 | 59.6 | >18 |
| ③ | 32×32 分块均值标准差 | 35.5 | 27.2 | >28 |
| ④ | **高梯度像素占比**（|∇|>3） | **0.77%** | **0.04%** | >0.25 |
| ⑤ | 8bit 削顶占比 | 0% | 0.07% | <3 |

**④ 是主判别判据**（新旧差 **19 倍**），①②③ 只相差 1.2~2.4 倍。机理：体积云的**边缘**
是真正的高空间频率，而渐变天空（哪怕加日晕）相邻像素几乎不变。

⚠️ ④ 原来写的是「`gradP99 / gradP50` 比值」，**已实测退化**：平坦天空区在 JPEG 里被压成
相邻像素完全相同 ⇒ `p25/p50` 都是 **0** ⇒ 除数恒 0，判据变恒真（实测报 257）。改用占比。

### 6.2 既有用例「普通⑥接缝」必须仍然通过

云是**高频内容**，且会跨越立方图的 12 条共享边 ⇒ 这条从「形式检查」变成真检查。

⚠️ **判据可能要回调，理由要说清**：v3.47 那条最终用的是「绝对接缝 ≤ 白天基准」
（因为无云程序化图的噪声底太低，比值判据失效）。加了云之后，**面内与接缝都是
高频量化残差，分子的分母重新同源** ⇒ 比值判据恢复成立。若绝对判据在新图上超出
白天基准（云的高频内容天然量化误差更大），改为比值判据并**记录为何此时恢复成立**，
不放宽阈值了事。

### 6.3 负向验证（必需）

| 注入 | 必须真红的用例 |
|---|---|
| 用**旧的无云** `assets/sky/normal/*` 跑新 ⑦ | ① 覆盖率下限 / ③ 块 SD / ④ 高梯度 |
| 把云层的 `topFall` 梯度注掉（云变成上下等亮的色块） | ⑦ 的结构/梯度判据 |
| 某一面把方向整体偏移 1 像素（模拟方向数学写错） | ⑥ 接缝 |

每条注入后**读回源码确认注入落地**，还原用 `cp` 副本（**不用 `git checkout`**）。

### 6.3.1 已完成的负向验证（真实结果）

用 `git show HEAD:assets/sky/normal/*.jpg` 取出 v3.47 的**无云版**作对照（不碰工作树）：

| 注入 | 结果 |
|---|---|

## 7. 已知风险

| 风险 | 处置 |
|---|---|
| 云让天空过曝（`bakeExposure=0.55` 是按无云标的） | 实现后做削顶扫描，若削顶 > 2% 则重标曝光并**记录在指纹里** |
| 地平线附近云压缩成细条 → JPEG 咬出锯齿 | 1024²×64 步（用户裁定）；实测抽检 + ⑥ 的梯度判据兜 |
| 3D 噪声生成慢（96³ + 40³） | 一次性，秒级；不计入每面成本 |
| 指纹盲区：改烘焙算法不动参数 ⇒ 指纹不变 | 靠 ⑦ 的内容判据 + 负向验证兜（与 v3.47 同类，写入 pitfalls） |
| 普通档雾色读数变化 | 实现后复核；若变化显著，报告而不是擅自改其它档 |
| 云把天空糊死（实测过） | 上游 `uCloudDensity=1.0` 在天空盒尺度下太厚（单点 0.73~0.76）⇒ 已裁定降到 0.3 |
| **云的线性亮度把 8bit 打爆**（实测过） | 旧口径 `×bakeExposure(0.55) → srgbEncode` 必然把云削顶成纯白（实测云像素 lum **251.1**、顶亮底灰全失）。⇒ 改走 AgX+punch + 前置曝光 0.25（与运行时同曲线） |
| 把「平均覆盖率」误当成「cov>0 比例」（实测踩过） | 见 §5.4.1；结论已写进参数注释 |

## 8. Builder check（自审，无委派授权）

按要求的「实施者视角」逐条核对文档，抓到并已修的问题：

1. **原方案漏了 `computeSH`**：云的 `ambTop`/`ambBot` 依赖 SH 辐照度，而上游是
   在 `Sky.update()` 里按 `sun/moon/cover/storm` 算的。文档初稿只写「调 skyRadiance」，
   实施时会拿不到环境光。已补 §5.1 的 `computeSH` 与 §5.2 的依赖关系。
2. **`uNoiseTex` 与云的两个 3D 体不是一回事**：`cloudWeather` 用的是 2D `.b` 通道，
   来自 `generateWaterTextures().noise`，与 `bakeCloudNoise()` 无关。初稿把三者并列，
   容易被实现成「一个 3D 体全包」。已拆成 §5.2 的两类，并标明 2D 体用的是四个通道中的哪个。
3. **天底半不能画云**：`t = (CB − camY)/sin(elev)` 在 `elev<0` 时无解；若实现时
   按「上半球画云、下半球填地面色」之外的顺序处理，会出现地平线以下也飘云。已明确 §5.3。
4. **接缝判据的前提变了**：v3.47 用绝对判据是因为无云图噪声底过低；加云后
   分子分母重新同源，比值判据恢复成立。若不写清，实施者会照抄旧判据然后困惑。已补 §6.2。
5. **`cloudCover` 有两个上游默认值**（`00_core.js` 0.45、`90_demo.js` 0.45、
   参考截图 0.35）。文档必须钉住用户裁定的 0.35，否则实现者会去读源码取 0.45。已钉 §5.4。
6. **雾色耦合**：初稿说「运行时零改动」就完了，没提 `materials.js` 的雾色采样也读这张图。
   已补 §5.5 的耦合说明与复核项。
