## Task 1：纹理/几何派生模块（前提：臂方向必须来自 TEMPLATES）

**问题**：烘焙脚本（node）要推导「每个栏杆件每个朝向给出哪些臂」，而形状权威在
`src/mesh/mesher.js` 的 `TEMPLATES`。`mesher.js` 依赖 `faces-data.js`（纯数据），
可以 node 侧 import（`build-atlas.mjs` 已 import 过 `TEMPLATES` 的先例，见
`tests/test-iso-icon.js`）。

**做法**：`tools/bake-arena.mjs` 直接 `import { TEMPLATES } from '../src/mesh/mesher.js'`，
用一个纯函数 `railArmsOf(quads)` 从 quad 顶点推导臂方向，再用一个**复刻 `rotateOffset`
的本地实现**旋转 —— ⚠️ **必须与 `mesher.js` 的 `rotateOffset` 逐位一致**；
若将来改动该公式，两侧会漂移出「烘焙写 orient=1、渲染转到另一个方向」的静默缺陷。

**消除漂移**：在 `src/mesh/mesher.js` 里把 `rotateOffset` 加 `export`（**零行为变化**），
烘焙脚本 import 同一份。

## Task 2：指纹共享模块

`tools/arena-fingerprint.mjs`：

- `ARENA_SOURCES`：`{ arenaGrass: 'arena1.schematic' }`（本轮只一项）
- `BLOCK_MAP`：源方块名 → 本仓方块名（`null` = 丢弃）。**未知名 throw**。
- `CONTENT_DROP`：`['air', 'barrier', 'bedrock']`（语义同 `BLOCK_MAP` 的 null，但单独一套

  常量) —— 与 `giant-pyramid-fingerprint.mjs` 同手法
- `check:data` 与 `bake-arena.mjs` **共用这一份**（红线 1）

**验收**：`node -e "import('./tools/arena-fingerprint.mjs').then(m=>console.log(m.ARENA_EXPECT))"` 输出正确。

## Task 3：烘焙脚本

`tools/bake-arena.mjs`（`npm run arena`）：

1. gunzip + `NbtReader`（复用 `tools/nbt-reader.mjs`）
2. 逐格遍历 → 丢弃 `CONTENT_DROP` → 按 `BLOCK_MAP` 映射（未知名 **throw**）
3. 求内容包围盒；`floorRow` = 包围盒最低层（归一化后为 1，显式写入）
4. 生成栏杆环：环的位置 = 内容包围盒外扩 `RAIL_RING_INSET`；对环上每格求臂集合；
   反查 (方块, orient) —— 查不到 → **throw**
5. 坐标归一化（x/z 以包围盒中心为 0；y 以最低层为 1）
6. 写 `assets/structures/arena_grass.json`：
   `{ palette, stride: 5, floorRow, blocks: [x,y,z,idx,orient, ...] }`
7. 写 `assets/structures/arena.meta.json`：`{ version, source, width, depth, height,
   floorRow, contentCells, floorCells, railCells, fingerprint }`

**产物形状约束**：`palette` 只包含 `BLOCK_MAP` 的**值**（本仓方块名）；
`check:data` 会双向断言 palette ↔ `BLOCK_MAP` 值集合。

**验收**：
- `npm run arena` 退出码 0
- 产物 `blocks.length / 5` == `contentCells + railCells`（3991 + 栏杆格数）
- 两次运行 sha256 相同（确定性）

## Task 4：锚点纯函数

`src/gen/structures/arena.js`（新，**Worker 同构、无 three、无 fetch**）：

```js
export const ARENA_WIDTH = 41;        // 含栏杆环
export const ARENA_DEPTH = 79;
export const ARENA_HALF_X = 20;
export const ARENA_HALF_Z = 39;
export const ARENA_MAX_SURFACE_SPAN = 10;
export const ARENA_MAX_GAP = 240;
export function computeArenaAnchor(seed)  // → {wx, wz, floorY, maxH, span} | null（seed 缓存）
export function inArenaFootprint(wx, wz, anchors)  // 与 giant-pyramid 的 inGiantPyramidFootprint 同签名
export function arenaOverlapsRegion(anchor, regionX, regionZ) // layout 层裁剪：只在与本 region 相交时携带
```

判据（见 spec DR-4）：城市 bounds / 地标圆 / 局部巨型金字塔 / 高台地带 / 雪原 /
100% 干燥 / 高差 ≤ `ARENA_MAX_SURFACE_SPAN`。扫描顺序：南门 x 为基准，dz 递增。

### RED（`src/tests/test-arena.js`）

1. `确定性`：`computeArenaAnchor(12345)` 深比较两次结果相同
2. `干燥`：默认 seed 的锚点上，占地内每格 `generateHeight >= SEA_Y`
3. `高差`：`maxH - floorY <= ARENA_MAX_SURFACE_SPAN`
4. `不压城市`：占地 AABB 与 `getCityBoundsForSeed(seed)` 不相交
5. `不压地标`：对 3×3 邻域全部 `regionLandmarkCenters` 逐个断言不相交
6. `不压高台地带`：地带的圆不被占地压到
7. `floorY 是最低点`：`floorY === min over footprint generateHeight`
8. `向南`：`anchor.wz > city.maxZ`（南门方向）

### GREEN

实现如上。缓存用 `Map<seed, result>`（容量上限 64，LRU 淘汰）；
**注意纯函数性** —— 缓存只存结果，不改任何输入。

## Task 6：`check:data` 的 `[竞技场]` 契约

`tools/check-data.mjs` 新增 `checkArena()`，并入成功行的判定（既有教训：
「新判据必须并入成功行的打印条件」，否则会出现「报了错但屏幕上仍有 ✓」）：

- 烘焙输入存在 + 产物存在
- **指纹匹配**（覆盖源字节 + `BLOCK_MAP` + 常量）：不匹配 → 「跑 npm run arena」
- `stride === 5`
- `palette` 只含本仓已注册方块名（`blocks-data.js`），且**不含** barrier/bedrock
- `palette` 的值集合 == `Object.values(BLOCK_MAP)` 去掉 null（双向）
- 产物 `width × depth` == `ARENA_EXPECT`；`floorRow` 指向的层恰好铺满 `41×79 - 栏杆格`
  … 具体数字由产物自身推导（不硬编码，避免第二份权威）
- **栏杆环闭合**：环上每格恰好 2 个环邻居
- **臂-朝向匹配**（核心判据，与单测同源，调 `railArmSet`）
