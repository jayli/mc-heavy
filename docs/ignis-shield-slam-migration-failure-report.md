## 一、根因：把「几何形状像砸地」当成了「这招是砸地攻击」

整条决策链只回答了**「盾在空间里怎么走」**，从未回答**「这招在原版里是干什么用的」**。
三个本该一票否决 `SMASH` 的语义证据，两轮调查一个都没查（§2.6~2.8）：

1. **剑指向**：`SMASH` 的 1 秒静止段里剑**斜举在头顶上方、指向前上方**（仰角 16.8°，剑尖高于头顶 0.307 格），
   收势时剑**水平正指前方**（前方分量 0.998）—— 这是**号令姿态**，不是任何一种劈砍的收势。
2. **招式衔接**：`SMASH` 首关键帧是 `startKeyframe(0)`（瞬间到位），且与 `SMASH_IN_AIR` 第二关键帧
   **逐轴最大差 0.000°** ⇒ 它是**接在跳起段后面的下半段**，不能独立成招。
3. **伤害来源**：`SMASH` 的伤害全部来自 `ShieldSmashparticle` / `ShieldSmashDamage`（**地面掀起的飞石**），
   `sword` 骨骼**根本没被这条动画驱动** ⇒ 伤害与剑无关，「盾砸地」的观感全靠粒子/震屏，而那些按裁定③全去掉了。

**而度量口径错误是让这个决策失误得以发生的工具**：调查用一个**虚构的单点探针** `shield` 局部 `[0, +16, −3]`
代表「盾下缘」，而盾的真实几何在 y 方向只到 **±8 px**（`+16` 落在盾体外 **8 px = 0.5 格**）。
这个点**不在盾上**，且盾在动画里大幅翻转 ⇒ 它读出的「最低/最高」**与盾的真实包围盒无关**。

于是：

| 招式 | 单点探针读数（错误口径） | 盾真实几何（32 角点） | 被误判成 |
|---|---|---|---|
| `SHIELD_SMASH_ATTACK`（用户要的） | 最低 0.368 / 最高 **2.087** 格 | 最低 0.650 / 最高 **4.291** 格 | 「盾从未下压、举不过头顶」❌ |
| `SMASH`（实际做的） | 最低 0.038 / 最高 3.620 格 | 最低 **−0.951** / 最高 4.965 格 | 「高举过顶砸到贴地」✅ |

**`SHIELD_SMASH_ATTACK` 的盾真实最高点是 4.291 格，而头顶只有 3.09 格 —— 它明确地举过了头顶。**
单点探针把这个数字压到 2.087 格（**少报 2.204 格**），才得出「它不是举盾动作」的结论。
这一个错误读数就是整条错误链的起点。

### 2.6 【v2 新增·决定性】剑的指向：`SMASH` 是号令动作，不是攻击动作

两轮调查**从未测过剑**（`sword` 骨骼一次都没进探针）。补测后（剑柄→剑尖单位向量，前方 = −z）：

| t(s) | 指向 x | 指向 y | 指向 z | 仰角 | 剑尖高于头顶 | 姿态 |
|---|---|---|---|---|---|---|
| 0.00 | 0.840 | −0.385 | 0.383 | −22.7° | −0.016 格 | 剑拖在身后（衔接姿态） |
| 0.20 | −0.108 | 0.781 | −0.615 | **51.4°** | **+2.316 格** | **剑高举过头顶 2.3 格** |
| **0.40~1.40** | −0.898 | 0.290 | −0.331 | **16.8°** | **+0.307 格** | **斜举指向前上方，静止 1 秒** |
| 2.00 | −0.042 | 0.054 | −0.998 | **3.1°** | −2.029 格 | **水平正指前方（前方分量 0.998）** |

**这就是「统帅挥剑指向前进方向、号召军队进攻」**：剑高举 → 斜举定格 1 秒 → 水平指向前方。
那 1 秒静止段在初版报告里被我描述成「盾压地不动 1 秒」，**实际上剑一直举在头顶上方指向前方** ——
**「定格展示一个指向」正是号令动作的典型结构**，攻击动作不会这样停。

对照 `SHIELD_SMASH_ATTACK`（用户要的）：剑全程**没有举过头顶**，剑尖 y 始终在 0.45~1.35 格（腰腿高度），
随身体前压而摆动 ⇒ 主角是**盾**，剑只是跟着身体走。两招的**主体部件不同**。

### 2.7 【v2 新增·决定性】`SMASH` 是 `SMASH_IN_AIR` 的下半段，不能独立成招

```
SMASH 关键帧结构：startKeyframe(0) → startKeyframe(8) → setStaticKeyframe(20) → resetKeyframe(15)
                  ↑ n=0：瞬间到位，不是从静止缓入
```

实测 **`SMASH` 首关键帧 vs `SMASH_IN_AIR` 第二关键帧：共有骨骼 7，逐轴最大差 `0.000°`**
⇒ `SMASH` 的起手姿态**就是跳起段的保持姿态**，它是**连招的下半段**。

`SMASH_IN_AIR` 的剑轨迹（本仓完全没接）：t=0 水平指前方（前方分量 **1.000**）→ t=1.2 仰角 40.5° 举剑
→ t=1.5~4.5 **定格 3 秒**（仰角 −22.7°）→ t=5.25 回到水平指前方。
**跳起段才是「号召」的主体**（3 秒定格），`SMASH` 只是落地收尾。

⇒ 本仓只接 `SMASH`、用自有 leap 物理代替 `SMASH_IN_AIR`，等于**把一个连招的下半段单独拿出来当独立招式**，
起手必然突兀（这也解释了 §4.4 里「只有一个起手式」的实玩反馈）。

> 这条判据**早在 v3.01 就有现成工具与先例**：`memory/reference-cataclysm-java-source-for-ignis` 明确记着
> 「Bedrock 导出的 t=0 帧未必是静止姿态，可能是原版 `startKeyframe(0)` 的连招衔接姿态」，
> 旋斩（v2.76）正是因此才在渲染层补衔接。**同一个坑，这次没查。**

## 四、过程失误清单（按危害排序）

### 4.0 【v2 新增·最严重】只验「几何形状」，不验「原版语义用途」

候选筛选的全部判据是「盾下缘最低 y / 最高 y」——**纯几何**。从未查过：
这招在原版由哪个 goal 触发、接在谁后面、伤害由什么提供、剑在做什么。
§2.6~2.8 三条中**任何一条**都能一票否决 `SMASH`，而它们的取证成本都很低：

| 本该做的核对 | 成本 | 结果 |
|---|---|---|
| 打印 `SMASH` 关键帧结构（`startKeyframe(0)`？） | 一行 | 立刻看出是连招下半段 |
| 与 `SMASH_IN_AIR` 保持段比首帧 | 复用现成 parse，10 行 | 0.000° ⇒ 衔接姿态 |
| 把 `sword` 加进探针 | 探针已有的 `PROBES` 里**本来就有 `sword_tip`** | 剑高举指前方 ⇒ 号令动作 |
| 读 `SMASH` 的 `aiStep` 分支看伤害来源 | 一次 read | 伤害来自地面飞石，与剑无关 |

**最刺的一点**：`tools/ignis-java-reference.mjs` 的 `PROBES` 常量里**早就有 `sword_tip` 和 `sword_grip`**，
盾的探针是本次新加的。**现成的剑探针没被用，新加的盾探针取错了点。**

### 4.1 用错误度量把错误目标写成了门禁

`src/tests/test-ignis-bake.js:1152` 起的用例：

> `shieldSlam 是盾砸地 —— 盾下缘触地(<0.15格) + 高举过顶(>3.0格) + 落差>3.0格`

而 `shieldBottomY()`（同文件 :1180）用的正是那个虚构单点 `[0, 16, -3]`。
后果：**「盾必须触地」被固化成永久断言**。用户要的那一招（不触地、向前砸）**在这个门禁下必然红**。
错误目标从此有了「测试保护」，越修越难回头。

### 4.2 度量口径错，且没有第二口径交叉验证

- 单点探针不在盾体上（§2.2），这一点**只要打印盾的立方体 y 范围就能发现**，成本一行代码。
- v3.01 的教训明确写着「临时探针必须复用已验证口径」，本次**确实复用了 `probePoints` 的矩阵链**（bind 自校验 0.01px 通过），
  于是产生了「探针已验证」的安全感 —— 但**验的是矩阵链，没验探针点选得对不对**。
  **矩阵链正确 ≠ 取样点正确**，这是本次新踩的坑。

### 4.3 把「像不像砸地」简化成「盾有没有到 y≈0」

用户说的是「举起盾牌**向前砸向玩家**」，判据却只看**竖直最低点**。
`z`（前伸量）从未进入判据 —— 而它恰恰是两招的**决定性差别**：
`SHIELD_SMASH_ATTACK` 前伸 1.477 格且持续推进；`SMASH` 前伸 1.288 格且砸下时**后退 0.68 格**。
**只量 y 不量 z，等于把「向前」这个核心语义整个丢掉。**

### 4.4 三次实玩反馈都归因到「参数」，没有一次归因到「选错招」

| 用户原话（会话记录） | 当时的归因 | 应有的归因 |
|---|---|---|

### 4.5 「配对鉴别 0.000°」被当成了「迁移正确」的证明

`SMASH ↔ attack9Sa` 关键帧逐轴最大差 **0.000°** 是真的，本次复核也成立。

## 六、事实与推断的分界

**实测事实**（本次重跑，可复现）：
- `SMASH` 静止 1 秒段剑仰角 **16.8°**、剑尖高于头顶 **0.307 格**；t=2.0 前方分量 **0.998**（水平正指前方）。
- `SMASH` 首关键帧 `startKeyframe(0)`，与 `SMASH_IN_AIR` 第二关键帧逐轴最大差 **0.000°**（共有骨骼 7）。
- `SMASH_IN_AIR` 有 **3.00 秒**静止定格段；`attack9Sa` 与 `attack1` **都不驱动 `sword`**。
- `SMASH` 伤害由 `ShieldSmashparticle`（:1665，地面方块粒子）+ `ShieldSmashDamage`（:1704，脚下地面飞石）提供。
- 盾真实半高 8px；单点探针 `y=+16` 不在盾体上，不是任何角点。
- `SHIELD_SMASH_ATTACK` 盾最高 4.291 格 / 前伸 1.477 格 / 下压 1.204 格 / 不触地。
- `SMASH` 盾最低 −0.951 格 / 砸下时 z 后退 0.68 格 / 砸下段约 180ms + 贴地静止约 1s。
- 产物 `shieldSmash` 与原版逐项吻合（4.290 vs 4.291；1.454 vs 1.477）。
- 探针 bind 自校验 0.01px。

**用户判定的采信**：「`SMASH` 是统帅挥剑指向前进方向、号召军队进攻的指向性动作，不是攻击性动作」
—— 用户 2026-11-15 明示。本报告 §2.6~2.8 的三项实测**与该判定一致**，故按事实采纳，不再列为待确认推断。
（严格说：原版代码仍把它挂在 `AttackAniamtionGoal3` 上并带 `AreaAttack`，所以它**在原版是有伤害的**；
但**动画语义是号令/指向**，伤害靠地面飞石而非武器挥舞 —— 两者不矛盾，用户的观感判定成立。）

**推断**（有据但非直接实测）：
- 「用户要的是 `SHIELD_SMASH_ATTACK`」—— 依据是用户原话「举起盾牌向前砸向玩家」与该招三段轨迹（举过顶 / 前推 1.48 格 / 下压 1.20 格）逐项对应，
  且 `SMASH` 在砸下时**后退**、方向相反。**建议由用户确认一次**再决定后续动作。
- 单点探针失效是「误判 `SHIELD_SMASH_ATTACK` 不是举盾动作」的**直接原因** —— 依据是错误读数 2.087 与
  spec/会话记录里的数字**逐位一致**，可确认当时用的就是这个口径。

**未做**：任何代码修改、任何提交、任何推送、任何产物重烘焙。
