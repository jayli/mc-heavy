# 测试分级策略（harness 分级规范）

> 本文是**测试分级的唯一权威**。CLAUDE.md 的「测试工作流」章节引用本文，不再自述分级细节。
> 定稿日期：2026-09-03（第一阶段 M0~M3 收尾后、M4 开始前）。
>
> **制定动机**：此前全部改动一律走 RED-GREEN-REFACTOR，连「改一个贴图地址」「修正一个 alias
> 映射」都要先写失败测试。这类改动的正确性肉眼即可判定，TDD 只增加成本不增加保障。
> 本文把测试要求按**改坏后的可发现性与修复成本**分级，把 TDD 投入集中到底层机制。

---

## 1. 分级判据

分级的唯一判据是：**改坏了会发生什么、多久能被发现**。不是「改动大小」，也不是「文件位置」。

| 级别 | 改坏了会怎样 | 发现方式 | 修复成本 | 测试要求 |
|---|---|---|---|---|
| **Tier 1** | 静默的数据错误 / 性能回退 / 架构红线回退 / 跨模块契约破裂 | **肉眼玩不出来的**，只能靠断言 | 高（污染存档、破坏确定性、要回滚） | **必须 TDD** + 门禁 |
| **Tier 2** | 约定值不一致（集合口径、资源引用悬空） | 立刻可见（图标空槽、方块消失） | 低（改回去） | **需要门禁断言，免 TDD 流程** |
| **Tier 3** | 观感/文案不对 | 立刻可见 | 极低（改回去） | **免测试** |
| **Tier 4** | GPU 渲染结果不对 | 单测测不到（TSL 节点在 GPU 求值） | 中 | **像素级实测**，不宣称目视验证 |

**核心原则**：越底层越要保护，越表层越不要保护。判据不是行数，是「错误能否逃逸到玩家手里且不被察觉」。

## 2. Tier 1 — 必须 TDD（机制性 / 架构 / 性能 / API / 稳定性）

### 2.1 适用范围

| 类别 | 具体对象 | 为什么必须 TDD |
|---|---|---|
| **纯函数算法** | `mesh/mesher.js`、`mesh/lighting.js`、`mesh/iso-icon.js`、`player/raycast.js`、`player/physics.js`、`gen/terrain.js`、`gen/caves.js`、`gen/structures/*`、`player/orientation.js` | 输出是 typed array / 顶点缓冲，错了肉眼看不出来（AO 算错、面剔除漏面、洞穴连通性断裂、朝向旋转错位），会静默污染渲染与存档 |
| **版本协议 / 竞态** | `voxel/chunk-column.js` 的 columnVersion、`core/scheduler.js` 队列语义、`core/worker-pool.js` RPC | 竞态错误只在特定时序出现，玩十局可能都不复现；红线 7 明确「禁止为竞态打补丁」，必须有断言钉住协议 |
| **数据模型契约** | `player/inventory.js` 的 `Slot`/`Inventory` 语义、`save/persistence.js` edits round-trip、`voxel/block-registry.js` 注册序 | 语义错了会污染存档（红线 2「存档只存 edits diff」）；`registry.all()` 顺序是物品集合的权威，错序会让快捷栏错位 |
| **性能冻结断言** | `src/bench/baseline.mjs` + `npm run bench -- --check`、fps/draw call/编辑 p95 | 性能回退是**渐进**的，单次改动看不出，累积到掉帧才发现。红线 3「重计算离开主线程」靠这些断言守住 |
| **架构红线** | 12 条重构红线的静态特征（依赖方向、禁止类名、workers 不 import three、gen/mesh 同构） | 红线回退是 mc-lite 病根的复活路径，**代码能跑但架构已死**。必须有静态门在改动当场拦住 |
| **跨模块 API** | `world.getBlockMeta()`、`WorldEditor.setBlock(id, meta)`、`registry.orientationModesTable` | 多个消费者共用同一签名，改坏了下游静默拿到错值（M3.2 就踩过：Task 6 若退化为只传 id 会丢朝向） |

### 2.2 TDD 流程要求（Tier 1 不变）

1. **RED**：先写失败测试 → 2. **验证 RED**：运行确认按预期失败 → 3. **GREEN**：最小实现
→ 4. **验证 GREEN**：全部通过 → 5. **REFACTOR**：重构保持绿。

测试一开始就通过，说明测试写错了或在测已有行为。**RED 阶段不得把新测试从 `src/tests/index.html`
临时移除来「通过」**（M4 plan Task 1 Step 2 已写明这条）。

### 2.3 冻结断言纪律（Tier 1 专属）

计划中标注「冻结」的断言数字（draw call 数、fps 阈值、p95 上限、`setGeometryAt` 阈值）
实测不符时 **停下来报告，不要擅自改断言或静默放宽**。

计时类断言 flaky 时的正确做法（本项目已三次踩坑，见 CLAUDE.md 实施记录）：
**分开按 spec 连跑拿数值分布，比均值与峰值** —— 仅凭「全量跑失败 / 单独跑通过」判定不够，
全量跑时不同 spec 会轮换失败，容易误读成「改动侧统计显著」。v1.24 实施时 HEAD 侧失败率
反而更高（3/4 vs 2/4），若只看全量跑就会得出相反结论。

**更可靠的做法是交替对照**（v1.29 建立）：改动侧 N 次 → `git stash` 到 HEAD → HEAD 侧 N 次
→ 反复，最后比数值分布而非失败计数。单侧连跑会让**后跑的一侧承担更高负载**（机器负载累积），
得出「改动侧更差」的假结论。v1.29 实测：`m1-acceptance` 的 `placeP95` 两侧分布完全重合
（改动侧 `1.7/2.0/1.9/1.8`、HEAD 侧 `2.0/1.7/1.8/1.9`），且 **HEAD 侧失败率反而更高**
（改动侧 3 通过 1 失败 vs HEAD 侧 1 通过 3 失败）。注意 stash 前须把未跟踪的新测试文件
移出 `tests/`（`git stash` 不处理未跟踪文件，留着会让 HEAD 侧跑不到改动侧的新用例）。

### 2.4 时序不定的竞态：断言落在内存侧，不要落在重载后的落库结果上（v1.29 建立）

竞态类改动（Tier 1）的测试**不能只断言「重载后数据正确」** —— 若该竞态的暴露时机本身
不确定，端到端断言会碰巧读到正确值而让缺陷静默逃逸。

**v1.29 实测案例**（`Game._discardEdits()` 清内存 edits 那步）：`beforeunload → flushNow(world)`
的 IndexedDB 事务能否提交取决于卸载快慢 —— 对照脚本只差一个变量（reload 前是否多一次
evaluate 往返）：给事务一点时间则确实写回（`savedColumns` 0→1，缺陷暴露）；紧跟
`location.reload()` 立即卸载则事务来不及提交就被中止（读回 0，**缺陷静默逃逸**）。

**负向验证是这类断言的必需环节**：把被保护的那一步临时移除，确认测试**真的 FAIL**。
v1.29 实测：移除 `col.edits.clear()` 后 → 内存断言 FAIL（`memEdits` Received 1）、
端到端断言仍 PASS。这印证了两条断言的职责分工：**内存断言才是门禁，端到端断言只是佐证**。

判据：被保护的不变式在**同步可观测的内存状态**上有没有对应断言？只断言异步/重载后的
最终落库结果 = 门禁缺失。

### 2.5 生成类代码的测试落点：必须过完整优先级链筛选（v1.30 建立）

给 `gen/**`（terrain / structures / vegetation）写测试时，**落点坐标不能只按数据条件筛**
（biome + 高度 + 随机数阈值），必须复现生成器的**完整优先级链**后再筛 —— 否则选中的点
可能根本不触发被测分支，写出**恒真或恒假的测试**。

**v1.30 实测案例（沼泽 lilypad）**：`apply.js` 的植被循环先调 `pointContext(wx, wz, ...)`
拿 `ctx.kind`，再按 `kind === 'water' && biome === 'SWAMP' && seededRandom(...) < 0.08`
放 lilypad。但 `pointContext` 内部有 **city / island / pyramid / plainLand / snowLand /
frozenMountain 六个地标判定，全部在 water 分支之前** —— 被任一地标覆盖的点 `ctx.kind`
就不是 `'water'`，直接跳过 lilypad。

只按三条件筛出 **12 个「候选点」**，完整 GEN 后 **落地 0 个**（全被 `clay`/`sand` 地标方块
覆盖）。若直接拿其中一个写测试，断言 `blocks[SEA_Y+1] === lilypadId` 会**恒假**（该格根本没
生成 lilypad），而 RED 阶段看起来「正是我预期的失败原因」→ GREEN 后仍失败，误判成实现没修对。

**正确做法（三步，实测有效）**：
1. 写廉价脚本**复现优先级链**（只 import 地标查询函数判 kind，不做光栅化）扫出真实落点；
2. 对候选落点跑**完整 GEN 流程**（`fillColumn → carveCaves → applyStructuresToColumn`，
   与 `world-worker.js:42-44` 同构）确认方块真的落地；
3. 才把该坐标写进测试常量，并在注释里记录**为什么必须过优先级链**（防后人照直觉换落点）。

判据：测试里出现的坐标常量，是「按数据条件推出来的」还是「跑过完整生成流程验证过的」？
前者在有多级分支覆盖关系的生成器里几乎必然踩坑。

**同源坑的另一面：测试里硬编码「被测代码写入的那个值」**。v1.30 同一批测试里还踩到
第二种恒真路径 —— 测试用 `SEA_Y + 1` 算叶面高度，而 `SEA_Y + 1` 正是 `apply.js` 写入的
生成格位 → **测试与被测代码共用同一个假设**。实测证实：把格位回退成 `SEA_Y`（bug 状态）后
该测试**仍 PASS**（拿硬编码值算出「叶面 -1.48 > 水面 -1.50」），缺陷静默逃逸。
修法：**从实际生成数据里读出真实格位**（扫 column 找 lilypad 的 y）再算派生量，
并补一条前置断言钉住前提（「水面格 `y=SEA_Y` 须仍是水」）。重做负向验证后该测试转 FAIL。

判据同 CLAUDE.md 的「对照脚本与被测代码必须只差那一个要考察的变量」，只是主体换成测试自身：
**测试里出现的每个派生量，其输入是「从被测产物里读出来的」还是「抄了被测代码的常量」？**
后者会让「值错了但关系式对」的缺陷恒过。

### 2.6 断言落点的六类踩坑（历次改动沉淀）

前四条都是「测试写了但抓不到缺陷」的路径 —— 全绿比失败更危险，因为它给出虚假信心。
后两条（⑤/⑥，2026-09-20 天空树评审与二次审核沉淀）是**同一类根因的两个变体**：
断言与机制论证**先于实测**（描述的是想象中的世界）。

**① 计时类断言 flaky 须用交替对照判定，不能只看「全量跑失败 / 单独跑通过」**

`m1-acceptance` 的放挖 p95（阈值 2ms）与 `frameMs.p95`（阈值 16.7ms）在高负载下偶发贴线。
判定口径：

- **分开按 spec 连跑**，拿数值分布比均值与峰值 —— 仅凭「全量跑失败、单独跑通过」不够；
- **并发跑测试会导致计时断言系统性失败**（争抢 CPU 与端口 8081）；
- 更可靠的是**交替对照**：改动侧 N 次 → HEAD 侧 N 次 → 反复，消除机器负载累积带来的顺序效应
  （单侧连跑会让后跑的一侧承担更高负载）。

实测出现过 **HEAD 侧失败率反而更高**的情况（HEAD 4/4 全失败 vs 改动侧 2/4），只看全量跑会
得出「是我的改动引入回退」的相反结论。机制相关性判据 = 改动是否命中被测热路径
（排斥力在 worker AI，不碰放挖热路径 / mesher / scheduler / physics → 不相关）。
**不得为了让测试通过而改断言或放宽阈值**。

**② 重载类断言的导航监听必须在触发动作之前武装**

`waitForLoadState('load')` 写在 click 之后会看到「当前页已是 load 态」立即返回，随后 `READY`
在**旧页**本就为真 → 读到动作前的世界。正确写法：

```js
const nav = page.waitForNavigation(...); // 先建 promise
await triggerAction();                    // 再触发
await nav;                                // 最后等
```

**③ 测试指纹口径须匹配改动范围**

`i += 997` 步长采样只适合「换 seed」类整片变化；**单格改动必须全量求和**
（实测踩坑：基线与改动侧同为 50533 → 断言恒真，改坏也测不出来）。

**④ 时序不定的竞态只能用内存侧断言钉住，端到端断言会让缺陷静默逃逸**

实测：`beforeunload → flushNow` 的 IndexedDB 事务能否提交取决于卸载快慢（多一次 evaluate
往返则提交；紧跟 `location.reload()` 则被中止），故重载后的 `savedColumns` **碰巧**可能读到
正确值（负向验证实测：注释掉清内存那步，E2E 仍全绿）。写竞态防护的测试时，断言要落在
**同步可观测的内存状态**上，不要只断言重载后的落库结果。

**⑤ 新写的断言必须先在真实数据上跑一次、打印实际值，再决定断言写成什么**

（2026-09-20 天空树评审沉淀，[`reviews/2026-09-20-sky-tree-review.md`](superpowers/reviews/2026-09-20-sky-tree-review.md)）。
两处阻断级缺陷都是「断言描述的是想象中的世界」：

- 「每棵树 4 格树干、每格都是 `sky_wood`」—— 实测 **21.4%** 的树干格被后写树冠覆盖
  （`makeColumnSetter` 无占用格守卫，后写胜）→ 断言必然 FAIL；
- 「树干底格下方是 `sky_grass`」当作圆判据漂移的护栏 —— 实测 **0/300** 个岛会因半径-1 而 FAIL
  （**无检验力**，注入缺陷也照样全绿）。

与既有的「不凭感觉宣称通过」「出现机制上不可能的数值时先怀疑脚本本身」同源。

**配套：坐标类判据一律用非负取模 `((wx % 16) + 16) % 16` 或直接按足迹判** —— `wx % 16` 在 JS 是
**取余**，本仓库世界无边界、负坐标是常态 → `Math.min(wx % 16, 16 - (wx % 16))` 这类「到最近边界距离」
的判据在负坐标下**恒真**（实测踩坑：跨 column 选点退化成「取第一棵树」，而那棵不跨界 → 用例归零）。
修法优先「直接枚举足迹算 column 集合」（以用例需要的前提为判据，不需维护位运算直觉）。

**⑥ 凡论证「A 优化与 B 优化等价/不冲突」，须在 A、B 各自的参数取值下分别实测一遍**

（2026-09-28 天空树二次审核沉淀，spec §9.2）。这类错误的形态特别隐蔽：**不是**数值错、
也不是引用错，而是一句听起来完全合理的机制推理。实例：`vegetation.js` 的 `surrounded`
生成期跳过被论证为「反正都会被 mesh 剔除，早跳晚跳一样」—— 实测**方向相反**：
cutout（`opaqueTable=0`）下跳过省 6 面/格，opaque（`opaqueTable=1`）下跳过反而多 6 面/格
（region[-1,1]² 净增 32,430 面 / +2.8%）。错在**没区分通道** —— 而当时正在改的就是那个参数。
与⑤同源（都是「先跑一遍再下结论」），但落点是**设计论证**而非测试断言，故单列。

### 2.7 负向验证的盲区高发区（M6 实测 15 条无效盲区；M7 新增第 10/11/12 类；v1.65 新增第 13 类；RedCity 新增第 14/15/16 类）

负向验证 = 注入缺陷后断言必须真 FAIL。**每条若「注入后仍全绿」，先怀疑断言落点而非实现**。

七类高发区：

1. 门控落点落在未加载 column → 别道门控先拒绝，被测门控不被触发；
2. 断言读内存值而注入改的是实例矩阵；
3. fixture 显式传参覆盖了被测的默认参数 → 默认值路径无覆盖；
4. fake 依赖立即完成 → 「在途」类断言不触发；
5. 测试用 dt 恰等于步长 → accumulator 恒 0；
6. worker 代码只在真游戏页加载，单测页跑不到 worker 注入；
7. **测试输入从被测常量派生**（`micro = EPSILON / 2` → 注入把常量改成 0 时输入也变 0 →
   断言恒真；须用字面量 + 前提断言）。

另两类（v1.37 / 2026-09-09 新增）：

8. **特征方块跨结构重叠** → 断言恒真（撒布结构测试踩坑）；
9. **像素取样点没对准被测图案的位置** → 注入「图案画错区域」仍全绿。丧尸头部 Tier 4 实测：
   顶面/侧面取样点落在格 4 而眼睛在格 3。根因是三个面 `buildPlane` 的 `vdir` 符号不同
   （正面/侧面 `-1`、顶面 `+1`），同一套「世界坐标 ← 归一化 u/v」公式会在某些面把 v 反向、
   偏一格 → 跨面取样须用**纹理坐标**作统一参数，各面按轴向换算。

另三类（M7 实测新增，2026-09-10）：

10. **断言所测的输入被下游校验兜住** → 注入上游校验后仍全绿。M7 蓝图测试踩坑：注入「去掉未知
    方块名校验」仍全绿，因为该测试的蓝图**只有一个方块且它就是最高格** —— 下游的「最高格不是
    gold」校验会兜住它并抛错，断言恒真。**修法**：让被测缺陷落在**不会被下游兜住的位置**
    （未知名字放非最高格、最高格保持合法）。通用判据：写校验链的负向验证时，先问「注入去掉这一层
    后，后面还有哪一层会抛同样的错」。
11. **断言读的是按 id 为键的 Map 的 size** → 注入「不去重」仍全绿。M7 controller 去重测试踩坑：
    `_controllers` 重复创建会**覆盖写** → size 恒为 1，注入后 size 断言不变。去重的真实价值是
    防创建多余对象（旧对象没 `dispose` → 引用泄漏），**不在 size 上**。修法：比较**对象引用**
    （`first === second`）+ 原对象未被 dispose。通用判据：断言「不重复创建」时先确认该数据结构
    是覆盖写还是追加写 —— 覆盖写时 size 永远看不出重复。
12. **断言落在「测试自己构造的路径」而非「用户真实走的路径」** → 用户实玩才暴露缺陷，注入后仍全绿。
    M7 最严重的一例（用户报告：背包选巢穴图标后右键只放出一个单格方块）：测试手工伪造
    `player.target` 且**只走 `selectPlaceable()` 测试 API**，而玩家真实走的是「背包选中 →
    `placeBlock()` 按物品名分流」路径 → 那条路径**零覆盖**。更隐蔽的一层：把背包路径测试与
    API 测试**合并到同一个 test** 时，前面调过的 `selectPlaceable()` 残留 `_selectedPlaceable`
    标志 → `placeBlock` 优先走 API 分支 → 注入在背包分支的缺陷不被触发，断言恒真。
    **修法**：① 测试从**用户实际入口**进入（背包选中真实图标 + 真实 DDA `blockPos`/`prevPos`）；
    ② 断言落在**最终产物**上（用蓝图核对全部 38 格落地，而非只看「调没调 place」）；
    ③ 多条放置路径必须**各自独立成 test**（新 page = 新实例，消除残留状态互相掩盖）。
    **通用判据**：写接线类测试前先问「玩家实际会怎么触发这个功能」，再决定测试从哪进入 ——
    有测试 API 不等于玩家会用它。

另一类（v1.65 / 2026-10-21 新增，用户复测才暴露）：

13. **断言落在「中间数据层」，而缺陷在它下游的「派生产物层」** → 修完仍全绿、用户截图里缺陷还在。
    「灯光有边界」第一次修复时，E2E 与单测都只断言 `column.light`（数据）—— 那一层确实被修对了（整图参考 BFS
    对比 0 个格子不一致），可缺陷在**由 light 派生的网格**：实际上传的 6 个 section 是旧的（Y 方向的脏标记
    传播漏了、在途 mesh 回包被丢弃后无人重发）。两个缺陷都满足「数据对、画面旧」，**数据层断言结构上抓不到**。
    **诊断手法 = 三层逐层缩小**（哪层第一次出现差异，缺陷就在哪层）：
    ① 数据层：整图参考实现（不做区域截断）vs 实际数据；
    ② 网格层：拦截 `renderWorld.uploadSection` 记录「实际上传了什么」，对照 `buildSectionMesh(当前数据)`
       逐顶点比较（两者只差「是否过期」这一个变量）；
    ③ 画面层：截图（夜景下灯光最明显；强制按当前数据重建后再截一张做差分）。
    **修法**：断言落在最终产物上（`tests/light-mesh-sync.spec.mjs`）；并为每个「派生缓存 ← 源数据」的依赖
    关系写**交叉比对**用例（`test-lighting.js`：pocket 世界里「预测依赖集合 == mesher 实测变化集合」）——
    判据落在「派生层真的读了哪些格」上，而不是落在依赖函数自己的假设上。
    **通用判据**：凡有「源数据 → 派生缓存（网格/AO/可见面）」的链路，测试必须覆盖「源变了 → 缓存同步」这一跳，
    而不是只测源。另外两点实测教训：① 缺陷与**地形几何**强相关（y=-1 的沙滩恰在 section 最上层，换个地形
    就藏起来）→ 用夹具把几何固定下来（顶面 y=79 的石头地面），不要依赖 seed；② 偶现类竞态
    （在途结果被丢弃）不要靠时间碰运气，**在被测代码的接缝处挂钩子确定性构造**（观察到在途 mesh 的同一个同步
    片段内做同 column 编辑），并加 sanity floor（`fired === true`）防空转。
14. **监控指标在缺陷出现时读数反而更好**（RedCity 烘焙不变量实测）：旧 I5 只数「竖向接触不一致」（`contactBreaks`），而同一列的块共用同一个平移量，
    竖向邻居永远不会被破坏——把烘焙改成「逐列平移」（正是旧 I5 想防的缺陷）后读数从 84 变成 **0**，门禁更绿。
    判据：给「防 X」的指标写测试时，先问「X 出现时这个指标会变大还是变小」；方向不对就换指标（严格 I5 数同一刚性分量内部的全部相邻对，注入后 504）。
15. **Tier 2 数据门禁自身也要做篡改注入**（RedCity `check:data` 实测）：第一版 `[RedCity]` 环节对「同列 dy 降序、palette 下标越界、三元组丢失、ground 与方块脱节」
    四类产物损坏全部放行（只信记录值 / 只验了头部）。修法 = 对产物副本逐类注入、确认每类都红，并把校验分两层：运行时加载器 `prepareRedCityModel` 校验形状
    （越界 `col` 写进 `Uint32Array` 会被**静默丢弃**，方块凭空消失），`check:data` 重算语义（I1/I2/I3、岛内列地面方块存在、三元组数 === `stats.retained`）。
16. **「改动了世界」的计数不能看被测 API 的返回值**（RedCity R15 编辑耗时观测用例实测）：`world.setBlock` 不做 no-op 检测——同值写入也返回非空并照样触发重建，
    所以用 `if (r1) changed++` 计数时，把放置的方块换成 air（= 在空气里放空气）计数仍是 200，负向验证**照样通过**。
    修法 = 在计时之外对比写入前后的方块 id（`was !== new && getBlockId(...) === new`）。判据：写「确实改动了」类 sanity 断言时，先用一次 no-op 注入确认它会红。

还有一类**看起来是缺陷但不是**：注入「`<` 改 `<=`」在丧尸排斥边界上仍全绿 —— 因为
`distance == minDistance` 时 `force = (minDistance-distance)/minDistance×strength` 本就为 0，
两种写法数学等价。这种情况不算漏网，但须**改用字面量输入 + 前提断言**，并补一条配对断言
（「略小于半径须有排斥」）才能真正钉住边界语义。

> **注入未生效会造成「假全绿」**（M7 巢穴图标改动实测）：用 perl/sed 做注入时若模式没匹配上
> （实测：模式要求 `'mine_cart', 'hanging_lamp',` 前是两个空格缩进，实际它接在
> `'vine', 'lilypad', ` 之后 → 静默未替换），源码没改 → 重烘焙后判据仍 100% 全绿。
> 这与第 10/11/12 类「断言落点错」同源但**方向相反**：那边是「注入生效了但断言抓不到」，
> 这边是「断言没问题但注入没生效」。
> **判据**：注入后必须**读回源码/产物的关键标识**确认注入真的落地（本例读指纹串
> `flat;...` vs `geom:box;...` —— 一眼区分平面/等轴测路径），不能只看「判据变红了」。
> 注入是**负向验证的前提**，前提没验证就等于没做负向验证。
> 修法：优先用 Edit 工具（精确匹配，失败会报错）而非 perl/sed（静默不匹配）。

> **测试 fixture 自身的耦合缺陷会让断言假失败**（M7 实测，与盲区同源但方向相反）：
> 刷怪搜索测试里 `supportAt` 在 `footY-1` 铺支撑，而**相邻层的支撑格正是下一层的脚格** →
> 给上层铺支撑会填掉下层脚格，两层互相污染（数学必然：同一列最多只有一层合法）。
> 表现为 `spawn=0`，看起来像实现坏了，实则是 fixture 写错。
> 判据：构造「使某候选合法」的 fixture 时，先问「这个写入会不会同时改变**其它**候选的合法性」。
> 修法：只铺目标层支撑；需要「A 非法、B 合法」对照时改用**同 dy、不同偏移**让被测条件成为唯一变量。

## 3. Tier 2 — 需要门禁断言，免 TDD 流程（数据契约 / 集合口径）

### 3.1 适用范围

值是**约定**而非**算法**：改错了立刻可见，修复成本 = 改回去。这类改动**不需要 RED-GREEN**，
改完跑 `npm run check:data` 即可。

| 对象 | 例子 |
|---|---|
| 方块→贴图映射 | `voxel/faces-data.js` 的 tile 名 |
| 图标平面清单 | `tools/icon-fingerprint.mjs` 的 `FLAT_BLOCKS`（哪些方块走平面贴图而非等轴测） |
| 物品排除集合 | `NON_PLACEABLE_ITEMS` / `HIDDEN_FROM_INVENTORY` |
| atlas 产物 | tile 数、gutter、size |
| 资源路径常量 | `WEAPON_ASSET_URLS`（M4）之类 |

> **v1.26 变更**：`ui/hotbar.js` 的 `INVENTORY_ICONS` 图标表已删除（图标改为全量离线烘焙产物
> `assets/icons-atlas.png` + `icons.json`）。改背包内方块的贴图/几何后须重跑 `npm run icons`
> ——忘跑会被 `check:data` 的指纹检查抓到（见 §3.3）。

### 3.2 关键改造：关系型断言取代硬编码计数

**这是本次 harness 升级的核心。** 硬编码计数断言（`expect(count).toBe(156)`）是「改动放大器」：
新增一张贴图就要改 3 处（spec + CLAUDE.md + 设计文档），改的是**同一个事实的三个副本**
（违反红线 1 精神：数据只有一份权威）。

改为**关系型断言**——校验不变式，而非钉死数值：

| 旧（硬编码） | 新（关系型） | 好处 |
|---|---|---|
| `expect(count).toBe(156)`（历史断言） | `faces-data` 引用的每个 tile 都必须在 atlas 里 | 新增贴图**不用改断言**；悬空引用当场报错 |
| `expect(items).toBe(118)` | 物品集合 = `registry.all()` − 两个排除集合 | 改排除集合**自动跟上**（原型已实测验证） |
| `expect(iconCount).toBe(9)`（v1.24） | 图标**输入指纹**比对：几何顶点序列 + 贴图名 + 贴图内容哈希 | 改几何/贴图/换同名 PNG 忘跑 `npm run icons` → 当场报错（图标静默过期） |

> **v1.26 变更**：atlas 现为 147 tile（背包图标已独立到 `icons-atlas.png`）。第一行的 `toBe(156)`
> 是**历史反例**——它正是要批判的「硬编码计数」反模式，实际已改为与 `assets/textures` 的 PNG 数
> 比对（`atlas.spec.mjs`），新增贴图自动跟上。第三行的图标同步从「tile 计数」改为**指纹比对**
> （精确判定，含贴图内容哈希，能抓「换同名 PNG 内容」这条计数抓不到的路径）。

**保留硬编码的例外**：`size=2048`、`gutter=16` 是**设计常量**（§4.4.1 定稿），不是随改动漂移的
计数 → 保留 `toBe`。判据：这个数是「设计决策」还是「事实统计」？前者钉死，后者用关系式。

### 3.3 Tier 2 的门禁

`npm run check:data`（`tools/check-data.mjs`，~1s，无需浏览器）：
- **引用完整性**：`faces-data` + 平面图标手工 tile 引用的 tile 必须都存在于 `atlas.json`
- **物品集合关系式**：`buildItemNames(registry)` ≡ `registry.all()` − 排除集合
- **图标 manifest 覆盖**：背包集合与 `icons.json` 两套尺寸档**双向一致**（缺项 = 忘跑 icons；
  幽灵项 = 方块移出背包但 manifest 残留）
- **图标 atlas 产物**：`icons-atlas.png` 存在且尺寸与 `icons.json` 的 `size` 一致
- **图标过期指纹**（v1.26 核心）：用当前源码重算每个方块的输入指纹与烘焙时写进 `icons.json`
  的比对，不匹配即报「跑 `npm run icons`」。指纹含**贴图内容哈希** → 能抓「换同名 PNG 内容」
- **几何路径正确性**：非实心方块必须在 `FLAT_BLOCKS`（否则被当实心立方体渲染，错）；异形
  geometry 指向缺失的 `TEMPLATES` 条目 → 静默 fallback 立方体（错）。`geometry='box'`/null 是
  正常的单位立方体标记，**不是缺陷**
- **测试注册完整性**：`src/tests/test-*.js` 必须全部出现在 `src/tests/index.html`
  （漏注册 = 测试静默不跑，比测试失败更危险）

**改指纹逻辑时须手动重跑的三条负向验证**（`tools/icon-fingerprint.mjs` 无自动化测试，见 §9 例外）：

| 路径 | 做法 | 预期 |
|---|---|---|
| 改几何 | 改 `mesher.js` 某个 `TEMPLATES` 条目的顶点 | 不跑 `npm run icons` 直接 `check:data` → 报该方块过期 |
| 改贴图映射 | 改 `faces-data.js` 某方块的 tile 名 | 同上 → 报该方块过期 |
| 换同名 PNG 内容 | 改一张贴图 PNG 的像素、不动 `faces-data` | 同上 → 报该方块过期（这条最易漏：只钉贴图名抓不到） |

验完把改动还原。第 3 条同时验证**不误报无关方块**（改 `stone.png` 时 `mine_cart` 不应被报）——
实测踩过这个缺陷，根因是平面路径的取图口径（`flatTile()`）与指纹不一致。

### 4.1 适用范围

### 4.2 既有 Tier 3 型测试的处理

`src/tests/test-ui.js` 与 `test-inventory-ui.js` 曾有 **13 个**用例钉死具体 tile 名或 CSS 值
（如断言 `tileOfName('planks_step') === 'inventory-icons/planks_step'`）。这类用例的处置：

- **钉值的用例随事实更新或随载体删除**：v1.26 把图标改为离线烘焙产物后，`tileOfName()`/
  `INVENTORY_ICONS` 已删除 → 测它们的 9 个用例**一并删除**（不是「保留但降级」）。
  它们保护的失效路径「图标回落 `faces-data` → 撞脸」在新架构下**结构上不存在**
  （图标不再从 faces-data 派生，而是独立烘焙），等价保障改由两处承担：
  ① Tier 1 单测 `test-iso-icon.js` 钉「`grass` 顶面必须是草绿、不得采成土色」；
  ② `check:data` 的图标契约（manifest 与背包集合双向一致 + 指纹未过期）。
- **钉不变式的用例必须保留并迁移**：「异形方块图标必须与母方块不同」「竖柱 vs 横梁形状不同」

  v1.26 把它们从「读旧 PNG」迁到「读 `icons-atlas.png` 裁矩形」，判据不变。

判据：**断言钉的是「值」还是「不变式」**？钉值 → 随载体存亡（载体删了就删，别为死代码留断言）；
钉不变式 → Tier 1，载体变了要迁移而不是删除。

## 5. Tier 4 — 视觉验证（GPU 渲染结果）

### 5.1 适用范围

正确性只在 GPU 渲染结果里，单测测不到（TSL 节点在 GPU 求值，主线程读不到片元输出）：
- `render/materials.js` 的片元逻辑（emissive 加项、bit13 解包）
- 图标的像素观感、吊灯 UV 分区效果、床的镂空问题

### 5.2 验证口径

- **像素级实测取代目视**：截图 → canvas 读像素 → 行剖面 / 亮度差 / 色数统计，
  判据是「形状必须与 `TEMPLATES` 几何定义对应」（v1.24 已建立此方法论）
- **必须标注环境限制**：本环境截图的 `Read` 只返回 URL、不渲染成图像 →
  **不能宣称目视验证**，须明确写「改用像素级实测代替」
- **像素级 diff 要有对照组**：改动侧 vs HEAD 的 diff 像素数 + 整体亮度均值，
  证明「只有目标局部变化」（吊灯 emissive 那次：2006 px 差异 / 亮度均值 150=150 不变）
- **断言阈值须匹配 `outputColorSpace`**：fixture 若用 `LinearSRGBColorSpace` 输出
  （ao-corner fixture 口径），读到的是纹理 sRGB→linear **解码后**的值（实测 `[64,107,48]` →
  `[13,37,8]`，三个值精确等于解码结果）→ 阈值得按 linear 写、不直觉且易错。丧尸头部 fixture
  改用 `SRGBColorSpace`（真实游戏口径）→ 读到的值接近原始纹理参数，阈值可对着图案参数读。
- **取样点须对准被测图案的实际位置**，不能凭几何直觉推：见 §2.7 第 9 类盲区
  （`BoxGeometry` 各面 `vdir` 符号不同导致跨面取样偏一格）。

## 6. 门禁分层与执行时机

| 层 | 命令 | 耗时（本机实测 2026-09-03） | 何时必须跑 |
|---|---|---|---|
| **静态架构门** | `npm run check:arch` | 285ms（扫 51 个源文件） | **每次改 `src/**`**（红线回退当场拦住） |
| **数据契约门** | `npm run check:data` | 307ms（7 项检查） | 改了 `faces-data` / `inventory` / `tools/` / atlas / 背包内方块的贴图或几何 |
| **lint** | `npm run lint` | 1.1s | 每次改 `src/**/*.js`（0 error，warning 可接受） |
| **单测** | `npm test`（`tests/harness.spec.mjs` 跑全部浏览器单测） | ~10s | 改了 Tier 1 对象 |
| **全量 E2E** | `npm test`（27 spec） | ~2.8min | 里程碑收尾、提交前 |
| **性能门禁** | `npm run bench -- --check` | ~5min | **碰了热路径**（mesher / materials / render-world / scheduler / physics） |

**便利入口**：`npm run check` = `check:arch` + `check:data` + `lint`（**2.6s 实测**，日常改动的最小门）。

### 6.1 分级 → 门禁映射

| 改动类型 | 最小必跑门禁 |
|---|---|
| 改贴图地址 / alias / 文案（Tier 3） | `npm run check` |
| 改物品集合 / `FLAT_BLOCKS` / atlas（Tier 2） | `npm run check` |
| 改纯函数算法 / 协议 / 数据模型（Tier 1） | `npm run check` + `npm test` |
| 改热路径（mesher/materials/render/scheduler/physics） | 上述 + `npm run bench -- --check` |
| 改 GPU 材质效果（Tier 4） | 上述 + 像素级实测 |

**不要**：为了改一个贴图地址而跑 5 分钟 bench 或全量 E2E。
**也不要**：改了 mesher 几何却只跑 `check`（热路径必须跑 bench）。

### 7.1 已知例外（白名单，需注明理由）

| 例外 | 理由 |
|---|---|
| `src/mesh/atlas-loader.js` import three | 它**不是** Worker 同构模块——只被 `core/game.js` 消费，负责运行时加载 atlas 纹理（必然依赖 three）。分层归属应为 `render/`，但历史放在 `mesh/`。**不移动**（属架构改动，需设计文档先行），在白名单注明 |
| `src/core/**` 依赖任何层 | `core/` 是**装配层**（`game.js` 组装全部子系统），必然依赖所有层。CLAUDE.md 原写「core/ 不依赖 voxel/」**是错的**，已修正 |

### 7.2 依赖方向的已知例外（待决策，不擅自修）

`src/voxel/world-data.js:6` → `import { recomputeSkylightAt } from '../mesh/lighting.js'`

  这是**算法依赖不是渲染依赖**；voxel 仍「不知道渲染存在」
- **门禁处理**：列入白名单并注明理由，**不擅自重构**（把 `recomputeSkylightAt` 挪进 voxel 层
  属架构改动，须先改设计文档 §3 分层图再动代码）
